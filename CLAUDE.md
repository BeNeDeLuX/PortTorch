# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

PortTorch is an internal, Shodan-style network reconnaissance platform made of two independently deployed components in this monorepo:

- **`/scanner`** (Go): a CLI that runs the scan pipeline (masscan → nmap → gowitness/RDP screenshots) and ships results to the webserver.
- **`/server`** (Node/TypeScript + PostgreSQL + React frontend under `/server/frontend`): a separate webserver with the dashboard, auth, and the database. Multiple scanner instances feed the same database.

## Commands

This monorepo splits build/test commands and deep component-specific architecture into two nested docs - read them when you're actually working in that half:

- `@scanner/CLAUDE.md` - Go scanner: build/test/lint commands, the scan pipeline stage-by-stage, submission durability/panic recovery, IPv6 targets, the installer.
- `@server/CLAUDE.md` - Node/TS webserver + React frontend: build/test/migrate commands, the scan-request queue, database shape, roles/permissions, webhooks, the external API, and everything else dashboard-side.

This file has what's genuinely cross-cutting: the project overview, the full-stack quick start, and the handful of features (excludes enforcement, Scan Profiles, scanner self-update, logging conventions, versioning) that only make sense described across both components at once.

### Full stack

```
cp .env.example .env           # fill in secrets first
docker compose up -d --build   # postgres + webserver; runs migrations and seeds the admin user on boot
```

The webserver generates its own self-signed TLS cert into `/data/certs` on first boot (see `server/src/tls/generateCert.ts`) — there's no separate cert setup step.

## Architecture

### Why two separate services

The scanner and webserver are split deliberately, and **all communication is scanner-initiated** (outbound HTTPS from scanner to webserver). This is a hard constraint that shapes several features below: the webserver is never assumed to be able to reach back into a scanner's network segment, since scanners may sit behind NAT/firewalls on arbitrary internal subnets. Every scanner authenticates with its own API key (`scanner_agents` table, created via the dashboard's "Scanner-Agents" page or `POST /api/agents`), hashed with SHA-256 for lookup (not bcrypt — API keys are high-entropy, not user passwords).

### Scan excludes are enforced scanner-side, fetched fresh before every scan

The dashboard's admin-only Excludes page (`scan_excludes` table, `kind` = `ip`, `port`, or `ip_port`, nullable `scanner_agent_id`) is the single source of truth for targets that must never be scanned — but the enforcement point is the scanner, not the webserver, and deliberately so: a manual `porttorch scan --target ...` run directly on a scanner host never goes through the webserver's queue at all, so filtering only in `scan_requests` creation would miss it entirely. Instead, all three entry points (`main.go`'s `runScan`, `internal/api/server.go`'s `runScan`, `internal/tui/commands.go`'s `runScanCmd`) call `client.Client.GetExcludes` (`GET /api/ingest/excludes`, API-key auth) immediately before `pipeline.RunScan` — fetched fresh every time rather than cached, so an admin's most recent change takes effect on the very next scan, and a fetch failure aborts the scan (fail closed) rather than proceeding unfiltered.

`scanner_agent_id IS NULL` means an exclude is the inherited default (applies to every scanner); a non-null value scopes it to one specific scanner *in addition to* the defaults (`GET /api/ingest/excludes` returns the union, not a replacement) — this exists because private IP ranges commonly repeat across scanners sitting in different, unrelated networks, so a global IP exclude keyed only on an address like `10.0.0.5` could silently exclude the wrong host on a different scanner's network entirely. Two partial unique indexes (`scan_excludes_global_unique`, `scan_excludes_scanner_unique`) enforce no-duplicates separately for global vs. per-scanner rows, since Postgres's plain `UNIQUE` treats every `NULL` as distinct and wouldn't catch duplicate global entries on its own.

`kind = 'ip'` accepts a single IPv4 address, a CIDR range, or a plain `startIp-endIp` range like `10.0.0.1-10.0.0.10` (`lib/net.ts`'s `isIPv4Range`) — masscan's own target-spec grammar already accepts that exact range syntax (confirmed against a real masscan run), so this only needed a validation change, no scanner-side one. IP/CIDR/range excludes are passed straight to masscan's native `--excludefile` flag (`pipeline/excludes.go`'s `writeExcludeFile`), which skips them even inside a larger targeted range; masscan has no equivalent for ports, so port/port-range excludes are subtracted from the requested port spec in Go (`subtractPorts`/`parsePortSet`/`serializePortSet`) before masscan ever runs — nmap only ever sees the ports masscan actually found open, so a port excluded here never reaches nmap either. Also accepts a single IPv6 address or an IPv6 CIDR (`lib/net.ts`'s `isIPv6`/`isIPv6Cidr` — deliberately no IPv6 "start-end" range counterpart, matching the scanner's own IPv6-target scoping decision, see `scanner/CLAUDE.md`) — since there's no masscan step in the IPv6 discovery path, these are enforced by the scanner's own `isTargetExcluded` (`pipeline/ipv6.go`) instead of `--excludefile`, see `scanner/CLAUDE.md`'s "IPv6 targets" section.

`kind = 'ip_port'` (value `"ip:portSpec"` for IPv4, e.g. `10.0.0.5:3389` or `10.0.0.5:8000-8010`; `"[ipv6]:portSpec"` for IPv6, e.g. `[2001:db8::1]:3389` — bracket notation is required there specifically because an IPv6 address itself contains colons, so a plain first-colon split can't unambiguously tell address from port; single address only, no CIDR/range for either family) is the odd one out: neither masscan's `--excludefile` (whole IPs/CIDRs/ranges only) nor its port spec (applies uniformly to every target) can express "skip this port on this one host but scan it elsewhere". So unlike the other two kinds, this is enforced *after* discovery — `pipeline.RunScan` calls `filterIPPortExcludes` (`excludes.go`) on the discovered results (from masscan for IPv4, or `RunNmapDiscovery` for IPv6) before the nmap enrichment stage, dropping any matching (ip, port) pair (and the whole host entry if that leaves it with zero ports); masscan/nmap discovery still probes that exact host:port, the exclude only means nothing downstream ever sees a match. `ingest/routes.ts`'s `GET /excludes` (which reconstructs `{ip, portSpec}` for the scanner) needs the same bracket-aware split — the scanner itself needs no changes here, since `client.go`'s `Excludes.IPPorts` already receives clean, pre-split fields regardless of family.

### Address patterns: in a scan's target, and as a permanent exclude

"Scan 10.46.0.0/16 but never .2 and .4 in any /24", or "scan only the .125 in each /24", used to mean typing out hundreds of addresses. A schedule then kept the list and forgot the rule behind it. `server/src/lib/targetPattern.ts` is a small grammar for it, shared by both places a pattern can appear so a pattern means the same thing in each:

- each octet is a number, `*` or a range `a-b` (`10.46.*.125`, `10.46.1-20.*`);
- a token starting with `!` excludes, either a plain address, CIDR or range, or a pattern that may give only the trailing octets (`!*.2`, `!*.0-9`);
- tokens are separated by commas or whitespace, so `10.46.0.0/16 !*.2 !*.4` works as typed.

**The scanner never sees a pattern, so no scanner needs updating for either use.** Both are expanded on the webserver into the plain grammar masscan and the scanner already take.

**In a target**, `scanGroups/queue.ts`'s `queueScan` expands the pattern before anything else: before the split across scanners, before the length limit, before the row is written. `scan_requests.target_spec` holds the expansion, which is what the scanner runs. `scan_requests.target_pattern` (migration `1747000000000`) keeps what was asked for, so Scan History and the queue show the pattern and Rescan reuses it. A schedule and a scan group store the pattern itself, so a schedule re-expands it on every run. Schedule save, the estimate and the External API all reject a pattern that does not expand, with the reason, so a typo fails the save rather than every run after it. A spec with no pattern syntax is returned byte-identical, so nothing that worked before changes shape.

The bounds are honest rather than silent:

- An exclusion pattern is tested address by address, so it is limited to a /12 worth of addresses.
- The expansion must fit the 64 KB one masscan argument can carry.
- An expansion that leaves nothing to scan is an error, not an empty scan.

**As an exclude**, `scan_excludes.kind = 'ip_pattern'` stores a range plus a pattern as one value (`10.46.0.0/16 *.2`). One value means the existing `(kind, value)` uniqueness covers it, so the same pattern in two ranges is two rules; whitespace is canonicalised so the same rule typed twice is a 409. `GET /api/ingest/excludes` expands it on every fetch into the addresses and ranges it covers, appended to `ips`. The scanner then enforces it through the same masscan `--excludefile` as any other IP exclude: fetched fresh before every scan, fail-closed, manual CLI scans included. The range is required and limited to a /12, so the list a scanner receives stays bounded. masscan was confirmed to honour `start-end` lines in an exclude file: a /24 minus a ten-address range and one address scanned 245 hosts.

Found while building it: the exclude route's validity check was written `kind === "ip_pattern" || kind === "ip" ? ... : ...`, which JavaScript reads as `(... || ...) ? ...`. That ran every pattern through the IP check and rejected all of them. The integration test caught it before anything shipped.

Verified by unit tests on the grammar (both examples above, octet ranges, suffix exclusions, passthrough of hostnames and IPv6, every refusal), by `targetPatterns.integration.test.ts` (ad-hoc, split, schedule re-expansion, estimate, history, External API, pattern excludes served to a scanner), and in a real browser: an estimate reading "expands to 65,024 addresses", a typo refused before queueing, the queue showing the pattern, and a pattern exclude listed as 256 addresses.

### Ad-hoc Scans: a DNS hostname target, resolved on the scanner

The dashboard's **Ad-hoc Scans** page (and its External API counterpart, `POST /api/v1/scans/adhoc`) fires a single one-shot scan against an arbitrary target - no schedule, and no requirement that the target already be a known host, unlike the Rescan button. Mechanically it's just another `scan_requests` row (`host_id: null`), so it shares the entire existing queue path with Rescan/Schedule Scans; see `server/CLAUDE.md` for the webserver half and the frontend.

**What makes it cross-cutting is the target field accepting a plain DNS hostname, which only the scanner can correctly resolve.** The webserver never resolves it - same reasoning as excludes being enforced scanner-side above, and rooted in "Why two separate services": scanners sit behind NAT/firewalls in networks the webserver has no visibility into, commonly with internal-only or split-horizon DNS, so a name resolved centrally would be wrong or unresolvable for exactly the targets this exists for. `scan_requests.target_spec` therefore carries the typed string untouched - no new column, no validation beyond non-empty, no ingest-endpoint change - and `pipeline.RunScan` resolves it at scan time (`isHostname`/`resolveHostnameIPv4`, IPv4-only and first-address-only, failing closed on a resolution error), then merges the original hostname into the `probeHostnames` map so that scan's TLS SNI and gowitness screenshot URL automatically use it. See `scanner/CLAUDE.md`'s "A DNS hostname target is resolved scanner-side" section for the Go-side detail and why it lives at the pipeline level (every entry point gets it, not just the queue-driven one).

### Scan Profiles: choosing which NSE scripts a scan runs

A scan's NSE script list no longer has to be the fixed 31-script Default set documented above - triggering a rescan (Dashboard bulk, Host Detail single) or creating/editing a Schedule Scans entry now offers a **profile** picker: **Default** (unchanged, today's hardcoded 31), **All Safe Modules** (nmap's own `safe and not intrusive` category, unioned with Default via `dedupSorted` rather than a plain swap - a union specifically so nothing already in Default can ever be silently dropped by switching profiles), or a named **Custom** profile with its own admin-curated script list (`/scan-profiles`, admin-only CRUD page).

**The webserver only ever sends a symbolic profile kind to the scanner - never the ~349-script "All Safe" list itself, and never the 31-script Default list either.** Both canonical lists live only in the Go scanner (`scanner/internal/pipeline/nse_default_scripts.go`'s `DefaultNSEScripts`, extracted verbatim from the old hardcoded `RunNmap` string; `nse_safe_scripts.go`'s `AllSafeNSEScripts`, captured from a real `nmap --script-help "safe and not intrusive"` run against the nmap version `install.sh` actually installs) - this avoids a second executable copy of either list that could drift, the same class of failure this codebase has a real documented precedent for (the `http-elasticsearch` incident described in `scanner/CLAUDE.md`'s Scan pipeline section, where one bad hardcoded script name broke nmap for every host in a scan). `RunNmap`/`RunScan` both gained an `nseScripts []string` parameter that falls back to `DefaultNSEScripts` when nil/empty, so every pre-existing call site (the one-shot `scan` CLI, the `menu` TUI, and `serve`'s own local REST-triggered scans) reproduces the exact previous `--script=` string byte-for-byte by simply passing `nil` - only the queue-triggered path (`internal/api/server.go`'s `pollOnce`) resolves a real value, via `resolveNSEScripts(profile, custom)`: `"all_safe"` → `pipeline.AllSafeNSEScripts`, `"custom"` → the scan request's own script list, anything else → `nil` (Default).

**Only a Custom profile's script list ever crosses the wire, and only as a resolved snapshot captured at creation/edit time - never a live foreign key.** `scan_profiles` (migration `1741800000000_scan_profiles.js`: `id`, `name UNIQUE`, `nse_scripts text[]`, `created_by`, `created_at`, `updated_at`) is the admin-managed source; `scan_requests` and `scan_schedules` each gained `nse_profile text NOT NULL DEFAULT 'default' CHECK (IN ('default','all_safe','custom'))`, `nse_scripts text[]` (set only for `'custom'`), and `nse_profile_label text` (a point-in-time display copy of the profile's name). `resolveNSEProfile(selection)` (`server/src/scanProfiles/resolve.ts`) is the one place that turns a `{kind:"default"|"all_safe"} | {kind:"custom", profileId}` selection into those three columns, called from every write path (the dashboard's own rescan endpoint, `rescan.ts`'s `requestRescan()` - now with an optional profile parameter, default `{kind:"default"}` so the External API's rescan endpoint keeps working unchanged - and `schedules/routes.ts`'s create/update) so they can't drift from each other. This snapshot design is deliberate and load-bearing in two directions at once: editing or deleting a custom profile later can never retroactively change an already-queued scan request or an already-fired schedule's history, and it's *why* hard-deleting a `scan_profiles` row is safe at all - there's nothing left for it to orphan. `scheduler.ts`'s `tick()` copies a schedule's own already-resolved `nse_profile`/`nse_scripts`/`nse_profile_label` straight onto each `scan_requests` row it spawns, rather than re-resolving from `scan_profiles` live, for the identical reason. Proven, not just asserted: an integration test creates a custom profile, rescans a host with it, then edits the profile's script list and re-reads the *original* `scan_requests` row's `nse_scripts` - confirmed unchanged.

`GET /api/ingest/scan-requests/next` (the scanner's own claim query) includes `nseProfile`/`nseScripts` in its response (deliberately not `nseProfileLabel` - display-only, the scanner never needs it). A Custom profile's script names are validated against `KNOWN_NSE_SCRIPTS` (`scanProfiles/knownNseScripts.ts` - a third, TS-side copy of the Go lists, used *only* for creation-time validation and the picker's checkboxes, never for execution) at `POST`/`PATCH /api/scan-profiles` time, rejecting a typo'd script name with a 400 immediately rather than only discovering it at scan time the way the `http-elasticsearch` incident once did. `frontend/src/components/ScanProfilePicker.tsx` (a plain `<select>`: Default / All Safe Modules / an `<optgroup>` of named Custom profiles) is the one shared control both `RescanModal.tsx` (opened by every rescan trigger point instead of firing immediately; remembers the last-picked profile per-browser via `localStorage`, but still always shows the confirmation - "a rescan's scope/intrusiveness can now vary a lot by profile") and `Schedules.tsx`'s form use. Editing an existing schedule can't reliably pre-select a matching Custom option in the dropdown (a schedule only carries the resolved snapshot, not a live profile id) - rather than guess and risk silently reverting to Default, the profile field is simply left untouched unless the admin deliberately interacts with the picker (`profileTouched`), with the schedule's current effective label shown as plain informational text instead.

**A fourth tier, "Active Modules," exists only as a source of additional script names for a Custom profile - it was deliberately never wired into execution as a selectable profile kind of its own.** `scanner/internal/pipeline/nse_active_scripts.go` captures nmap's own `intrusive`/`exploit`/`brute`/`dos` script categories into four lists (`ExploitNSEScripts` 45, `BruteNSEScripts` 75, `DosNSEScripts` 11, `OtherIntrusiveNSEScripts` 102 - the `intrusive` category minus whatever's already counted in the other three - 233 scripts total, all deduplicated against Default) - there is no `AllActiveNSEScripts` constant used by `RunScan`/`resolveNSEScripts` anywhere, and no `'active'` value in `scan_requests.nse_profile`'s `CHECK` constraint. These scripts can only ever enter a real scan as part of an arbitrary Custom profile's own already-snapshotted list - `knownNseScripts.ts`'s validation allowlist accepts them (so a Custom profile *can* include one), and the frontend renders them in their own "Active Modules" section on the Scan Profiles page (grouped into the same four nmap-native subcategories, each independently select-all-able, but with deliberately no single select-all across the whole tier) behind a `callout-danger` warning: these scripts are intrusive, exploit-attempting, credential-guessing, or can disrupt the target, and should only ever run against systems explicitly authorized for that kind of testing. A profile containing one gets a warning badge in the profiles list; `ScanProfilePicker` itself repeats the same warning centrally the moment a Custom profile containing one is selected in the Rescan popup or a Schedule's form - closing a real gap where the warning only ever showed while *building* the profile, not to whoever triggers a scan with it later, who may not be the same person and had no way to know.

The "All Safe Modules"/"Active Modules" script lists (hundreds of names each) render as one script per line inside collapsible, per-category `<details>` groups (`frontend/src/lib/nseScripts.ts`'s `groupAdditionalNseScripts`/`groupActiveNseScripts` - prefix/name-based heuristic grouping for the "safe" tier, since nmap's own categories don't subdivide it further; the "active" tier's four nmap-native categories need no such heuristic) rather than one long flat checkbox grid, which had become unreadable at that length - each group's own checkbox reflects native tri-state `indeterminate` when only some of its scripts are selected.

### Tags an ad-hoc scan or a schedule can request, applied to every host it touches

Ad-hoc Scans and Schedule Scans both target a range, not a known host - so until this existed, there was no way to later ask "which hosts did *this* scan actually find" except re-reading its target spec by hand and reasoning about what it must have covered. `frontend/src/lib/scanTags.ts` (client-side, splits the comma-separated field) and `server/src/lib/scanTags.ts` (the actual validator - trimmed, 1-64 chars per tag matching the existing single-tag-add endpoint's own rule, capped at 20, deduped) are the two ends of an optional "Tags" field on both forms; the webserver applies whatever was given to every host that scan's own results touch, via the exact same `host_tags` table manual tags and the service-derived auto-tags already share. Once applied, a scan-requested tag is an ordinary tag - filterable on the Dashboard, removable by hand - which is the whole point: "find exactly what this scan found" becomes a tag filter instead of a re-derivation.

**Much simpler than the NSE/nuclei profile snapshot design right above, deliberately.** There is no admin-curated named list behind a tag, just the literal strings typed into the form - `scan_requests.tags`/`scan_schedules.tags` (migration `1746600000000_scan_request_tags.js`) are plain nullable `text[]` columns, nothing to resolve and nothing that can drift, copied onto every spawned request by `scheduler.ts`'s `tick()` the same snapshot-copy idiom as the profile columns use for the identical reason (editing a schedule's tags only changes its future runs).

**The tags have to reach the scanner and come back, because the webserver never learns which hosts a scan touches until the scanner tells it.** `GET /api/ingest/scan-requests/next` echoes `tags` back to the scanner alongside `nseScripts`/`nucleiTags`; the scanner (`client.ScanRequest.Tags`) carries them through `pipeline.RunScan` and re-sends them on every single-host `POST /api/ingest/hosts` call for that scan job as a top-level `tags` field - the scan's own tags, not a per-host concept, so every call for one scan job repeats the identical array. Only the queue-triggered path (`internal/api/server.go`'s `pollOnce`) ever resolves a real value; the one-shot CLI, the `menu` TUI, and the local REST API all pass `nil`, same "every pre-existing call site keeps producing exactly what it always did" discipline the NSE/nuclei profile threading established. `ingest/routes.ts`'s `ingestHostPayload` inserts them into `host_tags` with the identical idempotent `onConflict-doNothing` shape the service-derived auto-tags use, logged under a distinct audit actor (`"scan-tag"` vs. `"auto-tag"`) so the two are still tellable apart afterward even though they land in the same table with no source column.

**A submission that fails and gets queued for retry has to carry its tags with it, or a retried host would come back untagged** - `internal/submitqueue`'s `queuedItem`/`Enqueue`/`drainEntry` all gained the same `tags []string` field for exactly this reason, pinned by a test that queues a tagged host, drains it against a real HTTP handler, and inspects the actual JSON body that reached `/api/ingest/hosts`.

**Found and fixed while wiring the schedule side: `PATCH /api/schedules/:id`'s "nothing to update" guard was a hand-enumerated field list that `masscanRate`/`priority`/the four window fields were never added to** - so a patch containing only one of those silently 400'd as "nothing to update" despite being otherwise fully supported by the same handler, a real pre-existing bug that would have repeated itself the moment `tags` was added the same way. Replaced with `Object.keys(parsed.data).length === 0`, which can't drift out of sync with the schema again - safe against a real HTTP body specifically because `express.json()`'s `JSON.parse` can never produce a key with a literal `undefined` value, only an absent key or an explicit `null`. Also found the same day: `GET /api/schedules`' explicit column list was missing `tags` (and, independently, `skipped_runs`/`last_skipped_at` - left alone, since fixing that is unrelated to this feature and is noted here only so it isn't lost).

Verified end to end in a real browser against a disposable stack, not just at the API layer: typing tags into the Ad-hoc Scans form and submitting shows them in the confirmation line; creating a schedule with tags shows them on its row in the list; opening that schedule's Edit form pre-fills the exact stored value. Separately, a full ingest round trip (claim a tagged request, submit a host under it, re-submit it) confirmed the tag lands in `host_tags` exactly once, coexists with a service-derived auto-tag on the same host, and is attributed to `"scan-tag"` in the audit log where the auto-tag is attributed to `"auto-tag"`.

### Nuclei: web-application vulnerability scanning

A discovered HTTP(S) port previously only ever got a screenshot (gowitness) and whatever nmap's own service-detection/NSE scripts found - nothing actively checked it for known CVEs, exposed admin panels/config files, or misconfigurations. **nuclei** (ProjectDiscovery) fills that gap as an independent pipeline stage (`scanner/internal/pipeline/nuclei.go`), run against every port `isHTTPPort` already classifies for gowitness - same job shape (`nucleiJob`/`startNucleiWorkers` in `orchestrator.go`, mirroring `startGowitnessWorkers`), just a different external tool and a different result field (`HostResult.NucleiFindings`). Off by default and opt-in per scan/schedule, unlike NSE's Default tier which always runs something - nuclei never ran at all before this existed, and its templates range from purely informational to genuinely intrusive.

**Same symbolic-profile-over-the-wire design as Scan Profiles above, but the "Safe" tier is defined the opposite way round.** NSE's "All Safe Modules" is a hand-captured, embedded list (nmap's own `safe` category) - nuclei has no equivalent single stable category to point at: a real count against a freshly downloaded template tree returned **7625 distinct tags** (`cve2024`, `wp-plugin`, `lfi`, `intrusive`, ...), growing with every template release. So `resolveNucleiProfile` (`scanner/internal/api/server.go`, `server/src/nucleiProfiles/resolve.ts`) defines `"safe"` as an **exclude**-tags expression (`dos`, `fuzz`, `intrusive`) passed straight to nuclei's own `-etags` flag, not an allowlist - and for the identical reason, a Custom nuclei profile's tags get no `KNOWN_NSE_SCRIPTS`-style validation allowlist either (`nucleiProfiles/routes.ts`'s tag schema is a structural regex, not membership in a list) - an unrecognized tag just matches zero templates, a harmless no-op, a fundamentally different risk than an unrecognized NSE script name (a hard error that aborts nmap for every host in the scan, the `http-elasticsearch` incident). Severity values, being nuclei's own small fixed enum (`unknown`/`info`/`low`/`medium`/`high`/`critical`), are still allowlist-validated.

`RunNuclei` always passes `-t http/` - confirmed by real testing (a disposable container, nuclei v3.11.1, default templates against a deliberately misconfigured nginx exposing `.env`/`.git/config`) that without it, nuclei also runs its `dns/`/`network/`/`ssl/` template categories against the target hostname (DNS rebinding checks, nameserver fingerprinting, wildcard-DNS detection, etc.) - irrelevant to "does this HTTP(S) port have a web finding," and a meaningful chunk of wasted scan time for every host. That same real run is also where the exact `-jsonl` output shape was captured rather than guessed (`template-id`, `info.severity`, `matched-at`, `curl-command`, etc. - `info.reference`/`info.classification` are absent entirely, not just empty, on many templates) and where the finding "`port` is a JSON string, not a number" surfaced - `NucleiFinding.Port` is always set from the caller's already-known port instead of parsed from that field, sidestepping it entirely.

**`scan_requests`/`scan_schedules` gained `nuclei_profile`/`nuclei_tags`/`nuclei_profile_label`, identical snapshot semantics to `nse_profile`/`nse_scripts`/`nse_profile_label`** (migration `1742700000000_nuclei_profiles.js`) - resolved once at request/schedule-creation time, never a live join against `nuclei_profiles`, for the same reason that makes hard-deleting a `nuclei_profiles` row safe. `nuclei_findings` is its own table (one row per matched template per observation, not a JSON blob column - same "needs to be fleet-wide filterable/sortable" reasoning that already makes `ssh_host_keys` a dedicated table rather than a `host_port_observations` column) - `POST /api/ingest/hosts`'s existing per-host transaction inserts these alongside `ssh_host_keys`, diffing against the host's prior findings (keyed on `template_id`+`matched_at`) to decide whether a new `nuclei.finding` webhook event fires, the identical "only genuinely new things alert" idiom `host.new`/`port.opened` already use.

`NucleiProfilePicker.tsx` sits *alongside* `ScanProfilePicker` (not merged into it) in `RescanModal.tsx` and `Schedules.tsx`'s form - two independent choices for the same scan, since NSE scripts and nuclei templates are orthogonal concerns. Unlike `ScanProfilePicker`, it has no way to tell client-side whether a given Custom profile's tags happen to pull in something intrusive (no small "known risky tags" set the way Active Modules scripts have), so every Custom pick gets the same `callout-danger` warning rather than a conditional one. Findings get their own fleet-wide page (`/web-findings`, `WebFindings.tsx` - "Web Findings" rather than "Nuclei Findings" as the user-facing name, since nuclei is an implementation detail the page's own description already explains) rather than folding into `/vulnerabilities` - a template match's shape (template-id/severity/tags) doesn't map onto that page's CVE/CPE/CVSS/EPSS/KEV columns at all - and their own section on Host Detail (also "Web Findings", severity-badged reusing the existing `cve-badge cve-{severity}` CSS class, extended with `.cve-info`/`.cve-unknown` for the two severities CVSS's own four-level scale doesn't have).

Packaging is the *inverse* of masscan's (see "Scanner installer" below): unpackaged on Debian/Ubuntu and Fedora, but genuinely available via EPEL on RHEL-family (confirmed by testing - `dnf search nuclei` on Rocky Linux 9 matches `nuclei.x86_64` 3.11.0) - `install.sh` tries the EPEL package first there, `go install .../nuclei/v3/cmd/nuclei@latest` everywhere else, then runs `nuclei -update-templates` once, best-effort (not kept up to date automatically afterward - see `scanner/CLAUDE.md`'s installer section). Refreshing them later is an admin-triggered, dashboard-driven action rather than a manual SSH step, using the same polled-flag mechanism as scanner self-update below - and for a reason specific to nuclei: the template tree resolves against the invoking user's home, so a manual root-run update silently updates the wrong copy while the service keeps scanning with the old one. See `server/CLAUDE.md`'s nuclei-template-staleness section and `scanner/CLAUDE.md`'s watcher section.

### Large targets are discovered in blocks, and a scan that stopped early can be resumed

Two features that depend on each other. masscan reports nothing until its whole pass finishes, so a /16 across a real port list used to mean hours of silence before nmap saw a single host, and cancelling it threw away everything masscan had already probed. There was also no way back from a cancelled scan except running all of it again.

**Blocks (scanner, `pipeline/chunks.go`).** `planIPv4Chunks` splits a plain-IPv4 target into address blocks when the scan is estimated (addresses × ports ÷ rate) to take longer than 10 minutes. Each block is sized to take about 5 minutes, with a floor of 256 addresses. `RunScan` runs discovery as a list of steps in a producer goroutine, feeding a bounded nmap job channel, so nmap works on block 1's hosts while masscan scans block 2. Anything below the threshold, and any hostname or IPv6 target, is exactly one step with the spec as given, so the masscan command line is byte-identical to before. Three decisions carry this:

- **Addresses are split, never ports.** A host's submission is its whole result for the scan, and the webserver infers `port.closed` from a port inside the requested spec that is absent from the submission. A host submitted once per port block would close every port found in the other blocks.
- **The 256-address floor exists because masscan's rate is a total.** Fewer addresses per pass means more packets per address, so a block is never more concentrated than scanning one /24 is today. That is also why a /24 across 1-65535 stays one pass: it cannot be split without concentrating the probes.
- **IP excludes are subtracted before planning**, so no block is spent on addresses masscan would skip, and a fully excluded block does not exist. masscan still receives `--excludefile` for every block and stays the enforcement point; the subtraction is only for planning.

masscan waits about 10 seconds for late replies after every pass, which is why blocks aim for minutes rather than seconds. masscan and nmap overlap by at most one block's tail: the next block starts once the previous block's hosts are all handed to the nmap workers. A discovery failure in block 7 of 40 is reported only after blocks 1-6 have been processed and submitted, since those hosts were genuinely scanned.

**Resume (`pipeline.ScanCoverage`, `scan_jobs.remaining_target_spec`).** Real pause/resume is not possible. masscan and nmap are separate processes, and freezing a stateless SYN scanner loses every reply that arrives in the meantime. So resuming means "scan the rest", and the scanner can state the rest precisely. A block counts as covered once its discovery pass completed, because every address in it either turned up or definitely did not. A discovered host counts as covered only once its full result was handed on while the scan was still running. A host completing after cancellation may have had its screenshot or certificate probe cut short, and a host whose nmap call failed never completes, so both are scanned again. `Remaining()` merges unfinished blocks and hosts into as few `start-end` ranges as possible. A single-pass scan that never finished discovery returns the target exactly as typed, which keeps a hostname or IPv6 list intact. A resolved hostname comes back as the hostname, so the resumed scan still gets its SNI.

Only `serve` mode reports a remainder, on the completion `PATCH` for `cancelled` and `failed` (`CompleteScanJobWithRemainder`). The one-shot CLI and the TUI pass `nil`, because they cannot be cancelled from the dashboard. The webserver stores the remainder only for a non-completed status. It is deliberately not length-capped on ingest, because it reports work already done. `POST /api/scan-jobs/:id/resume` (operator, scanner-scoped, 404 out of scope) is where the 64 KB `targetSpecSchema` cap applies, the moment the remainder becomes a target. The endpoint:

- queues a `scan_requests` row on the same scanner with the same ports;
- copies the NSE and nuclei profile snapshots, rate, priority and tags from the originating request, unlike the Rescan button, because this finishes *that* scan;
- is one-time via a compare-and-set on `resumed_at`, so two clicks queue it once;
- refuses a revoked or deleted scanner.

Scan History shows "partly done" or "rest queued" beside the status, and a Resume button.

Verified at each layer: `chunks_test.go` runs the real `RunScan` against stand-in masscan and nmap binaries, splitting a /20 into eight blocks and cancelling during block 4, and asserts the remainder is exactly blocks 4-8. `scanJobResume.integration.test.ts` covers ingest, settings carry-over, the double-click and every refusal. Real masscan 1.3.2 was confirmed to read the comma-separated `start-end` block grammar ("Scanning 267 hosts" for a 256 + 11 spec). A browser drive against a disposable stack clicked Resume and found the queued request in the database.

### UDP scanning

Until this existed the pipeline was TCP-only apart from four hardcoded probes (`dnsrecursion.go`, `snmp.go`, `ipmi.go`, `upnp.go` - UDP/53, /161, /623, /1900), each its own stage against its own fixed port. There was no way to ask for an arbitrary UDP port at all, leaving NetBIOS, TFTP, the MS-SQL browser, syslog and DHCP entirely unseen on an internal-recon platform.

**No new grammar was invented: masscan and nmap already share one, and it's passed straight through.** A port spec now accepts `U:`/`T:` prefixes per comma-separated part - `80,443,U:53,U:161` - which masscan echoes back verbatim (confirmed with `masscan --echo`) and nmap accepts as its own `-p` argument. Bare parts stay TCP, so every spec that ever existed means exactly what it always did. `PortResult.Protocol` was already carried end-to-end from masscan's own `proto` field, so nothing downstream of discovery needed changing.

The two Go changes are both about **not** changing the TCP case. `pipeline/excludes.go` gained `parseProtoPortSet`/`serializeProtoPortSet` alongside the existing flat pair, and a TCP-only set serializes with no `T:` prefix at all - byte-identical to what `subtractPorts` always produced, so no existing deployment's masscan invocation changes shape. Port *excludes* stay deliberately protocol-agnostic: excluding 53 removes both TCP/53 and UDP/53, because an exclude means "never touch this port on this network" and `scan_excludes` has no way to express a protocol anyway. `nmap.go`'s `nmapPortSpec` groups the discovered ports by protocol and only adds scan-type flags when UDP is actually involved (`-sU`, plus `-sS` when TCP is present too) - with TCP alone, nmap's own privileged default is what has always run, and passing it explicitly would change every existing scan's command line to no purpose.

Verified against real tools rather than reasoned about: nmap 7.99 with a real dnsmasq on UDP/53 and a real TCP listener on 8080, confirming all three forms - `-p 8080` reporting tcp/8080, `-sU -sS -p T:8080,U:53` reporting both, and `-sU -p U:53` reporting udp/53. (That run also surfaced an unrelated packaging trap: Alpine's `nmap` package ships without `nse_main.lua`, so anything invoking `-sV` fails with "could not locate nse_main.lua" until `nmap-scripts` is installed too.)

**The webserver half of this is `port.closed`'s protocol awareness**, not the scan path - see `server/CLAUDE.md`. `host_port_observations` keys on `(port, protocol)`, so a UDP sweep that finds nothing on UDP/53 must not conclude TCP/53 closed; both `lib/portSpec.ts` and the ingest comparison match on protocol for that reason. The UI warns that UDP is much slower than TCP (`PortSpecHint.tsx`, shared by Ad-hoc Scans and Schedules) - an unanswered UDP probe can only be timed out, never refused, so a wide UDP range can run for hours or days where the same TCP range takes minutes, and it's genuinely easy to queue that by accident.

### Scanner self-update

An admin can trigger a scanner running in `serve` mode to update itself to the latest published `scanner-vX.Y.Z` release, straight from the Scanner Agents page - no SSH access to the scanner host needed. `server/src/scannerUpdate/githubSync.ts` syncs the GitHub Releases API hourly (well under its 60-req/hour/IP unauthenticated limit at one fetch/hour) into a singleton `scanner_release_cache` row (same id-1 idiom as `digest_email_state`), filtered to non-draft/non-prerelease `scanner-v*` tags and picked by the same plain X.Y.Z `compareSemver` this codebase now has three independent copies of (Go scanner, TS webserver, TS frontend - each self-contained enough that a shared package wasn't worth the coupling). `GET /api/agents/latest-release` (read-only, not admin-gated) is what feeds the "→ vX.Y.Z available" hint next to a behind-version agent everywhere the Scanner Agents page and Fleet Health already show a version. The sync itself (`syncScannerRelease`, exported) is also exposed as `POST /api/agents/latest-release/refresh` (admin-only, unlike the GET above - a real outbound request plus a DB write) so a just-tagged release doesn't sit invisible on the dashboard for up to an hour waiting on the next scheduled tick - the Scanner Agents page's "Check for updates now" button is the one caller, same "expose the scheduled job's own logic as a manual trigger" pattern as `server/CLAUDE.md`'s `runRetentionSweep`.

**The webserver can never push anything to a scanner - all communication is scanner-initiated (see "Why two separate services" above) - so an update request is a flag the scanner has to notice on its own next poll, exactly like scan cancellation.** `POST /api/agents/:id/request-update` (admin-only) does a compare-and-set `UPDATE ... WHERE revoked_at IS NULL AND update_requested_at IS NULL` (409 if the agent's gone, revoked, or already has an update outstanding) on four new `scanner_agents` columns (`update_requested_at`, `update_request_status` — null/`'pending'`/`'failed'`, `update_failure_reason`, `update_attempt_count`). `GET /api/ingest/update-requested` and `GET /api/ingest/scanner-release` (both scanner-authenticated, scoped implicitly to the calling agent) are what `scanner/internal/updater`'s `StartUpdateWatcher` polls at the same interval as `StartPolling`/`StartCancelWatcher` - started only from `serve` mode, since `scan`/`menu` are one-shot processes with no background loop that could ever notice a request in the first place.

**Applying an update replaces the running binary on disk and re-execs the same process in place - no systemd restart, no dropped connections to anything else the process was doing.** `checkAndApply` first defers entirely if a scan is currently in progress (`Server.IsScanning()`) rather than interrupting one - `syscall.Exec` replaces the whole process image immediately, which would abruptly kill any in-flight masscan/nmap child with no chance for the clean, deliberate "cancelled" status a real `/cancel` request gets; updates aren't time-critical, so simply waiting one tick for idle costs nothing. Before downloading anything, it checks both the binary and its containing directory are actually writable (`syscall.Access`, `W_OK`) and fails fast with an actionable "not writable - re-run install.sh" message rather than partway through a download. `install.sh` used to install the binary as root while the systemd service runs as the unprivileged `porttorch` user, which could never have overwritten its own binary - **a real, production-confirmed gap that chowning the binary file alone did not actually fix**: `os.Rename`'s replacement needs write access to the binary's *containing directory* too (to create and rename in a temp entry), and `/usr/local/bin` is `root:root 0755` on every stock Debian install regardless of who owns the one file inside it. Reproduced directly (a plain `chown`-only setup fails the exact same directory-write check `checkWritable` runs, as the service user, in a disposable container) before landing the actual fix: `install.sh`'s `grant_bin_dir_access` grants the service user a POSIX ACL (`setfacl -m u:porttorch:rwx`, not a chown/chmod of the shared directory itself, which other packages/admins may also install into) on `$BIN_PATH`'s directory - applied both right after a fresh build/download and again after user creation, so `--rebuild-only` alone retroactively fixes an existing deployment too. Confirmed the fix actually closes the gap the same way: the identical `checkWritable` check, run as the unprivileged service user against a directory with the ACL applied, passes; an unrelated file in the same directory that the service user doesn't own is still correctly untouchable, confirming the grant doesn't broaden access beyond what self-update itself needs. The actual replacement mirrors `install.sh`'s own `download_release_binary` exactly - downloads `porttorch-linux-<arch>` plus `SHA256SUMS` from the resolved release's GitHub URL and verifies the checksum before anything touches the real binary path - but is fail-closed with no source-build fallback (unlike the installer, which falls back to building from source on a download failure): a failure here just means the update attempt failed, reported back and retried later, never a scanner silently running unverified code. The verified binary is staged as a temp file in the *same directory* as the running binary (guaranteeing the final step is on the same filesystem) and `os.Rename`'d into place atomically - never an in-place truncate-and-write of the currently-executing file - before `PATCH /api/ingest/update-outcome {status:"succeeded"}` and, finally, `syscall.Exec` re-passing the exact original `serve --config <path>` arguments: same PID, same systemd unit, no restart event, serving again as the new binary immediately. A release that turns out not to actually be newer than the running version (a stale or already-applied request) is reported as success anyway, so it clears rather than retrying forever against a target that was never reachable in the first place.

**A stale `'pending'`/`'failed'` update status can also be left behind entirely outside the self-update mechanism** - a real case: an admin fixes whatever caused a failure (e.g. the directory-permission gap above) and reinstalls manually (`install.sh --rebuild-only` on the scanner host) rather than re-triggering through the dashboard, so the scanner's own watcher never gets the chance to call `PATCH /update-outcome` and clear anything. Left alone, the "update failed" badge would sit there indefinitely with no way to dismiss it, even once the scanner is demonstrably already current. `apiKeyAuth.ts` closes this the same opportunistic way it already records `version`/`submit_queue_pending` on every ingest request: if an agent has non-null `update_request_status` and its freshly-reported version already meets or exceeds the cached `scanner_release_cache.latest_version`, the four update columns are cleared right there - the version header itself is the evidence the goal was already reached, however it actually got there. Only bothers with the extra `scanner_release_cache` lookup when the agent actually has update state to reconcile (null for the overwhelming majority of requests), and only ever clears - it never sets or overwrites a `version` comparison the other direction. Confirmed against a real request sequence: a still-behind version leaves the failed status and its reason untouched, while a caught-up version (both `'failed'` and `'pending'` starting states) clears all four columns on the very next authenticated request, no dashboard click needed.

**A failed attempt is retried automatically, up to a point, then requires an explicit admin re-trigger rather than looping forever.** `PATCH /api/ingest/update-outcome {status:"failed", reason}` increments `update_attempt_count`; once it reaches `MAX_UPDATE_ATTEMPTS` (3), `update_requested_at` is cleared and `update_request_status` set to `'failed'` (terminal - the failure reason stays visible until an admin calls `request-update` again), otherwise the request stays `'pending'` for the next tick. The Scanner Agents page's per-agent "Update" button is gated on a deliberately imperfect, documented heuristic for "this agent looks like it's actually running in `serve` mode right now" (`scanner_agents` carries no explicit flag for that) - a recent `last_seen_at` (within 5 minutes), since every `serve`-mode request including the update watcher's own polls refreshes it; a false positive here just means the button does nothing until the agent's next poll, not anything harmful. A bulk "Update all outdated scanners" button reuses the exact same eligibility filter that decides which agents get their own individual button, so the two can never disagree about who's included, and loops the same single-agent endpoint (`Promise.allSettled`) rather than adding a second bulk API surface - the same frontend-only-reuse pattern the Dashboard's own bulk tag/rescan actions already established.

### Logging is SIEM-oriented, not incidental

Every stdout line on both services is a single JSON object (pino on the webserver, stdlib `log/slog` on the scanner) — no plain-text `console.log`/`fmt.Printf` mixed in on the `scan`/`serve` scanner paths or anywhere in the webserver, since a log shipper reading the stream line-by-line needs every line to parse. The scanner's interactive `menu` (TUI) is the one exception, since it owns the whole terminal screen. The core traceability event is `scan.host_scanned` (webserver, in `src/ingest/routes.ts`) — scanner identity, target IP, ports with state/service, source IP, timestamp — and `scan_job_id` correlates events across both services' logs. Never log secrets (API keys, passwords, session cookies, `Authorization` headers) — only IDs/names.

On the scanner side, `scan.host_submitted` (one line per host, emitted from each entry point's `onHostComplete` callback — see `scanner/CLAUDE.md`'s "Scan pipeline" section) is the per-host equivalent, logged the moment that specific host's data is actually submitted rather than only once at the very end — `scan_job_id`, `target_ip`, and `open_ports` on each line, with `slog`'s own timestamp giving an exact per-host submission time. `scan.host_submit_failed` is its failure counterpart.

The webserver's own `scan.completed`/`scan.cancelled`/`scan.failed` line (`PATCH /api/ingest/scan-jobs/:id` in `src/ingest/routes.ts`) reports the scan's runtime and what it actually found: `duration_ms` (`finished_at - started_at`), `hosts_scanned` and `open_ports_found` (`count(distinct host_id)` / `count(*) filter (where state = 'open')` against `host_port_observations` for that `scan_job_id`), plus `screenshots`/`rdp_screenshots`/`tls_certificates` counts from their respective tables. These are computed from what's actually in the database at completion time rather than trusted from the scanner's own tally in the `PATCH` payload (which only ever sends `{status}`) - the scanner already streamed every host/port/screenshot into these tables as the scan ran, so counting rows tagged with this `scan_job_id` here can't drift from what actually got persisted, e.g. if a host's submission silently failed partway through (`scan.host_submit_failed`) the webserver's count reflects that automatically. The scanner's own logs (`scan.completed` in both `cmd/scanner/main.go` and `internal/api/server.go`) independently report the same shape of counts from its own in-memory tally plus `duration_ms` since scan start - useful for comparing "what the scanner thinks it found" against "what the webserver actually has," e.g. to catch a submission failure that only shows up as a discrepancy between the two.

### Versioning

Webserver and scanner are versioned independently (matching "two independently deployed components" above — different scanner instances can genuinely be on different versions of the same webserver). The webserver's version is a manually-bumped semver string: `server/package.json`'s `version` field, read once at startup (`server/src/version.ts`, via `fs.readFileSync` rather than a static `import "../package.json"` — that file lives outside tsconfig's `rootDir`) and returned from `/auth/login` and `/auth/me` (the frontend shows it as a small fixed corner badge, `App.tsx`, visible on every page once logged in). **Every webserver version bump gets a matching `webserver-vX.Y.Z` tag, in the same commit that raises `server/package.json`** (mirroring the scanner's `scanner-vX.Y.Z` naming). The tag is purely a historical marker and nothing reads it — but the practice had already lapsed once, with tags stopping at 0.6.0 while the webserver ran at 0.44.0, so it is written down here rather than left to memory. The 46 missing tags were backfilled onto the commit that first carried each version; `0.23.0` and `0.35.0` have none because those numbers never existed in `server/package.json` at all, which is a gap in the version sequence rather than in the tags. Unlike the scanner, **the webserver has no tag-triggered release workflow at all**: `.github/workflows/webserver-docker.yml` builds and pushes the Docker image on every push to `master` touching `server/**`, regardless of whether that push happens to coincide with a tag. That same workflow reads `server/package.json`'s version directly (a `jq -r .version` step) and publishes it as a third Docker Hub tag alongside `:latest` and the commit SHA — so `benedelux/porttorch-server:0.3.0` stays in sync automatically on every relevant push, with no separate step to remember when bumping the version.

**The same three tags also go to GitHub's registry** (`ghcr.io/benedelux/porttorch-server`, pushed with the workflow's own `GITHUB_TOKEN`), as a second source for the same image. `scripts/update-webserver.sh` is the update path the README and Fleet Health now point to. It pulls with retries and a growing pause, falls back to the ghcr.io copy when Docker Hub keeps failing, and only runs `docker compose up -d` once a pull has actually succeeded. A plain `pull && up -d` whose pull failed quietly restarts the old image while looking like an update. The script then waits until `/healthz` reports the *new* version, not just any healthy answer, so a still-running old process is not mistaken for success. It exists because Docker Hub timed out mid-pull on two deploys in a row. The compose image is read from `docker compose config` rather than repeated in the script, so the two cannot drift.

**Running scans are linked to their request when they start**, not only when they finish. From scanner 0.28.0, the queue path sends `scanRequestId` with `POST /api/ingest/scan-jobs`. The webserver then sets `scan_requests.scan_job_id` immediately, but only for a request that this scanner has claimed and that is not yet linked, so a scanner cannot attach its job to another scanner's request. This is what lets the running-scan lists show a share of a split scan as "part i/N" (opening the group view) and a pattern scan as its pattern. It also makes the External API's `/hosts/cancel-scan` exact instead of matching the running job on target and ports, which it still falls back to for an older scanner, pinned by `externalApiCancelScan.integration.test.ts` for both cases.

The scanner's is `scanner/internal/version/version.go`'s `Version` — a `var`, not a `const` — wired into cobra's `Command.Version` (gives `porttorch --version` for free) and also printed as the first line of `porttorch doctor`'s report. It's a `var` specifically so `.github/workflows/scanner-release.yml` can override it at build time via `-ldflags "-X .../version.Version=<tag>"` (`-X` only works against a package-level var, a `const` is inlined at compile time and can't be overridden this way) when it builds and publishes release binaries on a `scanner-vX.Y.Z` tag push — see `scanner/CLAUDE.md`'s "Scanner installer" section. Local/dev builds (`go build`, `install.sh`'s from-source path) don't set this flag, so they keep whatever the hand-bumped default in the source says; bump it on meaningful changes for the same reason as before (a rebuilt-from-source binary should be distinguishable from a stale one), independently of whatever the next release tag will be.
