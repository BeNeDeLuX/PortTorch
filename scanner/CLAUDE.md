# scanner/CLAUDE.md

Scanner-specific commands and architecture - the Go CLI in this directory. See the repo root [`CLAUDE.md`](../CLAUDE.md) for the project overview and cross-cutting concerns (excludes enforcement, Scan Profiles, scanner self-update, logging conventions, versioning) that span both this and `server/`.

## Commands

```
go build ./...
go vet ./...
gofmt -l .                     # formatting check; gofmt -w <file> to fix
go test ./...
go test ./internal/pipeline/... -run TestGowitnessStageAgainstRealTarget -v   # single test
```

Several test files are **real integration tests**, not mocked — they shell out to actual binaries or dial real sockets, and are skipped (not failed) if the dependency isn't available:
- `internal/pipeline/gowitness_test.go` needs `gowitness` + a Chrome/Chromium binary.
- `internal/pipeline/rdp_test.go` needs `xfreerdp3`, `Xvfb`, and `import` (ImageMagick), and a reachable RDP server (a local `xrdp` install works for testing).
- `internal/pipeline/tlscert_test.go` needs the webserver reachable on `127.0.0.1:443` (i.e. the docker-compose stack running).

Binary: `go build -o porttorch ./cmd/scanner`, then `porttorch scan|menu|serve|doctor --config <path>` (default config path is `~/.config/porttorch/config.yaml`; `config.example.yaml` documents every field). `masscan` and `nmap` need `cap_net_raw,cap_net_admin` (`sudo setcap cap_net_raw,cap_net_admin+eip $(which masscan)`) or root — the scanner binary itself does not need elevated privileges. `porttorch doctor` (`cmd/scanner/doctor.go`) checks all of this without running a real scan: binaries resolvable, masscan/nmap capabilities (via `getcap`, falling back to a warning if `getcap` itself isn't installed — this is a best-effort check, not a guarantee), gowitness/Chrome and the RDP tools (warnings only, both features are best-effort), and webserver reachability + API key validity (reuses `GetExcludes` rather than adding a health-check-only endpoint). Exits non-zero only on masscan/nmap/webserver failures, matching what the `Config` struct's `withDefaults()` considers hard requirements.

## Architecture

### Scan pipeline (`scanner/internal/pipeline`)

`orchestrator.go`'s `RunScan` runs five stages, each independently testable:
1. **masscan** (`masscan.go`) — fast port discovery, JSON output parsed tolerantly (masscan can emit a truncated array if interrupted). This is the one stage that can't stream: masscan only reports its discoveries once its entire pass across the target range finishes, a hard limitation of the external tool itself, not a design choice here.
2. **nmap** (`nmap.go`) — service/version detection + banner grabbing (NSE `banner` script) on masscan's discovered ports, run with bounded concurrency. Also best-effort SSH host key capture (NSE `ssh-hostkey` — nmap's ssh2 NSE library doesn't support modern KEX algorithms like curve25519-sha256, so it returns nothing against servers with only modern KEX defaults, e.g. stock OpenSSH 9.9+/10; confirmed via manual testing, not a bug here) and per-port CPE/`extrainfo`/`ostype` capture from nmap's own service fingerprinting. Separately, `applyBestOSMatch` reads nmap's `-O` OS/device-type fingerprint (`osmatch`/`osclass` XML) into host-level fields (`OSName`/`OSFamily`/`OSVendor`/`DeviceType`/`OSAccuracy`) — but `-O` is **root-only**: nmap refuses to run at all with `-O` unless the process's effective UID is 0 (not just `cap_net_raw`/`cap_net_admin`, confirmed by testing), so `RunNmap` only adds the flag when `os.Geteuid() == 0`. Everything else in this function works the same whether or not the scanner is running as root. `applyMACAddress` reads the `<address addrtype="mac">` element nmap includes whenever it resolves the host's MAC via ARP — no root requirement, unlike `-O`, but only ever present for a target on the scanner's own local L2 segment (a routed target's XML has no `mac`-typed address at all, only the `ipv4` one), so most internal network scans simply won't have one. `RunNmap` always passes `--privileged`: nmap's own internal "do I have raw-socket access" self-check (used to pick between a real SYN scan and a plain TCP connect scan when not running as root) can be wrong even when `cap_net_raw`/`cap_net_admin` is genuinely set and working — confirmed via manual testing in a capability-based non-root environment where nmap silently fell back to a connect scan, finding ports/services correctly but never resolving/reporting the MAC (a connect scan never builds a raw Ethernet frame, so there's nothing for `applyMACAddress` to read), and adding `--privileged` fixed it immediately. Always passing it is safe: masscan already requires the same raw-socket capability just to run at all, so by the time `RunNmap` runs, that capability is already known to be present. Also runs two anonymous-access enumeration scripts, `ftp-anon` and `smb-enum-shares` — read-only, no-credentials-needed checks (nmap's own "safe" script category, same as `banner`), unconditionally part of every scan rather than a separate opt-in flag, since nmap's own script portrule/hostrule matching already means neither ever fires against a target it doesn't apply to. `ftp-anon` is a per-port script (attaches directly to whatever port nmap classifies as FTP) — when it succeeds, its output is nmap's own human-readable report of the anonymous login plus a directory listing, captured verbatim into `PortResult.FTPAnonListing`. `smb-enum-shares` is a **host-level** script (`<hostscript>`, not nested in any one `<port>` element — one SMB session already covers every share, so nmap doesn't repeat it per port) — `hostResultFromNmapHost` (split out from `RunNmap`'s inline parsing specifically so this is unit-testable against a hand-built `nmapHost`, no real nmap binary needed) reads it once per host and copies the same output onto every port `isSMBPort()` classifies (typically just 445, sometimes both 139 and 445) via `PortResult.SMBShares`. Both fields stay empty whenever the target requires real credentials — same "absence means access was denied, not an error" reasoning as `ssh-hostkey`'s own best-effort behavior above — this only ever surfaces what's already reachable with zero credentials, it never attempts to guess or brute-force one. Ingested into `host_port_observations.ftp_anon_listing`/`smb_shares` (same free-text-blob treatment as `banner`), included in the dashboard's free-text search (`applyHostFilters`'s `q` `EXISTS` subquery), and rendered per-port on the host detail page's "Service Banners & Enumeration" section (renamed from "Service Banners" to reflect the broader scope). `smb-os-discovery` (OS version, computer name, domain, workgroup) and `nbstat` (NetBIOS name/domain) are two more host-level scripts riding the same anonymous SMB session as `smb-enum-shares` — unlike `smb-enum-shares`, though, neither gets its own dedicated `PortResult` field: `hostResultFromNmapHost`'s host-script loop captures any `HostScripts` entry that isn't `smb-enum-shares` itself into `PortResult.ExtraScripts` (see below) on every port `isSMBPort()` classifies, so a future host-level SMB script needs the same zero-new-code treatment the per-port scripts below already get.
**A second, steadily-growing batch of read-only "safe"-category NSE scripts checks for a wide range of specific, commonly-misconfigured no-auth-needed services and protocol-security-posture signals** — enumeration/listing scripts (`nfs-showmount`, `rsync-list-modules`, `ldap-rootdse`, `rpcinfo`, `msrpc-enum`), open-database checks (`mongodb-info`/`mongodb-databases`, `redis-info`, `mysql-info`, `memcached-info`, `oracle-tns-version`, `docker-version`, `couchdb-databases`, `cassandra-info`), HTTP checks (`http-methods`, `http-auth`, `http-git`), SMB protocol/security-mode checks (`smb-protocols`, `smb-security-mode`, `smb2-security-mode` - see `smb-os-discovery`/`nbstat` above for the host-level SMB scripts), RDP/SSH pre-auth info (`rdp-ntlm-info`, `rdp-enum-encryption`, `ssh2-enum-algos`, `sshv1`), and `smtp-open-relay` — this list keeps growing and `nmap.go`'s own doc comment on `RunNmap` is the authoritative, up-to-date enumeration of exactly what's in it and why each one was added; this paragraph deliberately doesn't try to duplicate that list verbatim going forward; duplicating it here just meant this summary quietly went stale the moment the list grew (confirmed - it happened once already). All of these are per-port scripts (unlike `smb-enum-shares`/`smb-os-discovery`/`nbstat`, which are host-level - see above), all unconditionally part of every scan for the same reason as `ftp-anon`/`smb-enum-shares`: nmap's own portrule matching means each only ever fires against a port it actually applies to. **`smtp-open-relay` is the one script in this batch that isn't purely passive** — it actively sends a handful of test messages through the target SMTP server to determine whether it relays mail for third parties (the classic open-relay misconfiguration check). Still non-destructive and still in nmap's "safe" category, but a successful check has a real side effect (the target server actually attempts to relay the test messages) rather than just reading something back, worth calling out explicitly since every other script on this list is a pure read. Unlike `FTPAnonListing`/`SMBShares`, none of these gets its own dedicated `PortResult` field or database column — `PortResult.ExtraScripts` (`[]NSEScript{ID, Output}`) is populated generically in `hostResultFromNmapHost`'s per-port script loop by a `default:` case that captures *any* script id it doesn't already have a named case for, skipping empty output (ran but found nothing, e.g. `redis-info` against a server requiring `AUTH`). This is deliberate: adding another script to this batch later is just adding its id to `RunNmap`'s `--script` list, with zero new Go struct fields, zero new migrations, and zero new zod schema fields needed - it flows straight through to `host_port_observations.nse_extra` (a `jsonb` array of `{id, output}` objects, ingested as-is from the scanner's own `extraScripts` payload field). The dashboard's free-text search unnests it the same way the CVE-id match already unnests `cve_cache.cves` (`jsonb_array_elements` + `ilike` on the `output` field, no Kysely builder helper for jsonb). The host detail page renders each entry in the same per-port "Service Banners & Enumeration" card as banner/ftp-anon/smb-enum-shares, labeled via `NSE_SCRIPT_LABELS` (falls back to the raw script id for anything not in that map, so a script added on the scanner side without a matching frontend change still displays, just less prettily).

**A real production incident, not a hypothetical**: this batch briefly also listed `http-elasticsearch`, on the (wrong) assumption that nmap ships an info-gathering script for Elasticsearch the way it does for MongoDB/Redis/CouchDB - it doesn't; the only Elasticsearch-related script nmap actually ships is `http-vuln-cve2015-1427`, a narrow check for one specific 2015 RCE, not a safe unauthenticated-info read, so it isn't a fit for this group either. Unlike an unrecognized `nmap-services` port hint or a script that simply never fires against an inapplicable port, a **nonexistent** `--script` name is fatal to the entire invocation: nmap's NSE engine validates every listed script name against its script database *before* scanning anything, and refuses to run at all if one doesn't resolve ("did not match a category, filename, or directory... QUITTING!") - so this one bad name broke nmap enrichment for literally every host on every scan run against a v0.4.0 scanner, not just Elasticsearch detection. Confirmed against a real user report showing every single host in a scan failing with the identical NSE initialization error. Fixed by removing the nonexistent entry; there's no generic safeguard against this class of typo added on top (e.g. validating script names before building the command) since the actual fix is simply "don't list a script that doesn't exist" - correctness in the `--script` list itself is the only mitigation, same as any other hardcoded external-tool argument in this codebase.

**A second, unrelated bug surfaced in the same report**: nmap's own "Duplicate port number(s) specified" warning (non-fatal, unlike the above) on scans covering more than one port. Root cause was in `RunMasscan` (`masscan.go`), not `RunNmap` - masscan's own `--retries` (added earlier for lossy-network reliability, see "Scan pipeline" above) resends each probe, and when more than one attempt gets a reply (common with duplicate ACKs/retransmits on a real network, not just packet loss), masscan writes a separate top-level JSON record for the same open port each time; `RunMasscan` appended every one of them into that host's port list unchanged, so the same port number could appear more than once in the `-p` list `RunNmap` builds from it. Fixed with a per-host `map[string]bool` keyed on `"<proto>:<port>"` in `RunMasscan` itself, deduplicating before the result is ever returned - nmap's own XML-based discovery (`discoveredFromNmapRun`, the IPv6 path) doesn't need the equivalent, since nmap's own port list per host is already naturally deduplicated.

**`snmp-info` (SNMP asset info via the "public" community string - the universal SNMP default, not a wordlist attempt) needed a genuinely different mechanism, not just another entry on the `--script` list, because SNMP is UDP-only and this scanner's pipeline is otherwise entirely TCP** — masscan discovery, `RunNmap`'s `-sV` enrichment, and every other NSE script above all only ever look at TCP ports from the requested port spec; there's no `-sU` anywhere and no protocol-aware port-spec syntax (confirmed by grepping the whole scanner module for any UDP handling at all before building this - there was none). Rather than adding general UDP scanning support (a materially bigger change: protocol-aware port spec parsing threaded through masscan/nmap/the webserver's scan-request validation, masscan UDP probing, `-sU` wired into the main enrichment pass), `snmp.go`'s `RunSNMPProbe` is a small, deliberately narrow exception: one extra, separate `nmap -sU -p 161 --script=snmp-info` invocation per host, independent of whatever TCP ports were actually discovered. `--host-timeout 10s` bounds it explicitly, since UDP's "no response" is inherently ambiguous (closed vs filtered vs just slow) and this now runs unconditionally against *every* scanned host (most of which don't run SNMP at all) rather than only against hosts that already showed a relevant TCP port the way every other enumeration script here does.

Because this bypasses `subtractPorts`/masscan's `--excludefile`/`filterIPPortExcludes` entirely (none of them would ever see a port that was never part of the requested TCP port spec in the first place), `RunScan`'s nmap loop calls a new `isPortExcludedForHost(ip, 161, excludes)` (`excludes.go`) before enqueueing the SNMP job - checking both a global port exclude covering 161 and an `ip_port`-scoped exclude for `<ip>:161`, so an admin's exclude list is still honored even though the normal three TCP-only exclude mechanisms never touch this path. A found result becomes a synthetic `PortResult{Port: 161, Protocol: "udp", State: "open", ServiceName: "snmp", ExtraScripts: [...]}` appended to the host's `Ports` like any other discovered port - no `(nil, nil)` "found nothing" case ever fabricates a port row, same "absence means access was denied, not a failure" reasoning as `ftp-anon`/`smb-enum-shares`. This is also the first UDP entry `host_port_observations.protocol` has ever actually received, but needed zero schema change to support: the column is plain `text` with no `CHECK` constraint, and `current_host_ports`' `DISTINCT ON (host_id, port, protocol)` already keys on protocol, so a `161/udp` row and a hypothetical `161/tcp` row on the same host would already coexist correctly rather than colliding.

**IPMI (`ipmi-version` against UDP/623) is the identical exception, added later for the same reason and built by copying the SNMP mechanism exactly**: `ipmi.go`'s `RunIPMIProbe`/`ipmiPortFromNmapRun` mirror `snmp.go`'s `RunSNMPProbe`/`snmpPortFromNmapRun` line for line (separate `nmap -sU -p 623 --script=ipmi-version --host-timeout 10s` invocation, synthetic `PortResult{Port: 623, Protocol: "udp", ServiceName: "ipmi", ...}`, `(nil, nil)` on no response), `orchestrator.go` gets a sixth worker pool (`startIPMIWorkers`, `ipmiJobs` channel) alongside the SNMP one, and the exclude check is just a second `isPortExcludedForHost(ip, 623, excludes)` call - no new exclude mechanism needed, since that function already takes the port as a parameter. IPMI/BMC out-of-band management interfaces are a genuinely high-value target for a SOC recon tool specifically because they're easy to overlook: they sit on their own network path (often a dedicated management NIC), commonly ship with default or no authentication, and a device with one exposed is a materially different risk than the same device's regular OS-level services - exactly the kind of asset this scanner's other enumeration scripts already exist to surface without needing credentials.

**`dns-recursion` (open recursive resolver check, against UDP/53) is a third copy of the same exception, discovered while researching further NSE additions**: nmap's own documented usage for this script is `-sU -p 53 --script=dns-recursion`, not TCP - even though nmap's portrule technically also matches TCP, the check is only meaningful over UDP in the first place, since the abuse it detects (using an open resolver as a DNS amplification reflector for a DDoS against a third party) specifically relies on UDP's small-request/large-response asymmetry; a TCP-based recursion check wouldn't demonstrate that risk at all. `dnsrecursion.go`'s `RunDNSRecursionProbe`/`dnsRecursionPortFromNmapRun` are the same shape again (`nmap -sU -p 53 --script=dns-recursion --host-timeout 10s`, synthetic `PortResult{Port: 53, Protocol: "udp", ServiceName: "dns", ...}`), `orchestrator.go` gets a seventh worker pool (`startDNSRecursionWorkers`, `dnsRecursionJobs` channel), and the exclude check is a third `isPortExcludedForHost(ip, 53, excludes)` call.

**`upnp-info` (UDP/1900, SSDP/UPnP self-description) is a fourth copy of the same narrow exception** (`upnp.go`'s `RunUPnPProbe`/`upnpPortFromNmapRun`, `nmap -sU -p 1900 --script=upnp-info --host-timeout 10s`, synthetic `PortResult{Port: 1900, Protocol: "udp", ServiceName: "upnp", ...}`, an eighth worker pool `startUPnPWorkers`, and a fourth `isPortExcludedForHost(ip, 1900, excludes)` exclude check) - a UPnP root device reachable from beyond its own local segment (UPnP was never designed to be exposed past a single LAN) is a real, common misconfiguration worth surfacing the same way an open SNMP/IPMI service already is. Confirmed against a real local nmap install's `script.db` that `upnp-info` is categorized `safe`+`discovery`, not assumed - this codebase has its own documented precedent (the `http-elasticsearch` incident above) for a wrong category assumption breaking every host in a scan. `ntp-monlist` (UDP/123, the classic NTP-amplification-vector check) was deliberately **not** given the same treatment despite being a similarly well-known UDP reflection/misconfiguration check - confirmed via `script.db` that it's categorized `intrusive`, not `safe`, unlike every other script in this group; running an intrusive script unconditionally against every scanned host would be a real change to this scanner's safe-by-default posture, not a mechanical addition like the others, so it's left out rather than silently included.

**The SNMP probe itself grew a second round of scripts** (`snmp-sysdescr`, `snmp-interfaces`, `snmp-netstat`, alongside the original `snmp-info`) - since all four ride the same single `-sU -p 161` invocation, this needed no new worker pool, just more names in `RunSNMPProbe`'s `--script=` list. `snmpPortFromNmapRun` was generalized to match: instead of special-casing `snmp-info` specifically, it now captures *any* script on that port with non-empty output into `ExtraScripts` (the same "unrecognized script id -> generic capture" treatment `nmap.go`'s per-port default case already gives the TCP scripts) - a host might answer one of the four but not another (e.g. a community string permitting a `sysDescr` read but not the fuller interface/netstat tables), and any one succeeding is equally valid confirmation SNMP is actually present.
3. **gowitness** (`gowitness.go`) — screenshots ports classified as HTTP(S) by `isHTTPPort()` (service-name heuristic with a port-number fallback list, `httpPortHints`) — the same classification also gates the TLS certificate probe (`isTLSPort()`, `tlscert.go`) below, so a port missing from both the service-name match and this fallback list gets neither a screenshot nor certificate info at all. `httpPortHints` includes `8006` specifically because nmap's own `nmap-services` database labels that port `wpl-analytics` (a real entry in nmap's database, but not an actual identification of anything actually running - no product/version/banner alongside it) even though it's the Proxmox VE web UI's default (HTTPS) port - confirmed against a real host that turned out to be exactly that, with neither a screenshot nor a certificate captured until this was added. Also captures TLS certificate info, detected technologies, and the full HTTP response headers from gowitness's JSONL output (`tls`/`technologies`/`headers` fields) — these are persisted, not just the screenshot. `Config.ScreenshotWidth`/`ScreenshotHeight` (default 1920×1080, `--chrome-window-x`/`--chrome-window-y`) set gowitness's Chrome window size and therefore the captured PNG's resolution — deliberately higher than gowitness's own 1280×720 default, for a sharper image in the host detail lightbox. Confirmed against a real capture: the resulting PNG's actual width matches the configured value exactly; the height can come out smaller than configured, since gowitness captures the full rendered page content height, not a fixed viewport crop — expected for short pages, not a bug.

**A target requiring HTTP authentication (e.g. Basic Auth) silently produces no screenshot at all, with no error surfaced by gowitness itself** — confirmed via manual testing against a real 401+`WWW-Authenticate: Basic` server: gowitness exits `0` (not a crash, not a non-zero exit) and writes nothing to its JSONL output file, no result line and no `failed`/`failed_reason` entry either. The likely mechanism: Chrome shows its own native, un-dismissable authentication prompt for the challenge, the page never finishes loading in a way gowitness can capture, and gowitness gives up without reporting why. `readGowitnessJSONL` (in `gowitness.go`) detects the resulting empty-file case and returns a message explicitly naming HTTP auth as the likely cause, rather than a bare "no result written by gowitness" that gave no hint where to look — this surfaces through the existing best-effort `onProgress`/`scan.progress` logging same as any other capture failure, no separate plumbing needed. A host with an open HTTP(S) port but no screenshot and no obvious network-level explanation is worth checking for this before assuming something else is wrong.
4. **RDP screenshots** (`rdp.go`) — for ports classified by `isRDPPort()`, spins up `Xvfb` (race-free display allocation via `-displayfd`), connects with `xfreerdp3 /sec:rdp` (deliberately not NLA, since we have no valid credentials — this only captures a login screen on servers that allow legacy RDP security; NLA-only servers can't be screenshotted without credentials, which is a protocol limitation, not a bug), and captures with ImageMagick `import`.
5. **TLS certificate probe** (`tlscert.go`) — a real TLS handshake (`crypto/tls` only, no external tool) against every port `isTLSPort()` classifies as TLS-carrying, not just HTTP(S) (also IMAPS/SMTPS/LDAPS/etc). Captures the certificate (CN, issuer, SANs, validity, SHA-256 fingerprint, self-signed via `bytes.Equal(cert.RawIssuer, cert.RawSubject)`) plus the negotiated handshake (TLS version, cipher suite) and the certificate's key algorithm/size — independent of whatever gowitness already captured for HTTP(S) screenshots in stage 3.

**Manual "probe hostname" override for SNI-based virtual hosting** (`hosts.probe_hostname`, set on the Host Detail page) — a real, reported bug: `RunTLSCertProbe` used to hardcode `ServerName: ip` in its `tls.Config`, and Go's `crypto/tls` treats an IP-literal `ServerName` as "send no SNI extension at all" (per RFC 6066, an IP address isn't a valid server name) — so this probe has never sent a working SNI value, against any host. Confirmed via direct `curl` testing against a real target: a server using nginx-style SNI-based virtual hosting (which rejects a handshake whose SNI doesn't match any configured `server_name`, sending a fatal `internal_error` alert) fails identically whether no SNI is sent or the wrong hostname is sent — only the *correct* hostname lets the handshake complete, and a scan only ever discovers the bare IP (nmap's own reverse-DNS/PTR-derived `hosts.hostname` is a separate, frequently-*wrong*-for-this-purpose value — confirmed in the reported case, where the PTR name also failed identically, since it wasn't the real vhost name either). Since there's no way to derive the *correct* vhost hostname automatically, `hosts.probe_hostname` is a manual, per-host override (operator-level, `PATCH /api/hosts/:id/probe-hostname`, `null` clears it — never written by the scan pipeline itself, unlike `hostname`) that the scanner fetches once per scan (`client.Client.GetProbeHostnames`, `GET /api/ingest/probe-hostnames`, scoped strictly to the requesting scanner's own hosts by `(ip, scanner_agent_id)` — no global variant, unlike excludes) and uses instead of the bare IP for: the TLS probe's SNI (`RunTLSCertProbe`'s new `sni` parameter — the dial target itself stays pinned to the exact scanned IP regardless, only the SNI value changes, so this never risks probing the wrong device) and the gowitness screenshot URL's hostname. gowitness/Chrome has no IP-pinning + hostname-override mechanism exposed (checked via `gowitness scan single --help` — no equivalent of Chrome's `--host-resolver-rules`), so unlike the TLS probe, the gowitness capture relies on the override hostname's own DNS still resolving to this same IP — true for "my own domain," which is the case this exists for. Verified with a real, non-mocked test (`tlscert_sni_test.go`'s `TestRunTLSCertProbeUsesSNI`): a local `tls.Listen` server presents a different self-signed certificate depending on the ClientHello's `ServerName` (a miniature version of nginx's own SNI routing), and `RunTLSCertProbe` called with different `sni` values against the same `ip:port` gets back the correspondingly different certificate — proving the SNI value actually reaches the wire, not just that it's plumbed through unused.

**Stages 2-5 (plus the SNMP probe below) run concurrently with each other, not as sequential batches, so results can stream to the webserver per host instead of only after the entire scan finishes.** `startGowitnessWorkers`/`startRDPWorkers`/`startTLSWorkers`/`startSNMPWorkers` (each its own bounded worker pool, same concurrency settings as before) all start running *before* nmap's own worker pool begins, and keep running for the whole duration of the nmap stage — as each nmap worker finishes a host, it immediately enqueues that host's HTTP(S)/RDP/TLS-carrying ports (and, unconditionally, a single SNMP probe job - see below) onto the pools' job channels rather than waiting for every other host's nmap call to finish first. A `hostTracker` (in `orchestrator.go`) tracks, per host, how many of these sub-tasks are still outstanding and fires `RunScan`'s new `onHostComplete` callback exactly once that count reaches zero — independently for every host, so a host with no follow-up work (e.g. only an SSH port) can be reported and submitted while a different host's screenshot is still capturing. All three entry points (`scan`/`menu`/`serve`) pass a callback that calls `client.SubmitHostResult` (submits one host's ports/screenshots/RDP/TLS-certs together, sharing the actual submission logic across all three) immediately, rather than the old design of collecting every host into one slice and issuing a single batch `SubmitHosts` call after the whole target range finished scanning. This has a real practical benefit beyond just visibility: if a long scan is killed, cancelled (see `server/CLAUDE.md`'s "Stopping a running scan" section), or crashes partway through, whatever hosts had already streamed in are not lost, unlike the old batch-at-the-end design where nothing was submitted until the very end. A host whose submission fails is logged and skipped (`scan.host_submit_failed`) — the rest of the scan keeps running, matching the existing tolerance for individual screenshot/RDP/TLS submission failures. `ScanResult.Hosts` is still fully populated at the end too (each `onHostComplete` invocation also appends to it under a mutex) for whatever still wants the complete list after the fact — the menu TUI's final summary counts, mainly.

**Screenshot OCR** (`ocr.go`) runs after both stage 3 and stage 4, on every successfully captured HTTP(S)/RDP screenshot: `RunOCR` shells out to `tesseract <imagepath> stdout` and stores the recognized text on the `Screenshot`/`RDPScreenshot` struct (`OCRText`), which the client submits as an extra multipart field (`ocrText`) alongside the image. This makes page/login content searchable (the dashboard's search matches against the resulting `ocr_text` column on `screenshots`/`rdp_screenshots`, see below) even when it never appears in a banner or HTTP header, e.g. a wordmark baked into a background image or an RDP login screen. Best-effort exactly like gowitness/RDP themselves: `Config.TesseractPath` defaults to `"tesseract"`, and a missing binary or failed recognition just means no OCR text — it never fails the screenshot capture itself, and there is no retry (unlike the timeout retry in gowitness/RDP stages, since OCR failures aren't the resource-contention pattern that retry exists for).

All three CLI entry points (`scan` one-shot, `menu` TUI, `serve` REST API) call the same `pipeline.RunScan` — there's no duplicated pipeline logic per entry point. Screenshot files live in per-capture temp directories; callers are responsible for `pipeline.CleanupScreenshots` after upload.

**ICMP being blocked/disabled on a target doesn't affect any of this.** masscan has no host-discovery/ping phase at all — it sends its probe (SYN, by default) directly to the specified ports on every target IP and just listens for a response, regardless of ICMP reachability. nmap is explicitly run with `-Pn` (`nmap.go`'s `RunNmap`), which skips nmap's own host-discovery phase (the one that would otherwise use ICMP/ARP/TCP probes to decide whether to bother scanning a host) and treats every target as online unconditionally. gowitness, the RDP screenshot stage, and the TLS certificate probe all connect straight to a specific IP:port over TCP/TLS, with no ICMP step anywhere in between. So a host with ICMP fully disabled is scanned identically to one that responds to ping — the only requirement anywhere in the pipeline is that the actual TCP ports being probed are reachable.

Gowitness and RDP screenshots use their own concurrency settings (`gowitnessConcurrency`/`rdpConcurrency`, default 2), deliberately separate from and much lower than the general `concurrency` (default 5, used by nmap, the TLS probe, and the SNMP/IPMI/DNS-recursion probes) — each gowitness/RDP screenshot spawns a full Chrome instance or an Xvfb+xfreerdp+import chain, far heavier than an nmap process, and reusing the higher general concurrency for them starves every concurrent instance of CPU/RAM. This was a real bug, not a hypothetical one: a scan with the (then-shared) concurrency at 5 timed out on 5 of 7 gowitness attempts, all started within milliseconds of each other, all failing on `context deadline exceeded` around the same timestamp — individually they'd have finished fine, but launching that many headless Chrome instances at once starved all of them. If a port has an open HTTP(S)/RDP port but no screenshot and no obvious error, check for this pattern (a burst of near-simultaneous "capturing ..." log lines followed by a burst of timeouts) before assuming the target itself is unreachable.

On top of the concurrency fix, both stages retry once (after `retryDelay`, 2s) when a capture fails with what `isTimeoutLikeErr` considers a timeout-shaped error — deliberately a plain substring check (`"timeout"`/`"deadline"`) rather than `errors.Is`, since neither gowitness nor xfreerdp report their internal timeouts as a typed Go error, just plain text in the wrapped error/JSONL `FailedReason`. This is gated on looking-like-a-timeout specifically so it doesn't retry RDP's NLA rejection or a plain connection-refused — those fail the same way every time, and retrying them would just double the wasted time with zero chance of success. masscan itself also got a robustness pass: `masscanRetries` (default 2, masscan's own `--retries`) resends each probe, since masscan is a stateless SYN scanner where a single lost packet in either direction means a genuinely open port simply isn't reported that run — this is a distinct failure mode from the gowitness/RDP one (packet loss during discovery, not resource contention during screenshotting) and was the actual explanation the one time a host's previously-open port didn't reappear in a later scan at all.

### Submission durability, worker-pool resilience, and failure classification

**A submission failure used to mean losing that host's result outright.** `internal/submitqueue` (new package) durably persists a host's scan result to disk when `client.SubmitHostResult` fails, so it can be retried later instead of being lost - without this, a submission failure was genuinely unrecoverable, since every entry point calls `pipeline.CleanupScreenshots` right after the attempt regardless of outcome, and streaming per-host submission (see above) means there's no final "resubmit everything" step at the end of a scan to fall back on. `Enqueue(queueDir, jobID, host)` copies the host result plus any screenshot/RDP image files into a `entry-*` temp directory (`os.MkdirTemp`) as `item.json` - deliberately a *copy*, not a move/mutation of the caller's `host` value, since every caller still runs `pipeline.CleanupScreenshots` against the original, unmodified value immediately afterward. `Drain(ctx, queueDir, c)` resubmits every queued entry and returns a `DrainResult{Succeeded, GaveUp, Pending, Dropped, Rejected}` - `GaveUp` is a transient failure that finally exhausted `maxAttempts` (10) or `maxAge` (7 days, mirroring the webserver's own `MAX_UPDATE_ATTEMPTS` pattern); `Dropped` is a corrupted queue entry (unreadable/unparseable `item.json`) removed so it doesn't jam every future `Drain` call. All three entry points opportunistically call `Drain` once at startup (so a backlog from a prior outage doesn't wait indefinitely for a lucky retry window); `serve` mode additionally runs `submitqueue.StartRetryWatcher` as a background ticker (`RetryIntervalSeconds`, default 60) alongside `StartPolling`/`StartCancelWatcher`/the update watcher, so a backlog accumulated mid-scan doesn't have to wait for the process to restart either.

**Not every submission failure deserves a retry.** `client.HTTPStatusError` (wrapped via `%w` in `doJSON`/`uploadImage`) carries the actual response status code, and `submitqueue.IsPermanentFailure(err)` uses `errors.As` to classify a 4xx as permanent (the webserver definitively rejected this exact payload - retrying it unchanged will never succeed) versus a 5xx or network error as transient (worth retrying). This is checked at two points: at the original failure site in all three entry points (a 4xx is logged as rejected and never even reaches `Enqueue`, avoiding a disk write for something that can't succeed) and again inside `drainEntry` (an already-queued entry that turns out permanently invalid on a later retry attempt is removed immediately, rather than burning through all 10 attempts pointlessly first).

**A panic in one host's worker used to crash the entire scanner process, losing every other in-flight host's results too.** `recoverJob(onPanic func(recovered any), fn func())` (`orchestrator.go`) wraps each of the seven sub-task worker pools (gowitness/RDP/TLS/SNMP/IPMI/DNS-recursion/UPnP) - a panic inside `fn` is recovered and reported via `onPanic` (logs it and calls `tracker.complete(...)` so the host's `hostTracker` count still reaches zero and `onHostComplete` still eventually fires) instead of taking down the process. The main nmap worker loop gets a log-only variant of the same wrapper, deliberately *not* calling `tracker.complete` on panic - `hostTracker.register()` has to happen before any sub-task can safely call `complete()`, and a panic in the nmap loop could occur before that registration ever happens, so blindly calling `complete()` there risks a mismatched count. The accepted tradeoff: a panicking host's own result may be lost or leak a stuck `remaining` count, but the process itself survives to keep serving every other host and every future scan.

**Retry-queue backlog visibility on the dashboard.** The scanner's own `internal/submitqueue` backlog size (host submissions still waiting to be retried) was previously only visible via that scanner's local Prometheus `/metrics` endpoint (below) - invisible from the dashboard entirely. `client.Client` now tracks its current backlog size (`SetSubmitQueuePending`, updated after every `Enqueue`/`Drain` call across all three entry points) and reports it on every ingest request via a new `X-Scanner-Submit-Queue-Pending` header, the same piggyback-on-every-request mechanism `X-Scanner-Version` already uses (`setAuthHeaders`). `apiKeyAuth.ts` parses and validates it (`parseSubmitQueuePendingHeader` - a missing header, a non-numeric value, or a negative number all map to `null`/"unknown", never to `0`, same "absence isn't zero" reasoning as the `version` column right next to it) into `scanner_agents.submit_queue_pending`. Surfaced as a small badge next to a scanner's version on the Scanner Agents page, and as its own "Submission Retry Backlog" card on Fleet Health (see `server/CLAUDE.md`) - deliberately distinct from that page's "Scan Queue" card, which tracks unclaimed `scan_requests` rows waiting to be picked up, not results waiting to be *re*submitted after already having been picked up and scanned.

### Scanner operational tooling: `--dry-run`, `--targets-file`, a local scan audit log, and `/metrics`

**`--dry-run` previews what a scan would actually target without running masscan/nmap or creating a scan job.** `pipeline.PreviewScan(targetSpec, portSpec, excludes)` (`preview.go`) deliberately reuses `RunScan`'s own unexported helpers (`subtractPorts`, `isTargetExcluded`, `parseIPv6TargetList`) rather than re-implementing exclude logic a second time, so a preview can never drift from what a real scan would actually do. Returns a `PreviewResult` with the effective port spec after port excludes are subtracted, and - for IPv6 targets (always a small, fully enumerable address list) - a per-address excluded/not-excluded breakdown; for a single bare IPv4 address, the one IPv4 case a preview can resolve definitively the same way; for an IPv4 CIDR/range, just the list of IP/CIDR/range excludes that would be passed to masscan's `--excludefile`, since enumerating a large range itself isn't something a preview should attempt. `ip:portSpec` excludes are shown as an informational list rather than resolved against anything, since which hosts actually get discovered isn't known yet at preview time.

**A permanent, append-only local record of every host a scanner has ever found** - `internal/auditlog` (new package), deliberately distinct from `internal/submitqueue` above: submitqueue exists to recover from a *transient* outage (entries are deleted once resubmission succeeds, or after exhausting retries); this package logs every host unconditionally, submitted or not, and never removes an entry - the same preserve-history-over-hard-delete philosophy the webserver's own `audit_log` table follows, for the same reason (a forensic trail that outlives whatever else may have gone wrong, including a webserver outage longer than the submit queue's own bounds, or a `scanner_agent` later being deleted and its `scan_jobs` history going with it). `auditlog.EntryFromHost(jobID, host, submitted)` builds a compact JSONL line (`time`, `scan_job_id`, `ip`, `hostname`, `ports` as `"port/protocol"` strings for open ports only, `submitted`) - a summary rather than the full result (banners/CPEs/screenshots stay in the real submission only), so the file grows slowly regardless of scan volume; `submitted:false` lines are exactly what isn't yet confirmed delivered, greppable directly. `Config.ScanAuditLogPath` defaults to a `scan-audit.jsonl` alongside the config file; `Write`/`Close` on a nil `*AuditLog` are safe no-ops, so a failure to open it at startup is logged but never fatal to scanning.

**`--targets-file` scans many discontiguous ranges in one run without hand-building a comma-separated `--target` string.** `parseTargetsFile(path)` (`main.go`) reads one target-spec fragment per line (blank lines and `#`-comments skipped) and joins them with `,` into exactly the string `--target` already accepts - masscan's own target-spec grammar and `parseIPv6TargetList` both already natively accept a comma-separated list, so this needed zero changes anywhere in the `pipeline` package. Mutually exclusive with `--target`.

**A Prometheus `/metrics` endpoint** (`internal/api/metrics.go`'s `handleMetrics`, `serve` mode only) exposes a scanner's own health independent of the webserver's necessarily-inferred, last-seen-based heuristics: uptime, whether a scan is currently in progress, total scans by terminal status, poll failure count and last success/failure timestamps, the current submit-queue backlog size, and whether `masscan`/`nmap` are resolvable on `PATH`. Deliberately hand-written plain-text exposition format rather than pulling in `prometheus/client_golang` - a handful of gauges/counters already tracked elsewhere in this package doesn't need a registry/encoding dependency.

### The nuclei template refresh is a watcher, for the same reason self-update is

`internal/updater`'s `StartTemplateUpdateWatcher` is `StartUpdateWatcher`'s twin - started alongside it from `serve` mode only, polling `GET /api/ingest/template-update-requested` at the same interval, and answering an outstanding request by shelling out to `<cfg.NucleiPath> -update-templates` and reporting the outcome via `PATCH /api/ingest/template-update-outcome`. It defers while `IsScanning()` for a different reason than the binary update does: `-update-templates` rewrites the tree in place, and a scan already running nuclei is reading templates out of it.

**That it runs inside the scanner process is the whole value, not incidental.** The template tree resolves against the *invoking user's* home (`pipeline.DefaultNucleiTemplatesDir`), so a manual `sudo nuclei -update-templates` on the host updates root's copy while the service, running as `porttorch`, keeps reading its own - a silent no-op that looks identical to a successful update from the dashboard's side, since the reported age simply never moves. Invoking it here can't miss that way. `RefreshNucleiTemplatesUpdatedAt` is called *before* reporting success specifically so the very next ingest request already carries the new age; reporting first would clear the "updating" badge while still showing the stale age, which reads exactly like the refresh did nothing.

Failure reasons carry nuclei's own combined output (tail-trimmed to 500 bytes, cut at a line boundary), not just the bare `exit status 1` - it's rendered directly on the Scanner Agents page, and the exec error alone says nothing actionable. `nuclei: command not found` on a host where nuclei was never successfully installed is the expected first failure this surfaces.

### A DNS hostname target is resolved scanner-side, and becomes that scan's SNI/screenshot hostname

`RunScan` accepts a plain DNS hostname as its `targetSpec`, not just an IPv4 address/CIDR/`start-end` range or the IPv6 forms below - `isHostname` (`orchestrator.go`) decides by elimination, since nothing in this codebase validated target-spec shape before this existed (masscan simply errored out on anything it couldn't parse): false for empty input, anything containing a comma (masscan accepts comma-separated multi-target specs, and a hostname never contains one - this is also what rejects an IPv6 *list*), anything `net.ParseIP` accepts (which is what covers a bare IPv6 address - there's deliberately no separate `:` check) or `net.ParseCIDR` accepts, and anything matching the `start-end` range grammar; true for the remainder. The range check confirms **both** sides of a `-` split parse as IPs before concluding it's a range - a plain "contains a hyphen" test would misclassify a perfectly valid hostname like `web-01.internal`. Checked immediately after port-exclude handling and before the IPv6/masscan dispatch below.

**Resolution deliberately happens here, in the scanner, not webserver-side.** The webserver has no visibility into a scanner's own network (see the root `CLAUDE.md`'s "Why two separate services" - scanner-initiated-only communication, scanners sit behind NAT/firewalls with their own internal/split-horizon DNS), so a name it resolved itself would be wrong or unresolvable for exactly the internal-only targets this exists for. `scan_requests.target_spec` carries whatever string was typed, untouched, and `resolveHostnameIPv4` resolves it via the scanner's own local resolver (`net.DefaultResolver`) at scan time. **IPv4 only, first address only** - an IPv6-only hostname fails clearly rather than being silently mishandled (the IPv6 path below is explicitly single/list-address-only by design), and taking only the first A record is the least-surprising reading of "I typed a hostname, I meant that one host," avoiding an accidental sweep of every edge IP behind a load-balanced/CDN-fronted name. A resolution failure aborts the scan with a clear error, same fail-closed treatment as a `GetExcludes`/`GetProbeHostnames` fetch failure.

The resolution itself is reported via `onProgress("discovery", "resolved <hostname> -> <ip>")`, so it shows up in the scan's live log/Details popup like any other stage event - without it, a scan whose target silently became an IP would give no indication of *which* IP a name actually resolved to on that scanner. The resolved IP replaces `targetSpec` for everything downstream (masscan/nmap never see the original hostname), and `withProbeHostname` merges `{resolvedIP: originalHostname}` into the `probeHostnames` map `RunScan` already receives - copy-not-mutate, since callers keep using their own map afterward. That map is the *exact* mechanism `RunTLSCertProbe`'s SNI and gowitness's screenshot URL already consult for a manually-set `hosts.probe_hostname` (see "Scan pipeline" above), so a hostname target automatically gets correct SNI/screenshot behavior with zero changes anywhere downstream of this point - and no new DB column, ingest endpoint, or `client.go`/`server.go` plumbing was needed for any of it. Living at the pipeline level rather than in one entry point means every caller benefits (the queue-driven `serve` path the dashboard's Ad-hoc Scans page and Schedule Scans use, plus the one-shot `scan` CLI and the `menu` TUI), not just the feature it was built for.

### IPv6 targets bypass masscan entirely and use nmap for both discovery and enrichment

masscan has no IPv6 scanning capability at all (a limitation of the external tool itself), so `RunScan` branches on whether `targetSpec` contains a `:` (never true for an IPv4 address/CIDR/range) before ever calling `RunMasscan`. Unlike IPv4, where masscan can cheaply sweep a whole `/24`, IPv6 address space is far too large to brute-force scan a range/CIDR at all — real IPv6 asset inventories are always specific known addresses (DNS/NDP/DHCPv6 records), not a sweep. So this path deliberately supports only **a single IPv6 address, or a comma-separated list of specific addresses** as the target — `parseIPv6TargetList` (`pipeline/ipv6.go`) rejects a CIDR or `start-end` range outright with a clear error rather than silently mis-scanning or falling through to masscan.

Discovery for this path is `RunNmapDiscovery` (`nmap.go`) — a bare `nmap -6 -Pn --privileged -sS` pass (no `-sV`/scripts/`-O`) across one or more explicit targets in a single invocation (nmap natively accepts multiple target args and returns one `<host>` element per target, so there's no need to shell out per address), keeping only `state="open"` ports and returning the same minimal `map[string][]PortResult` shape `RunMasscan` produces — mirroring masscan's own contract of only ever reporting open ports. This is a genuine drop-in replacement at the exact call site `RunMasscan` occupies for IPv4, so **everything downstream is completely unchanged**: `filterIPPortExcludes`, `hostTracker`, the stage-2 `RunNmap` enrichment worker pool, and the gowitness/RDP/TLS worker pools all already operate on the `discovered` map by string key with zero address-family assumptions. `RunNmap` itself only needed one addition — it detects an IPv6 `ip` internally (`net.ParseIP(ip).To4() == nil`) and adds `-6`, so the existing service/version/banner/OS enrichment stage works identically for both families.

There's no masscan `--excludefile` step in this path, so IP/CIDR excludes are checked directly in Go instead: `isTargetExcluded` (`pipeline/ipv6.go`) tries each entry in `excludes.IPs` as a CIDR (`net.ParseCIDR`+`Contains`) then as an exact address match, dropping any excluded target before `RunNmapDiscovery` ever runs (mirroring masscan's own silent-skip behavior for IPv4). Confirmed via a real, non-mocked integration test (`ipv6_integration_test.go`'s `TestRunScanIPv6LoopbackAgainstRealTarget`) that runs the actual `RunScan` pipeline against `::1` with a real `nmap` binary — no masscan involved at all — and checks that both the bare discovery and the full `-sV`/banner enrichment (service name, product, SSH banner) come back correctly; skipped, not failed, if nmap isn't installed or nothing is listening on `::1:22`, matching the existing gated-integration-test pattern (`gowitness_test.go`/`rdp_test.go`/`tlscert_test.go`).

Three unrelated `fmt.Sprintf("%s:%d", ip, port)`-style address constructions (the gowitness URL and RDP progress-log string in `orchestrator.go`, the TLS dial address in `tlscert.go`, and xfreerdp's `/v:` target in `rdp.go`) were real bugs for any IPv6 host reaching stages 3-5 — an unbracketed IPv6 literal like `fe80::1:443` is ambiguous/invalid. Fixed by switching all four to `net.JoinHostPort(ip, strconv.Itoa(port))`, which already brackets IPv6 (`[fe80::1]:443`) and leaves IPv4 untouched — no custom bracket-detection code needed.

### Scanner installer (`scanner/install.sh`)

Supports two distro families, detected from `/etc/os-release`'s `ID`/`ID_LIKE` (falling back to whichever package manager is actually present if that detection is inconclusive): Debian/Ubuntu (`apt-get`) and RHEL/Rocky/Alma/Fedora (`dnf`) - `pkg_install()` wraps whichever one applies, used everywhere a package needs installing so the rest of the script doesn't need its own family branches. Required packages (`nmap`, `libcap`/`libcap2-bin`, `acl`, and `masscan` - see below) abort the script on failure; optional ones (`chromium`, `freerdp`/`freerdp3-x11`, `xvfb`/`xorg-x11-server-Xvfb`, `imagemagick`/`ImageMagick`, `tesseract-ocr`/`tesseract`, plus building `gowitness` itself via `go install`) only warn — consistent with those features already being best-effort everywhere else in this codebase (see the pipeline stages above), so a missing optional dependency shouldn't block getting the scanner running at all. Runs as a dedicated system user (`porttorch`, `/var/lib/porttorch`) rather than root, since `setcap` on the `masscan`/`nmap` binaries themselves is what grants raw-socket access (file capabilities, independent of the calling process's UID) — the systemd unit therefore must NOT set `NoNewPrivileges=true`, which would suppress exactly that file-capability inheritance on exec. Re-running the script (e.g. after `git pull`) rebuilds and restarts the service but never touches an existing `config.yaml` — the interactive webserver-URL/API-key prompt only runs once, on first install. `./install.sh --rebuild-only` skips the package-install/gowitness/setcap/user/config/systemd-unit steps entirely and just gets the `porttorch` binary (see below) + `systemctl restart` - a fast path for "I only changed Go source, nothing else" that requires a prior full install to already exist (checked up front: system user, `config.yaml`, and the systemd unit file must all already be present, or it exits with a clear error rather than doing a partial/confusing install). Added after a real case of "re-ran the installer, still looks like the old binary" turned out to be checking `porttorch --version`/the dashboard's reported version as the signal - which hadn't actually been bumped in `internal/version/version.go` despite substantial code changes, so the (correctly rebuilt) binary looked unchanged. Bump the version var on meaningful changes if you want re-running the installer to be visibly distinguishable from not having rebuilt at all.

**Two real gaps on the RHEL/Fedora side, confirmed by actually running the installer against real Rocky Linux 9 and Fedora 41 containers (including a genuine raw-socket capability check, not just "setcap didn't error") - not just reasoned about:**

- **`masscan` is packaged on Fedora but not in RHEL9/Rocky9/Alma9's own repos or EPEL** - confirmed via `dnf search masscan` returning nothing even with both EPEL and CRB enabled (EPEL carried it for EL7/EL8, dropped for EL9). The installer tries `dnf install -y masscan` first (succeeds on Fedora, gets distro-maintained updates); when that fails, it builds from source instead (`git clone` + `make`, needing `gcc make git libpcap-devel`, installed to `/usr/local/bin/masscan`) - confirmed this build actually runs and, once `setcap` is applied the same as the packaged case, actually opens raw sockets successfully (tested with a real container granted `--cap-add=NET_RAW --cap-add=NET_ADMIN`, not just `getcap` reporting the file capability). A second, narrower packaging conflict surfaced during this same testing: RHEL-family minimal images (including this installer's own test containers) ship `curl-minimal` preinstalled, which conflicts with the full `curl` package dnf would otherwise try to install alongside `nmap`/`libcap`/`acl` - worked around by only installing `curl` if it isn't already available under either name, since `curl-minimal` is fully sufficient for this script's own plain HTTPS downloads. A third gap, found later while adding nuclei support below and confirmed the same way (a real install.sh run against a fresh Rocky 9 container): `libpcap-devel` - needed only for the masscan-from-source build above - lives in CRB (CodeReady Builder), not the base repo or EPEL, so a stock Rocky/RHEL9 host with only EPEL enabled failed this exact `dnf install` outright (`Unable to find a match: libpcap-devel`) before ever reaching the masscan build itself. Fixed by enabling CRB (`dnf install -y dnf-plugins-core && dnf config-manager --set-enabled crb`) right before that install, same "not needed on Fedora" condition as EPEL.
- **SELinux (Enforcing by default on RHEL/Fedora, unlike Debian) is a second access-control layer on top of the `setcap` capabilities and the self-update ACL grant below** - a file capability or POSIX ACL permission SELinux's own policy doesn't separately allow can still be silently denied, independent of whether the underlying Linux capability/ACL mechanism itself is set up correctly. The installer does not attempt to write an SELinux policy, only warns if `getenforce` reports `Enforcing` - this one is **not** verified end-to-end against a real enforcing policy the way the masscan-from-source path above is, since Docker containers don't run a full guest SELinux userspace to test against.

**Chromium and FreeRDP screenshot support, by contrast, were both confirmed working correctly on Fedora and Rocky Linux via this same testing** - the original assumption going in was that these would be the main RHEL/Fedora risk (Red Hat has historically been more conservative about shipping Chromium), but `dnf install chromium`/`dnf install freerdp` both resolved and worked cleanly via EPEL on Rocky and natively on Fedora, with `porttorch doctor` confirming all of gowitness/Chrome/xfreerdp/Xvfb/ImageMagick/tesseract found and working on both. The one real difference: FreeRDP's CLI binary is named `xfreerdp` (not `xfreerdp3`) on both Fedora and RHEL-family, regardless of which FreeRDP major version the distro actually ships (Fedora ships 3.x, Rocky ships 2.x, both under the same `xfreerdp` name) - confirmed the exact CLI flags this scanner passes (`/cert:ignore`, `/sec:rdp`, `/log-level:OFF`, etc.) are supported identically by both major versions, so no scanner-side code needed to change, only which binary name `config.yaml`'s `xfreerdpPath` points at. The installer detects this automatically at config-generation time (`command -v xfreerdp3` first, falling back to plain `xfreerdp`) and writes it into the generated `config.yaml` only when it differs from the compiled-in `"xfreerdp3"` default, so a Debian install's config looks exactly as it always has. Chrome/Chromium needed no equivalent handling - `chromePath` is left unset by default on every distro, and gowitness's own `chromedp`-based auto-detection already finds the `chromium-browser` binary name Fedora/RHEL-family use (confirmed via `porttorch doctor`'s "Chrome/Chromium (auto-detected)" check reporting `/usr/bin/chromium-browser` correctly on both test distros).

**`nuclei` (the web-vulnerability-scanning stage's binary - see the root `CLAUDE.md`'s Scan Profiles-style "nuclei web application scanning" section) is packaged in the exact inverse pattern from masscan above** - confirmed by testing: unpackaged on Debian/Ubuntu (`apt-cache policy nuclei` returns nothing) and on Fedora's own repos, but genuinely available via EPEL on RHEL-family (`dnf search nuclei` on Rocky Linux 9 with EPEL enabled matches `nuclei.x86_64`, version 3.11.0). The installer tries `dnf install -y nuclei` only on RHEL-family non-Fedora hosts (mirroring the EPEL-enable condition above); everywhere else (Debian, Fedora, or a failed EPEL attempt) falls back to `go install github.com/projectdiscovery/nuclei/v3/cmd/nuclei@latest`, same treatment as `gowitness` - both confirmed working end-to-end via a real full `install.sh` run on both Debian bookworm and Rocky Linux 9 containers, reaching the final "Scanner registration" prompt cleanly on both. After installing (either way), the script runs `nuclei -update-templates` once, best-effort - nuclei's own template repo installs to `~/nuclei-templates` (confirmed via testing, not `~/.config/nuclei/templates` as its own docs might suggest), and is a one-time fetch here, not kept up to date automatically afterward; an admin who wants fresher templates re-runs `nuclei -update-templates` manually - **and specifically not via `install.sh --rebuild-only`**, which skips this step entirely along with the rest of the `else` branch it lives in (that flag only ever rebuilds/replaces the `porttorch` binary and restarts the service). It also has to be run **as the same user the systemd service runs as** (`sudo -u porttorch nuclei -update-templates`): the tree location is per-user (`os.UserHomeDir()`, see `pipeline.DefaultNucleiTemplatesDir`), so a plain root-run update writes `/root/nuclei-templates`, which the service user's own scans and `NucleiTemplatesUpdatedAt` never look at. `install.sh` used to have exactly this bug - it runs as root, so a fresh install's very first template fetch landed in root's home and the service never saw it. Fixed by moving the fetch to *after* the service user is created (it previously ran before `useradd`, when that user might not even exist yet) and invoking it as `sudo -u "$SERVICE_USER" env HOME="$SERVICE_HOME" nuclei -update-templates` - `HOME` set explicitly rather than relying on sudo's own handling, since whether sudo resets it depends on the host's sudoers policy (`always_set_home`/`env_keep`), which this script can't assume. Verified in a disposable container that the tree lands in the service user's home, owned by them, with nothing written to `/root`. The `--rebuild-only` fast path deliberately still skips it: that flag exists for "I only changed Go source", and a multi-minute template download doesn't belong there.

**`porttorch doctor` checks the template tree separately from the `nuclei` binary** (`checkNucleiTemplates`), which is what makes this whole class of mistake visible at all - a resolvable binary says nothing about whether it has any templates to run, and the two fail independently. Reports the tree's age, warning past 30 days (the same threshold as the webserver's own Fleet Health card, kept as its own small copy for the same reason `compareSemver` is duplicated across the two languages) and warning-with-instructions when it's missing entirely. Warning-only, never a failure: running without nuclei at all is a supported configuration, same as gowitness/RDP/tesseract.

**Getting the `porttorch` binary itself is one of two paths, decided automatically.** If this checkout's current commit is exactly a `scanner-vX.Y.Z` tag (`git describe --tags --exact-match --match 'scanner-v*'`), the binary is downloaded from that tag's GitHub Release instead of being built (`download_release_binary`, checksum-verified against the release's `SHA256SUMS` before `install`-ing it to `$BIN_PATH` — a download or verification failure is never treated as fatal, it just falls back to building from source instead, logged via `warn`). Any other checkout state (a branch, or commits ahead of the last tag) has no matching release, so it always falls back to source — this can never install code different from what's actually checked out here, since the download path only ever activates when the checkout *is* the release. `--from-source` forces the from-source path unconditionally, e.g. for testing local scanner changes or on a host with no route to github.com's release CDN. Only building from source needs a Go toolchain: it's still bootstrapped the same way as before (built from the upstream tarball into `/usr/local/go` rather than trusting `apt`'s `golang-go`, frequently far behind the `go.mod` version on stable Debian releases — checked directly at `/usr/local/go/bin/go` in addition to `$PATH`, since the script's own `export PATH=...` only affects its own process and never persists, so a plain `command -v go` would otherwise report a false miss and silently re-download Go on every re-run) but only runs when actually needed - i.e. not skipped just because `--rebuild-only` was passed, since `gowitness` (below) always needs it regardless of which path got `porttorch` itself. The releasing side is `.github/workflows/scanner-release.yml`: triggered by a `scanner-v*` tag push (or manual `workflow_dispatch` with a `tag` input, for re-publishing an existing tag - e.g. after fixing a bug in the release workflow itself, since a tag's own release build always runs the workflow YAML as it existed at that tag's commit, not whatever's since been fixed on `master`), it gofmt/vet/test-checks the code, cross-compiles `linux/amd64`+`linux/arm64` (`CGO_ENABLED=0` - confirmed no cgo anywhere in this module) with the version injected via `-ldflags` (see the root `CLAUDE.md`'s "Versioning" section), and publishes both binaries plus `SHA256SUMS` as release assets (idempotent via `gh release view`+`upload --clobber` if the release already exists, so re-dispatching doesn't fail). `gowitness` is still always built from source regardless of which path `porttorch` took - it isn't part of this project's own releases, so there's nothing to download for it.



### The queue loop runs several scans at once (`maxConcurrentScans`)

`StartPolling` used to call `pollOnce` inline, so the loop blocked for the entire duration of a queue-triggered scan: a `/16` or a wide UDP sweep held the queue for hours, and the webserver's scan priority could only decide *who's next*, never *who gets in now*. `config.yaml`'s `maxConcurrentScans` (default **1** - byte-for-byte the old behaviour) caps how many queued requests this process works on at once, and the ticker branch keeps claiming until the slots are full or the queue is empty.

**Nothing in the pipeline needed changing for this.** The local REST endpoint has always done `go s.runScan(...)`, so concurrent scans were already possible on this process and every temp file involved is already `os.CreateTemp`/`os.MkdirTemp` with a random suffix (masscan output, exclude files, gowitness/RDP shot dirs, nuclei JSONL, `submitqueue`'s own entry dirs), and `CleanupScreenshots` only ever removes the dirs belonging to its own result. The change is entirely in who is allowed to start a scan.

**A slot is reserved *before* the claim, not after.** `PollNextScanRequest` mutates `scan_requests` on the webserver, so claiming a request this process then can't run would leave it looking like this scanner was working on it. That's also why `runningScans` is its own counter rather than `len(s.cancels)`: there's a window where a slot is taken but no cancel func exists yet. `pollOnce` owns the slot and hands it to the scan's goroutine once one is actually started; every path that returns without starting a scan releases it itself.

A **REST-triggered** scan (`handleCreateScan`) takes a slot too, but via `reserveScanSlot`, which doesn't check the limit: someone running a scan locally on that host is an explicit action and is never refused - it just means the queue loop backs off rather than piling more work on top of it.

An empty queue still costs exactly one poll per tick, not one per free slot, so raising the limit doesn't multiply the request rate against the webserver for an idle scanner - pinned down by its own test, alongside tests that the default of 1 claims exactly one request while a scan is running, that a limit of 3 genuinely runs three in parallel, and that freed slots are reusable (a leaked slot would leave the scanner permanently unable to pick up work). All run under `-race`.

Raising it is a resource decision, not a free speedup: `concurrency`, `gowitnessConcurrency`, `nucleiConcurrency` and the rest are **per-scan**, so two scans at once means twice the processes and twice the bandwidth.

### Reporting slot usage back to the dashboard

Capacity is only useful if whoever queues work can see it, and the webserver cannot read a scanner's `config.yaml`. So serve mode reports `X-Scanner-Scan-Slots: running/max` on every authenticated request, alongside the `X-Scanner-Version` / `X-Scanner-Submit-Queue-Pending` headers that already ride along.

The header is **omitted entirely** rather than sent as `0/0` when this process has no scan slots at all (`scan`/`menu`), because absence is load-bearing: it is how the webserver distinguishes "unknown" from a reported 0, and a one-shot run on the same host must not overwrite a serve process's reported capacity. `PublishScanSlots` is called once at startup so an idle scanner reports `0/N` from its very first request rather than staying unknown until it happens to run something, and again from the config watcher, since otherwise a dashboard-changed limit wouldn't show up until the next scan started or finished. The two values are separate atomics rather than a mutex-guarded pair: they are only ever read together to build one header line, and a momentarily mismatched pair during a limit change is a cosmetically odd number, not a correctness problem (the webserver rejects `running > max` anyway).

## Dashboard-managed config overrides

`serve` mode runs a fifth watcher alongside `StartPolling`/`StartCancelWatcher`/`StartUpdateWatcher`/`StartTemplateUpdateWatcher`: `Server.StartConfigWatcher` polls `GET /api/ingest/config` and overlays the returned tuning onto the in-memory pipeline config. Its own loop rather than a step inside `pollOnce` for the same reason as the others: "lower the rate on this scanner, it's hammering a fragile segment" should land on a fixed interval *during* a long scan, not whenever the queue loop next happens to have something to do.

**Overrides are applied in memory only; `config.yaml` on disk is never rewritten.** A restart therefore falls back to the file and the override is simply fetched again on the next tick - which is also what makes a bad override always undoable from the dashboard, with no risk of having corrupted the file in the meantime.

`applyConfigOverrides` resets to `Server.baseCfg` (the config as loaded at startup) before applying, and that reset is the load-bearing part: without it, *clearing* a setting on the dashboard would leave the last pushed value in memory until the process restarted, which is the opposite of what clearing means. It returns only the settings whose value actually changed, so `scanner.config_applied` appears when something really did rather than on every poll. An unknown key is ignored rather than erroring, so a scanner older than a newly added tunable keeps working.

`maxConcurrentScans` is the one override that isn't a pipeline setting - it governs how many scans this process runs at once, and putting it on the struct handed to `RunScan` would give every scan a field about a queue it knows nothing about. `applyServeOverrides` handles it with the identical base-first semantics; the webserver sends it in the same map and knows no difference.

`s.pcfg` gained its own `cfgMu` now that a watcher writes it - deliberately not `s.mu`, which is held around scan bookkeeping; a scan starting shouldn't block, or be blocked by, a config poll. `runScan` takes its copy via `s.pipelineConfig()` under that lock, so a scan runs against one coherent config even if the watcher updates it mid-scan.
