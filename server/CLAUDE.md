# server/CLAUDE.md

Webserver-specific commands and architecture - the Node/TS backend + React frontend in this directory. See the repo root [`CLAUDE.md`](../CLAUDE.md) for the project overview and cross-cutting concerns (excludes enforcement, Scan Profiles, scanner self-update, logging conventions, versioning) that span both this and `scanner/`.

## Commands

```
npm install                    # also run: npm install --prefix frontend
npm run dev                    # tsx watch, backend only (frontend: npm run dev --prefix frontend, Vite proxies /api and /auth to :8443)
npm run build                  # tsc + frontend vite build, output to dist/ and frontend/dist/
npm start                      # run the built server (node dist/src/index.js)
npm run migrate:up             # apply migrations (node-pg-migrate, migrations/*.js)
npm run migrate:down
npm run seed-admin:dev         # upsert admin user from ADMIN_USERNAME/ADMIN_PASSWORD env vars (tsx)
npx tsc -p tsconfig.json --noEmit   # type-check backend only (includes *.test.ts - see tsconfig.build.json below)
npx tsc -b                     # type-check frontend only (run from server/frontend)
npm test                       # vitest run - unit tests for pure-logic modules, see below
npm run test:watch             # same, in watch mode
npm run test:integration        # vitest against a real Postgres - see "Integration tests" below, needs postgres-test running + migrated first
```

**Unit tests (vitest) exist only for pure-logic modules that need no database/network** - `auth/totp.ts`, `lib/cron.ts`, `lib/net.ts`, `lib/dateOnly.ts`, `lib/staleness.ts`, `ingest/apiKeyAuth.ts`'s `hashApiKey`. `vitest.config.ts` sets dummy `DATABASE_URL`/`SESSION_SECRET` env vars purely so `config.ts`'s `required()` doesn't throw at import time for modules that transitively import it (e.g. `lib/staleness.ts` via `config`) - none of these tests actually touch a database, and the config excludes `tests/integration/**` so `npm test` never needs one running. `tsconfig.build.json` (extends `tsconfig.json`, adds `src/**/*.test.ts` to `exclude`) exists so the production `npm run build` doesn't emit compiled test files into `dist/` (and from there into the Docker image) - the plain `npx tsc -p tsconfig.json --noEmit` dev command still type-checks test files, only the build output is filtered. `totp.test.ts` is the one worth understanding before extending: it cross-checks `verifyToken` against a second, independently-written RFC 4226 HOTP implementation inline in the test file (different byte-packing approach - `DataView` instead of the source's `Buffer.writeUInt32BE` - deliberately, so a bug shared by both wouldn't just be a copy-paste artifact) rather than hardcoding expected codes from memory, which would risk baking in a misremembered constant.

**Integration tests** (`tests/integration/*.integration.test.ts`) exercise real routes through `supertest` against a real, disposable Postgres - `docker compose --profile test up -d postgres-test` (a separate service in `docker-compose.yml`, `tmpfs` data dir, published on `127.0.0.1:5433`, never starts with a plain `docker compose up`), then `DATABASE_URL=postgres://porttorch_test:porttorch_test@localhost:5433/porttorch_test npm run migrate:up` once before the first run. `src/app.ts` (extracted from `src/index.ts` for exactly this reason) exports `buildApp()` - the fully-wired Express app (session, routers) with none of `index.ts`'s process-level side effects (HTTPS listener, self-signed cert generation, the background scheduler/CVE-sync/retention/webhook-alert timers) - so a test can import a real app without any of that running against the test database. `tests/integration/helpers.ts`'s `loginAs()` works around a real, confirmed-by-testing limitation rather than a hypothetical one: the session cookie is `secure: true`, and supertest's own `request.agent()` cookie jar correctly refuses to resend a Secure-flagged cookie over what it perceives as a plain-http connection (the same thing a real browser would do) - so `loginAs` logs in once (with `X-Forwarded-Proto: https` so `express-session`'s own secure-cookie check passes, since `trust proxy` is already enabled) and manually re-attaches the extracted cookie on every subsequent call instead of relying on the agent's jar. `vitest.integration.config.ts` sets `fileParallelism: false` since every integration test file shares one real database - parallel files could otherwise see each other's fixtures (e.g. two files' excludes-union assertions colliding on the same global exclude). Current coverage: RBAC boundaries (`rbac.integration.test.ts`), the scan-request queue's pending→cancelled state machine including the scanner's own claim query (`scanQueue.integration.test.ts`), the excludes global+scoped union (`excludes.integration.test.ts`), host identity being scoped per scanner agent rather than by `ip` alone (`hostIdentity.integration.test.ts`), and account preferences' partial-update semantics (`preferences.integration.test.ts`) - each test creates its own uniquely-named fixtures (users, scanner agents) and deletes them in `afterEach`/`afterAll`, same discipline as this session's manual verification convention, just automated.

Writing the integration harness surfaced a real, pre-existing bug, not a hypothetical one: `src/version.ts` read `package.json` via a hardcoded `path.join(__dirname, "../../package.json")`, which only resolves correctly when running the compiled `dist/src/version.ts` (two levels under `server/`) - running `src/version.ts` directly instead (`npm run dev`'s `tsx watch src/index.ts`, and these integration tests, both one level under `server/`) resolved to the repo root instead, which has no `package.json` at all, and threw at import time. Confirmed by actually running `tsx` against `src/version.ts` directly before fixing it, not just reasoned about. Fixed by walking upward from `__dirname` looking for the nearest `package.json` instead of assuming a fixed relative depth - verified against both the compiled dist build and running `src/` directly. `app.ts`'s own analogous `frontendDist` path has the same depth-dependent construction but was never a real bug: it's guarded by `fs.existsSync()`, so resolving to the wrong (nonexistent) path in dev mode just means "skip serving the frontend statically," which is already the correct dev-mode behavior (the frontend's own Vite dev server serves it instead) - left as-is rather than "fixed" for a problem that had no actual symptom.

## Architecture

### Schedule Scans, the rescan button, and Ad-hoc Scans share one mechanism

All three features (dashboard "Rescan" button on a host, `scan_schedules` — the dashboard nav/page calls this "Schedule Scans", and the "Ad-hoc Scans" page below) write to a single `scan_requests` queue table rather than the webserver calling back into the scanner. Scanners running in `serve` mode poll `GET /api/ingest/scan-requests/next` (atomic claim via `FOR UPDATE SKIP LOCKED`) and report back via `PATCH /api/ingest/scan-requests/:id`. A schedule is just something that periodically inserts into the same queue (`server/src/scheduler.ts`, a 60s in-process ticker) — see `docs`-free context in `server/src/schedules/routes.ts` and `scanner/internal/api/server.go`'s `StartPolling`/`pollOnce`. When touching one of these three features, check whether the change belongs in the shared queue plumbing or in the feature-specific trigger.

**`scan_requests.masscan_rate` / `scan_schedules.masscan_rate` (migration `1743100000000_scan_masscan_rate.js`) is a per-scan override of the scanner's own configured `masscanRate`.** Until it existed, the rate was only settable in the scanner's `config.yaml` - so "scan this fragile segment slowly" meant SSHing to the scanner host, editing the file, restarting the service, and it then applied to every scan that scanner ran from then on. NULL means "use the scanner's config value", so existing rows and anyone who never sets it keep today's behavior exactly. Snapshotted onto `scan_requests` the same way `nse_profile`/`nuclei_profile` already are (`scheduler.ts` copies the schedule's value onto each run it spawns rather than re-reading live). Returned by `GET /api/ingest/scan-requests/next` as `masscanRate`; the scanner's `runScan` copies its `pipeline.Config` and overrides the field on the copy - never mutating `s.pcfg` - so a deliberately slow one-off scan can't quietly re-rate every later scan that long-running `serve` process handles.

### Ad-hoc Scans: a one-shot trigger against an arbitrary target, including a DNS hostname

`server/src/adhocScans/routes.ts`'s `POST /api/adhoc-scans` (`requireOperator`, same access tier as the Rescan button — not `requireAdmin` like Schedule creation, since this is a one-shot operational action, not persistent config) inserts a single `scan_requests` row directly, structurally identical to what `scheduler.ts`'s `tick()` inserts when firing a schedule (`host_id: null`, `requested_by: req.session.username`, resolved NSE/nuclei profile columns via the same `resolveNSEProfile`/`resolveNucleiProfile` Schedule creation already uses) — just triggered immediately instead of by a cron/interval check, and with no `scan_schedules` row created at all (no recurrence, nothing left behind once the scanner claims it). Because this route is reachable by restricted operator/user accounts (unlike Schedule creation, `requireAdmin`-only, where every admin is always unrestricted), it's the one scan-request-creation path that has to explicitly re-check `getAllowedScannerAgentIds(req)` against the chosen `scannerAgentId` before inserting.

**The Target field itself accepts a DNS hostname, not just an IP/CIDR/range/IPv6 list — entering one both selects what gets scanned and automatically becomes the TLS SNI / gowitness screenshot-URL hostname**, the exact same effect as manually setting a host's `probe_hostname` (see this file's "Manual 'probe hostname' override" content by way of `scanner/CLAUDE.md`'s "Scan pipeline" section), just supplied up front instead of after the fact. The webserver itself does no hostname validation or resolution here — `target_spec` is stored and transmitted as whatever string was typed, exactly like an IP/CIDR/range target — because the webserver has no visibility into a scanner's own network (root `CLAUDE.md`'s "Why two separate services": scanner-initiated-only communication, scanners sit behind NAT/firewalls with their own internal/split-horizon DNS). Resolution happens **scanner-side**, in `pipeline.RunScan` (`scanner/internal/pipeline/orchestrator.go`): `isHostname(targetSpec)` detects a target that's neither an IPv6 target, a valid IPv4 address/CIDR, nor the `start-end` range grammar; `resolveHostnameIPv4` then resolves it via the scanner's own local DNS (IPv4 only, first address only — the least-surprising interpretation of "I typed a hostname, I meant that one host," avoiding an accidental sweep of every edge IP behind a load-balanced/CDN-fronted name), rewrites the local `targetSpec` to the resolved IP for the rest of the function (masscan/nmap never see the original hostname), and merges `{resolvedIP: originalHostname}` into the existing `probeHostnames` map via `withProbeHostname` (copy-not-mutate) — the same map `RunTLSCertProbe`'s SNI and gowitness's screenshot URL already consult, so nothing downstream needed to change. A resolution failure fails the scan immediately with a clear error, same fail-fast treatment as a `GetExcludes`/`GetProbeHostnames` fetch failure elsewhere in this codebase. Since this lives at the pipeline level rather than being plumbed per-caller, Schedule Scans and the one-shot `scan` CLI get hostname-target support for free too, not just this page. No new database column, ingest endpoint, or `client.go`/`server.go` change was needed for any of this — `scan_requests.target_spec` already carried whatever string was typed, and `RunScan` already threaded a `probeHostnames` map through to the TLS/gowitness stages.

`frontend/src/pages/AdhocScans.tsx` reuses `ScanProfilePicker`/`NucleiProfilePicker` exactly as `Schedules.tsx`'s form does, with Target/Ports/Scanner fields in the same shape minus every scheduling concept (no repeat-mode builder, no cron field, no run-at picker, no persistent list below the form) — submitting shows a plain one-line confirmation rather than embedding live progress tracking, matching Schedule Scans' own "fire and forget, go look elsewhere (Scan History / the scan queue) for live state" scope. Nav entry lives in `PageHeader.tsx`'s "Scanning" dropdown, above "Schedule Scans", not admin-gated (matching Rescan's operator-level access).

`scan_schedules.schedule_type` is `'interval'` (the original "every N minutes", `interval_minutes`), `'cron'` (`cron_expression`, a standard 5-field cron string), or `'once'` (`run_at timestamptz`, a single one-time run at a picked UTC datetime) — `scan_schedules_type_fields_check` enforces exactly one of `interval_minutes`/`cron_expression`/`run_at` is set, matching the type. `server/src/lib/cron.ts` wraps the `cron-parser` package (`isValidCronExpression`/`nextCronRun`); expressions are parsed/evaluated in UTC, consistent with the interval type having no timezone concept at all (the `'once'` type's `run_at` is likewise treated as UTC — the frontend's `datetime-local` input has no timezone of its own, so `Schedules.tsx` appends `:00.000Z` before sending). `nextCronRun` supports `cron-parser`'s Quartz-style `#`/`L` weekday-of-month extension (e.g. `0 9 * * 0#1` = first Sunday of the month at 09:00 UTC, `0 9 * * 0L` = last Sunday) — confirmed via manual testing this is necessary: a plain day-of-month + day-of-week combination (e.g. `0 9 1-7 * 0`) does **not** work for "first Sunday", since POSIX cron ORs those two fields together when both are restricted, not ANDs them, so it'd match every day 1-7 of the month *and* every Sunday, not just the first one. `scheduler.ts`'s `tick()` and `schedules/routes.ts`'s create/re-enable-from-paused paths all branch on `schedule_type` to compute the next `next_run_at` correctly - `now() + interval_minutes` only makes sense for the interval type; a cron schedule's next run is whatever `nextCronRun` says, which for a schedule created or re-enabled mid-day (e.g. "daily at 09:00" created at 2pm) is *not* "now"; a `'once'` schedule has no notion of a "next" occurrence at all.

A `'once'` schedule is deliberately never deleted when it fires — consistent with this codebase's established preserve-history-over-hard-delete philosophy (host retention, scanner agent deletion, etc.). Instead `scheduler.ts`'s `tick()` sets `enabled = false` and `last_run_at` without recomputing `next_run_at`, so it shows up as a done, disabled row rather than disappearing. Re-enabling it (`PATCH /:id` with `enabled: true`) is treated as "run this one-off scan again" — `next_run_at` is reset to `now()`, firing on the very next 60s tick, same as any other schedule whose `next_run_at` has passed. The frontend (`Schedules.tsx`) reflects the fired-but-not-yet-rerun state with its own labels rather than the interval/cron ones, which would otherwise look like a bug: "-" instead of a stale past date in the Next run column, "done" instead of "paused" in Status, and "Run again" instead of "Activate" on the action button.

The frontend (`Schedules.tsx`) offers a friendly builder for the cron type (daily / specific days-of-week / Nth-or-last-weekday-of-month + a time picker) that generates the cron string client-side, plus an "edit as raw cron expression" escape hatch for anything the builder doesn't cover - both ultimately just produce a plain cron string sent to the same API field, so the backend never needs to know which path produced it.

**The friendly builder's "Time" picker and the "once" type's "Run at" `datetime-local` picker both work in the user's preferred timezone (Account settings' `pref_timezone`, falling back to the browser's own local zone if unset), not raw UTC** — this was a real reported bug: everything stored/evaluated server-side is UTC, but a browser's native time/datetime-local inputs have no concept of an arbitrary named timezone, only their own local one, and the pickers used to just prepend the raw typed digits with `Z` as if they were already UTC. `lib/zonedTime.ts` (`resolveTimezone`/`zonedDateTimeToUtcIso`/`zonedTimeToUtcHourMinute`) does the actual conversion using the standard "round-trip through `Intl.DateTimeFormat`" technique (interpret the picked wall-clock as a naive UTC instant, ask `Intl.DateTimeFormat` how that instant reads in the target zone, the difference is the zone's offset) — no date library needed. The "once" type's conversion (`zonedDateTimeToUtcIso`) is fully correct with no caveats, since a one-time event has no DST-recurrence problem. The recurring cron builder's conversion (`zonedTimeToUtcHourMinute`) is deliberately **not** perpetually DST-correct — a plain 5-field cron expression has no timezone of its own, so this bakes in the zone's *current* UTC offset at creation time (same as if the user had manually written a UTC cron expression); the UI states this caveat directly next to the generated cron preview, and if the zone's DST offset later changes, the schedule keeps firing at that fixed UTC time until deleted and recreated. Converting the picked hour/minute can shift the calendar day by ±1 (e.g. "Monday 00:30 Berlin" in winter is "Sunday 23:30 UTC") — `shiftWeekday` shifts the "days"/"monthly weekday" picker's selection by the same amount before building the cron string, or the schedule would fire on the wrong day-of-week in UTC terms. The raw "edit as raw cron expression" escape hatch is deliberately left as plain UTC, unconverted — it's a power-user tool for people who already think in cron/UTC terms directly.

Re-enabling a paused schedule (`PATCH /api/schedules/:id` with `enabled: true`) recomputes `next_run_at` from scratch (via the type-appropriate math above) if the existing value is already `<= now()` — otherwise a schedule paused for a while would show a `next_run_at` stuck visibly in the past on the dashboard. Functionally harmless either way (`scheduler.ts`'s `tick()` already treats any `next_run_at <= now()` as due and fires within the next 60s regardless), but confusing to look at, so the `PATCH` handler fetches the existing row first and only rewrites `next_run_at` in that specific stuck-in-the-past-and-being-re-enabled case (or when `intervalMinutes`/`cronExpression` itself is being changed), leaving a schedule whose `next_run_at` is still in the future untouched.

**An existing schedule's scope/ports/scanner and time can be edited, not just toggled/deleted** — `updateScheduleSchema` also accepts `targetSpec`/`portSpec`/`scannerAgentId`/`runAt` (the last only valid against a `'once'` schedule, same type-guard pattern as `intervalMinutes`/`cronExpression`). **Schedule type itself stays immutable** even via edit — converting between interval/cron/once is still delete-and-recreate only; the frontend's edit mode disables the "Schedule type" `<select>` rather than hiding it, so the field stays visible as context. Editing `runAt` sets `next_run_at` to the new value unconditionally (not the isStale-or-changing conditional the interval/cron branch uses) since a `'once'` schedule's `next_run_at` always mirrors `run_at` exactly — and editing does **not** implicitly touch `enabled`/`last_run_at`, so editing a fired schedule's time leaves it disabled until separately re-armed via the existing "Run again" toggle, keeping every field independently settable rather than adding a hidden side effect.

The frontend (`Schedules.tsx`) has no prior "edit an existing item" precedent anywhere in this app (confirmed by checking every other admin page — Excludes/Webhooks/ScannerAgents/ApiTokens/Users/host tags-comments are all create-only + toggle/delete, and there's no Modal/Dialog component anywhere in `components/`), so this establishes the first one: **the create form is reused as the edit form** rather than introducing a new modal component — clicking "Edit" on a row (`handleEdit`) pre-fills the same form state already used for creation and switches the submit button to "Save changes" (calling `api.updateSchedule` instead of `api.createSchedule`), with a "Cancel" link (`resetForm`) to back out. Pre-filling the friendly cron builder from a stored (UTC) expression needs the *inverse* of the create-time conversion: `parseCronForBuilder` first checks the expression is actually one of the builder's own producible shapes (day-of-month/month both `*`, day-of-week is `*`/a plain comma-list/`D#N`/`DL`) — anything else (e.g. a schedule created via the raw escape hatch with a real day-of-month field) falls back to opening in advanced/raw mode with the exact stored string, rather than risking silently misrepresenting an expression it can't losslessly reconstruct. `lib/zonedTime.ts`'s `utcIsoToZonedDateTimeLocal`/`utcHourMinuteToZonedTime` invert `zonedDateTimeToUtcIso`/`zonedTimeToUtcHourMinute` respectively — confirmed by testing both directions round-trip losslessly (create a "days" cron schedule with a specific weekday selection, open its edit form, and the exact same weekdays/time come back pre-filled, and saving unchanged produces the identical stored cron expression).

The schedule list is grouped into **Active / Done / Paused** sections (each an `<h3>` with a `(count)`, own `<table>`), rather than one flat sortable table with a "Status" column — mirrors `ScannerAgents.tsx`'s existing Scanning/Idle/Revoked grouping (`sharedHeaders`/`sharedCells`/`sortedGroup` helpers, same names, same pattern: one global `sortKey`/`sortDirection` still applies within each group via `sortedGroup`, just applied to three filtered subsets instead of the whole list). `scheduleStatus(s)` is the single source of truth for which group a schedule falls into (reused for both the grouping filter and the "Next run" column's `"-"` case for a fired-and-not-yet-rearmed `'once'` schedule) — the standalone "Status" column was removed as redundant once grouping itself conveys it, same reasoning `ScannerAgents.tsx` already applied to its own three sections.

### Active scans and scanner agent versions

`server/src/scanJobs/routes.ts`'s `GET /api/scan-jobs/active` (polled every 5s, includes `scanner_agent_id` specifically so callers can group by agent) is deliberately keyed off `scan_jobs.status = 'running'`, not `scan_requests.status = 'claimed'` — `scan_jobs` is created by `CreateScanJob` at the very start of every scan regardless of entry point (`scan` one-shot, `menu`, or a `scan_requests`-queue-triggered run in `serve` mode), while `scan_requests` only exists for the queue-triggered subset. A `scan_jobs` row that never gets marked `completed`/`failed` (e.g. the scanner process died mid-scan) will show as "active" indefinitely — there's no staleness *timeout* that actually marks it failed or lets another scanner pick it up, since the webserver has no independent way to know the scanner is actually gone. There is a staleness *display hint* though: `/active` flags each job `is_stale: true` via `lib/staleness.ts`'s `isStaleScanJob`, rendered as a small warning badge in both the Dashboard banner and the Scanner Agents column below.

**`isStaleScanJob` is activity-aware, not just a fixed age check against `started_at`** — a real, reported case: a scan that's genuinely still progressing (masscan's own single, unstreamable pass across a large target range legitimately taking well over an hour before nmap even starts - see below) was getting flagged stale purely from elapsed time, even while the scanner's own progress heartbeat kept arriving every few seconds. The fix: `isStaleScanJob(startedAt, lastProgressAt, thresholdMinutes)` checks staleness against `scan_job_progress.updated_at` when a row exists (falling back to `started_at` only when there's no progress row yet), since `scanner/internal/progress.Tracker`'s ticker pushes a heartbeat snapshot every `DefaultPushInterval` (3s) for as long as the scanner process is alive — regardless of whether anything *new* actually happened in that window, which is exactly what makes it a reliable liveness signal rather than a "did real progress occur" one. A genuinely dead scanner process's `Tracker` goroutine dies with it, so the heartbeat actually stops and this still correctly goes stale once that silence itself exceeds the threshold — it's "is the scanner demonstrably still alive," not "did something new happen recently." `GET /active` `LEFT JOIN`s `scan_job_progress` (`scan_job_id` is that table's own primary key, so this can never fan out to more than one row per job) to get `updated_at` per job; the dismiss endpoint (`POST /:id/dismiss`) and `webhooks/operationalAlerts.ts`'s `checkStaleScans()` each fetch it for their own candidate job(s) the same way, so all three staleness checks agree.

The threshold itself (`app_settings.stale_scan_threshold_minutes`, default 60) is a Settings-page-editable DB value, not a `config.ts` env var — same "admin needs to flip this live, not via redeploy" reasoning as `host_retention_days`/`require_admin_totp` (migration `1742800000000_app_settings_stale_scan_threshold.js`, seeded once from `STALE_SCAN_THRESHOLD_MINUTES` if set, same one-time-seed idiom as `host_retention_days`' own migration). `lib/staleness.ts`'s `isStale`/`isStaleScanJob` are pure functions that take the threshold as an explicit parameter rather than reading it themselves — every call site fetches `getAppSettings()` once and passes it through, so there's no hidden caching to go stale in its own right. `GET /api/hosts/:id`'s `lastScanRequest` gets the plain (non-activity-aware) `isStale` treatment from the same helper, measured from `claimed_at` (falling back to `created_at` if never claimed) and only for `pending`/`claimed` status — a `scan_request` has no progress-heartbeat equivalent to check (it's not "running" yet in the `scan_jobs` sense), so this one is deliberately just the age check: stuck `pending` means the target scanner hasn't polled in a while (offline), stuck `claimed` means it died after picking the request up but before finishing; `completed`/`failed` are terminal and never flagged regardless of age.

`/active`'s `target_spec`/`port_spec` reflect what was *requested*, not necessarily what's actually being probed - scan_excludes are applied scanner-side before masscan runs (see the excludes section below), so an admin watching a scan that looks like it's covering fewer hosts/ports than expected has no way to tell whether that's an exclude or something wrong. `/active` addresses this by also returning `applicable_excludes` per job (the union of global excludes and ones scoped to that job's `scanner_agent_id`, same union logic as `GET /api/ingest/excludes`) - but only when the requester is admin (`req.session.role`), since exclude management itself is `requireAdmin`-gated elsewhere; operators/users still get the base active-scans data, just without this field.

### Scan progress ("Details" popup) is scanner-pushed, not webserver-pulled

A running scan can look completely silent for a long time from a purely masscan-output perspective - it itself reports nothing until its entire pass finishes (see `scanner/CLAUDE.md`'s "Scan pipeline" section), and a full port range across a large CIDR can legitimately take well past the stale-scan threshold before nmap even starts (a real reported case: a /24 across ports 1-15000 at the default `masscanRate: 1000` takes ~64 minutes just for masscan's first pass - past the 60-minute default). `isStaleScanJob`'s activity-aware check (above) now correctly keeps this from being flagged stale on elapsed time alone, since the scanner's own progress heartbeat keeps arriving throughout that pass regardless of masscan's own silence. The "Details" button on a running scan (Dashboard's Active Scans banner, and the Scanner Agents page's active-scan column) still exists for the same underlying reason though - the stale badge (or its absence) only ever answers "is the scanner process still alive," not "what is it actually doing right now" - so an operator who wants the latter without SSHing into the scanner host to read `journalctl` still opens it.

Since all communication is scanner-initiated (see the root `CLAUDE.md`'s "Why two separate services" section), the webserver can't poll the scanner for this - so the scanner pushes it instead. `internal/progress.Tracker` (new package, `scanner/internal/progress/tracker.go`) wraps a scan's existing `onProgress` callback (already called for every pipeline stage transition - masscan/discovery/nmap/gowitness/rdp/tls, see `scanner/CLAUDE.md`'s "Scan pipeline" section) plus each host's submission outcome (a new `"submit"` stage, added alongside `onHostComplete` at all three entry points specifically for this feature). It buffers the most recent 100 lines (same cap as `internal/api/state.go`'s pre-existing, unrelated local buffer for the scanner's own `serve`-mode REST API - the two run independently even when both are active, since one feeds the webserver and the other only ever answers the scanner's own local `/scans/:id`) and pushes a snapshot - current stage, the latest message as `stageDetail`, and the log buffer - to `PATCH /api/ingest/scan-jobs/:id/progress` every `progress.DefaultPushInterval` (3s), plus once more on `Close()` so the final state isn't lost to the last few seconds of silence before the scan reports `completed`/`failed`/`cancelled`. All three entry points (`scan`, `menu`, `serve`) wire this in identically; `internal/tui/commands.go` imports the package under the alias `scanprogress` since that file already uses "progress" as the naming prefix for its own unrelated bubbletea message type.

The webserver stores this in `scan_job_progress` (one row per `scan_job_id`, `ON DELETE CASCADE`) - deliberately a separate table from `scan_jobs` itself rather than more columns on it, since this gets overwritten every few seconds for the duration of a scan (far more update traffic than anything else on that row) and holds nothing worth keeping once the job finishes, unlike `scan_jobs`' own permanent history. Each push replaces `recent_logs` wholesale rather than appending - the scanner already sends its own capped snapshot, so there's no reason to also merge/cap server-side. `GET /api/scan-jobs/:id/progress` (session-authenticated, same read-only access level as `/active` - not operator-gated, since viewing this is no more sensitive than the active-scan list already visible) returns `{currentStage, stageDetail, logs, updatedAt}` with all fields `null`/empty before the scanner's first push, which is a normal state (e.g. immediately after a scan starts), not an error.

The frontend (`components/ScanProgressModal.tsx`, opened via `components/Modal.tsx` - the first generic content modal in this app, `Lightbox.tsx` being the only prior overlay and image-specific) polls this every 3s while open. Phase 1 (masscan/discovery - IPv6's masscan-equivalent) is shown as a single done/active step, since it's genuinely sequential: it always fully finishes before anything below can start (the gowitness/nuclei/RDP/TLS worker pools only ever consume jobs nmap's own pool enqueues). Everything after that - nmap enrichment, the gowitness/nuclei/RDP/TLS/SNMP/IPMI/DNS-recursion workers, and host submissions - is **not** numbered as further sequential phases (a literal "phase 3/4/5" would misrepresent concurrent work as sequential, since all of these genuinely run alongside each other once nmap starts - see `scanner/CLAUDE.md`'s "Scan pipeline" streaming-architecture notes). Instead it's a checklist of nine named activities (`nmap`/`gowitness`/`nuclei`/`tls`/`rdp`/`snmp`/`ipmi`/`dnsrecursion`/`submit`), each independently marked not-seen / seen / currently-active based on whether that stage has appeared in the pushed logs yet - a scan with no RDP-classified ports simply never marks "RDP capture" seen, which is accurate (nothing for that worker pool to do), not a stuck step; "SNMP probe", "IPMI probe", and "DNS recursion probe" are the three exceptions that always eventually show *seen*, since (unlike RDP/HTTP/TLS) none of them are gated on any discovered port at all - see their own sections above. "Seen" is a union across every poll in the modal session, not just the latest 100-line snapshot, since an early-finishing activity could otherwise scroll out of the scanner's capped buffer before the next poll and wrongly look like it never ran. The phase 1→2 transition itself only ever moves forward within one modal session (tracked via a ref, not state, so a stale/out-of-order poll response can't flicker it backward).

Verified beyond typecheck/build: a real integration test (`scanProgress.integration.test.ts`) covers the push/read/ownership/restriction behavior, and - beyond that - an actual end-to-end run: a real compiled scanner binary invoking real `masscan` against a real compiled webserver backed by a real Postgres, confirming the exact JSON shape the frontend receives (`{"currentStage":"masscan","stageDetail":"found 0 host(s) with open ports",...}`) matches what the scanner actually sent, not just what the code is reasoned to send.

**The same popup also opens from Scan History, for an already-finished job** - `GET /:id/progress` was never actually gated on `scan_jobs.status = 'running'` in the first place (it just reads whatever's in `scan_job_progress` for that id, no status check at all), and the row itself isn't cleaned up on completion (`ON DELETE CASCADE` only fires if the `scan_jobs` row itself is deleted, which normal completion never does) - so the *final* pushed snapshot (the guaranteed one-more-push on the scanner's `Close()`, see above) was already sitting there the whole time, just with nothing in the UI pointing at it. `ScanHistory.tsx` adds the same "Details" button/`detailsJobId` state pattern as the Dashboard/Scanner Agents call sites, passing a new `live={false}` prop to `ScanProgressModal`. `live` (default `true`, so the two existing call sites are unaffected) skips the 3s polling interval (fetches the snapshot exactly once - a finished scan's data can't change, so polling it forever would just be wasted requests for identical data) and swaps one string for ones that don't imply the scan is still running - the empty-logs case reads "no progress log was recorded for this scan" instead of "the scanner pushes an update every few seconds."

**A finished scan's log feed can show the complete log, not just the last `maxLogLines` (100) - a separate, one-time upload from the scanner at `Close()`, not a bigger cap on the periodic push.** The periodic 3s push (above) has to stay small and frequent, so raising its own cap wasn't the fix; instead `progress.Tracker` also accumulates a second, much less tightly capped buffer (`maxFullLogLines`, 10000 - generous enough that no real scan should ever hit it, but still bounded rather than truly unlimited, trimming from the front the same way `maxLogLines` does if it ever is) alongside the existing one, and uploads *that* exactly once, in `Close()`, via a new `PushFullScanLog`/`PATCH /api/ingest/scan-jobs/:id/full-log` call - a genuinely separate request from the periodic ones, not a bigger version of them, so a running scan's request volume is completely unaffected. The webserver stores this in `scan_job_full_log` (one row per job, `scan_job_id` primary key, `ON DELETE CASCADE` with `scan_jobs`) - a separate table from `scan_job_progress` for the same reason `scan_job_progress` itself is separate from `scan_jobs`: different write pattern (written exactly once, vs. every few seconds, vs. never after creation). `GET /:id/progress` prefers `scan_job_full_log` over `scan_job_progress.recent_logs` whenever a row exists, and reports which one it used via a new `logsComplete` boolean - `false` for a still-running scan (the full-log row doesn't exist until `Close()`), and also `false` for anything that finished before this feature existed or whose upload happened to fail, in which case it falls back to the same capped `recent_logs` snapshot as before (same "best-effort, graceful degradation" reasoning as everywhere else scanner-pushed data is read). `ScanProgressModal.tsx`'s historical note reflects this honestly - "Complete log for this scan (N lines)" when `logsComplete` is `true`, the original "final snapshot... earlier lines were not kept" wording otherwise - rather than always claiming the log might be truncated even once it demonstrably isn't.

### Scan History is /active's historical counterpart

`GET /api/scan-jobs/history` (`scanJobs/routes.ts`) lists every terminal (`completed`/`failed`/`cancelled`, i.e. `status != 'running'`) `scan_jobs` row, paginated, searchable (target/ports/scanner name), and filterable by status. Per row it computes `duration_ms` (`finished_at - started_at`) plus `hosts_scanned`/`open_ports_found`/`screenshots`/`rdp_screenshots`/`tls_certificates` - same reasoning as the `scan.completed` log line below: these are scalar subqueries against `host_port_observations`/`screenshots`/`rdp_screenshots`/`tls_certificates` filtered by `scan_job_id`, computed from what's actually in the database rather than trusted from the scanner's own report, so they can't drift from what was actually persisted. Deliberately scalar subqueries, not joins - joining `host_port_observations` and `screenshots` into one query would fan out (a host with 10 ports and 2 screenshots multiplies into 20 rows before aggregation), silently double-counting everything.

**Postgres `count(*)`/`count(distinct ...)` returns `bigint`, which `node-postgres` returns as a JS `string`, not `number`** (avoids silent precision loss above `Number.MAX_SAFE_INTEGER` for values the driver can't tell won't occur) - existing count-returning queries elsewhere in this codebase (search facets, `open_port_count`, etc.) never noticed because they only ever *display* a single count value, where a string and a number render identically in JSX. This route was the first place that needed to combine two count columns (`screenshots + rdp_screenshots`) - left as strings, `+` silently string-concatenates instead of adding (confirmed as a real bug via testing, not just reasoned about: `"0" + "0"` rendered as `"00"` in the table, and non-zero pairs like `"5" + "20"` rendered as the equally-plausible-looking but wrong `"520"`). Fixed by explicitly `Number(...)`-wrapping every count field before sending the JSON response - the frontend (`ScanHistory.tsx`) then does real numeric addition. Any future endpoint that does arithmetic on a Kysely `sql<number>` count column needs the same explicit conversion; the TypeScript annotation alone doesn't affect the actual runtime value from the driver.

### The scan request queue as its own view

`GET /api/scan-jobs/queue` (`scanJobs/routes.ts`) is the third parallel "what's happening" view alongside `/active` (running) and `/history` (terminal) - it lists every `scan_requests` row still `status = 'pending'`, oldest first. This exists because each scanner's `serve`-mode `StartPolling`/`pollOnce` loop (see "Recurring scans and the rescan button share one mechanism" above) processes one job at a time, sequentially, per scanner instance - a rescan or scheduled run created while that scanner is already mid-scan just sits `pending` until the loop cycles back, with no prior visibility into that fact anywhere in the dashboard. The endpoint left-joins `scanner_agents` (name) and `hosts` (ip/hostname, null for schedule-triggered requests that have no `host_id`) so the Scanner Agents page's new "Queued" section can show a human-readable target without a second round-trip. `POST /api/scan-jobs/queue/:id/cancel` (operator-level, same access as dismiss/rescan on `/active`) is the queue's own cancel action - deliberately much simpler than `/:id/cancel` on a running `scan_jobs` row, since nothing is actually running yet: no scanner has claimed the request, so there's no process anywhere to notify, just a `status='pending' -> 'cancelled'` update (409 if it's already been claimed or finished by the time the click lands - re-checked server-side, not trusted from the client's last poll). Marking it `cancelled` rather than deleting the row keeps a trail (same reasoning as `dismiss` on a stuck `scan_jobs` row above) while still fully removing it from `/queue`'s own `status = 'pending'` filter and, more importantly, from the scanner's `GET /api/ingest/scan-requests/next` claim query (`ingest/routes.ts`) - which filters on the same column - so a cancelled request can never be picked up and run after the fact. Cancelling a request created by a still-`enabled` schedule doesn't touch `scan_schedules` itself - the schedule's own ticker just queues another one on its next `next_run_at`, same as if this one had run normally. A backlog here (many `pending` rows, old `created_at`) is itself a useful signal that a given scanner has stopped polling - confirmed against real accumulated data on this deployment, where a scanner that had gone quiet left over 20 hourly-scheduled requests stacked up for that agent alone, which is exactly the case this cancel action exists to let an admin clear out.

### Stopping a running scan (serve-mode only)

`POST /api/scan-jobs/:id/cancel` (operator-level, like dismiss/rescan) only ever sets `scan_jobs.cancel_requested_at` — the webserver has no inbound channel to the scanner (see the root `CLAUDE.md`'s "Why two separate services" section), so it can't tell the scanner anything directly. Only jobs with `cancellable = true` can be targeted (409 otherwise): that column is set by the scanner itself at `POST /api/ingest/scan-jobs` creation time, and is only ever `true` for the two entry points that run inside the long-lived `serve` process (`internal/api/server.go`'s `handleCreateScan` and `pollOnce`) — `scan` and `menu` are one-shot processes with nothing polling *during* their single blocking scan, so a cancellation request could never reach them no matter what the webserver does.

`serve` mode runs a second, independent goroutine loop for this — `Server.StartCancelWatcher` (`internal/api/server.go`), started alongside the existing `StartPolling` in `newServeCmd` — deliberately separate from `StartPolling`/`pollOnce`, since that loop blocks for the *entire duration* of a queue-triggered scan and couldn't notice anything else in the meantime. `StartCancelWatcher` polls `GET /api/ingest/scan-jobs/:id/cancel-requested` (scanner-authenticated, ownership-checked) for whatever's currently in `Server.cancels` (a `map[string]context.CancelFunc`, populated in `runScan` for the duration of `pipeline.RunScan`) and calls the matching `CancelFunc` when it sees `true`. Cancelling that context kills whichever external process is currently running (masscan or nmap, both invoked via `exec.CommandContext` throughout the pipeline) — confirmed against a real running scan (`ps aux` showing the masscan process actually die within one poll interval of calling `/cancel`), not just reasoned about from the code. `runScan` distinguishes "genuinely failed" from "we cancelled it" via `scanCtx.Err() != nil` and reports `CompleteScanJob`/`CompleteScanRequest` with status `"cancelled"` rather than `"failed"` — a real third terminal state, not a repurposed `"failed"`, since an operator stopping a scan on purpose and a scan genuinely erroring are different things worth telling apart in the history/audit log.

**This `scanCtx.Err()` check must happen unconditionally, not only inside `RunScan`'s error branch** — a real bug caught by testing cancellation against the streaming pipeline (see `scanner/CLAUDE.md`'s "Scan pipeline" section) rather than just reasoning about it: once hosts stream in as they finish instead of all-or-nothing at the end, a scan cancelled *after* at least one host already succeeded gets a **nil** error back from `RunScan` (it only returns an error when every host's nmap call failed), so checking `scanCtx.Err()` only inside `if err != nil` silently missed every cancellation that happened to catch a scan already streaming results in — those got misreported as `"completed"` even though `cancel_requested_at` was set. Confirmed against a real scan: cancelled mid-flight after 5 of 32 hosts had already streamed in, and without this fix the job's final status showed `"completed"`; with the fix, `"cancelled"` — and, per the point above, those 5 hosts' data stayed in the database either way, which is the whole point of streaming.

The scanner reports its own version on every ingest request (`X-Scanner-Version` header, set once in `client.go`'s `setAuthHeaders` and used by all three request-building call sites — `doJSON`, `uploadImage`, and `PollNextScanRequest`'s one-off request). `apiKeyAuth.ts` records it alongside `last_seen_at`/`last_seen_ip` on every authenticated request, so the Scanner Agents page reflects whatever version last talked to the webserver, not just whatever was true when the agent was created — useful for spotting a fleet where some scanners haven't been upgraded yet.

The Scanner Agents page groups agents into three sections — **Scanning** (has a row in `/api/scan-jobs/active`), **Idle** (neither scanning nor revoked), **Revoked** — computed client-side from the same `GET /api/agents`/`/api/scan-jobs/active` data the page already fetched, rather than a new endpoint. A scanning agent's Revoke button is hidden (not just disabled) - revoking mid-scan would leave it authenticated but permanently unable to report that job's outcome, so the scan has to be stopped first via the existing Stop button; idle agents keep Revoke unchanged.

### Fleet Health is a client-side aggregation, not a new backend concept

`/health` (`frontend/src/pages/FleetHealth.tsx`) answers "is anything wrong with the fleet itself" in one glance, without an admin having to separately check the Scanner Agents page, the scan queue, and Settings. `frontend/src/lib/useFleetHealth.ts` (shared by the Fleet Health page itself and the Dashboard's own small "needs attention" banner, so the two can never disagree) is a pure client-side aggregation of data other pages already fetch: `GET /api/agents`, the latest cached scanner release, `GET /api/scan-jobs/active`, `GET /api/scan-jobs/queue`, `GET /api/scan-jobs/queue-threshold`, and (admin-only) the webserver's own TLS certificate info. Each of five cards gets an independent `HealthStatus` (`"ok" | "warning" | "critical"`, `worstOf(...)` picks the worst across all of them for the page's overall banner):

- **Scanner Fleet** — `critical` if any active scan job is `is_stale`, else `ok`.
- **Scanner Updates** — `critical` if any live agent's `update_request_status === "failed"`; else `ok`. A newer release existing (or an update already requested and still pending) is deliberately *not* a `warning` - a real, reported point of confusion, since it isn't itself a problem - it still shows as a plain, muted "N behind"/"N update pending" detail line on the card, just without escalating the card's own status color or the page's overall banner.
- **Scan Queue** — `ok` if nothing's pending; `critical` if the oldest pending `scan_requests` row has been waiting past a 30-minute display-only threshold (`STALE_QUEUE_THRESHOLD_MS` - a strong signal the target scanner has stopped polling entirely, same reasoning as "The scan request queue as its own view" above, and independent of the setting below since a single stuck-30-minutes request means the same thing regardless of how many others are also queued); else `warning` once the queue depth reaches `app_settings.scan_queue_warning_threshold` (admin-editable on the Settings page, default 1 - a real report that warning on even a single pending request was too sensitive for a fleet where a handful queued during a busy period is normal). `GET /api/scan-jobs/queue-threshold` is deliberately **not** admin-gated (same "read-only hint value" precedent as `GET /api/agents/latest-release`) even though *setting* it (`PATCH /api/settings/app`) is - every role sees Fleet Health, so every role needs the same threshold to compute a consistent status, not just admins.
- **Submission Retry Backlog** — `ok` if no live agent reports a nonzero `submit_queue_pending`; `critical` at 20+ pending submissions fleet-wide; else `warning`. Distinct from the Scan Queue card above: this tracks a scanner's local `internal/submitqueue` backlog (results waiting to be *resubmitted* after a transient failure), not `scan_requests` waiting to be *claimed* - see `scanner/CLAUDE.md`'s "Submission durability" section for where the underlying `submit_queue_pending` value comes from.
- **Webserver TLS Certificate** (admin-only, omitted entirely for other roles) — derived from the same `certExpiryStatus` helper the Settings page and the fleet-wide Certificates page both already use.

Deliberately **excludes** the fleet-wide Certificates page (TLS certificates captured *from scanned hosts*) - those devices aren't part of "our fleet" the way the scanners and the webserver itself are, so their certificate hygiene isn't this page's concern; a card for it existed briefly and was removed for exactly this reason. The Dashboard's own banner (`callout-link`, rendered directly under `PageHeader`, only when `overall !== "ok"`) links straight to `/health` rather than duplicating any of the card content inline.

### Finding triage: marking a CVE or web finding as handled

**`finding_triage` (migration `1743000000000_finding_triage.js`) is what stops a known-false-positive or accepted-risk finding from re-competing for attention after every single scan.** Before it there was no such concept anywhere - the only workaround was a free-text host comment, which nothing filters on. States are `false_positive` / `accepted_risk` / `fixed`; **absence of a row means "open"/untriaged**, the same absence-means-default idiom as `scan_excludes.scanner_agent_id IS NULL`, so the table only ever holds deliberate exceptions rather than a row per finding in the fleet.

**It's its own table rather than a column on the finding, because neither finding kind has a stable row to hang state off.** CVE matches aren't persisted at all - `vulnerabilities/routes.ts` derives them at query time by joining `current_host_ports.cpes` against `cve_cache`, so there is literally no row to update. `nuclei_findings` rows *are* persisted, but a fresh row is inserted on every scan that re-observes the finding (one row per observation, deliberately), so state stored there would be silently dropped on the next rescan - covered by an integration test that rescans and re-asserts the state survived. Identity therefore reuses whatever each kind already treats as its identity elsewhere: `(host_id, cve_id)` for CVEs, and `(host_id, template_id, matched_at)` for nuclei - the exact triple `ingest/routes.ts` already uses to decide whether a finding is new enough to fire a webhook. Rather than one packed key string, the two shapes are explicit nullable columns with a `CHECK` enforcing exactly one is populated (a `matched_at` is a URL and could contain any delimiter), plus **two partial unique indexes** - Postgres treats each NULL as distinct, so a plain `UNIQUE` would happily allow duplicate `cve` rows; same shape and reasoning as `scan_excludes_global_unique`.

`PUT /api/finding-triage` upserts (re-triaging is the normal case, not a conflict) and `DELETE` removes the row rather than storing an explicit "open", keeping absence the single source of truth. Both are `requireOperator`, matching host tags/comments/rescan - this is day-to-day analyst annotation, and it never deletes or hides underlying scan data, only its display state. The Vulnerabilities and Web Findings pages left-join the state in and **hide triaged findings by default** (a toggle reveals them) - that filtering is the actual payoff; the shared `TriageControl.tsx` is a plain `<select>` rather than a modal, since the action is reversible from the same control.

**Triage is consulted in four more places than the two list pages, and deliberately means something different in each** - `findingTriage/sqlFilters.ts` holds that policy in one place precisely so the four call sites can't drift apart (they're separate raw-SQL queries with different table aliases). `NOT_A_LIVE_RISK_STATES` (`false_positive`, `fixed`) is excluded from the host list's risk indicator (`cve_count`/`max_cvss_score`/`has_kev` in `GET /api/hosts`) - **`accepted_risk` is deliberately not in that set**, since an accepted risk is still a real, still-present exposure and dropping it would misrepresent the fleet's actual risk number. `ANY_TRIAGE_STATE` (all three) is excluded from EPSS and KEV webhook alerting (`cve/epssSync.ts`, `cve/kevSync.ts`) - re-paging on a decision someone already made, accepted risk included, is exactly the alert fatigue triage exists to prevent, and that broader set is the one place the two policies differ. Host Detail is the third answer: it attaches triage state but **hides nothing**, since a host's own page is its complete record - a triaged CVE stays listed with a badge. Pinned by `tests/integration/triageConsistency.integration.test.ts`, which asserts all three behaviors against the same fixture.

### Deleting a scanner agent preserves its scan history

`DELETE /api/agents/:id` (admin-only, like agent creation/revocation) only ever accepts an agent that's already revoked (`revoked_at IS NOT NULL`, checked in the query itself, 404 otherwise) — deleting an agent that could still be actively scanning makes no sense, and revocation is the existing, separate step that stops it from authenticating at all. The delete itself does **not** cascade-delete that agent's historical `scan_jobs`/`scan_requests`: migration `1739600000000_scanner_agent_delete.js` dropped the `NOT NULL` constraint on both tables' `scanner_agent_id` and changed their FK to `ON DELETE SET NULL`, so a deleted agent's past scan history survives with the agent reference cleared, rather than disappearing along with the agent row. This was a deliberate design choice (confirmed with the user before touching the schema, given the destructive/irreversible alternative): a naive cascading delete would have silently wiped out the very audit trail an admin might delete an agent *because of* wanting to keep clean. `scan_schedules`/`scan_excludes` still cascade on agent delete, since a schedule or exclude scoped to a now-gone agent is meaningless on its own. `requestRescan()` (`server/src/rescan.ts`) guards against the resulting nullable `scanner_agent_id`: if the scanner that last scanned a host has since been deleted, rescanning that host now fails with a clear 400 instead of erroring on a null agent reference.

### Host retention

`server/src/retention.ts` runs an hourly sweep (same in-process-timer pattern as `scheduler.ts` and `webhooks/expiryAlerts.ts`) that hard-deletes any host whose `last_seen_at` is older than the current retention window (0 disables the sweep). There's deliberately no "still alive but portless" check: masscan only reports hosts it finds with at least one open port, so a host that's gone quiet simply stops appearing in scan results and its `last_seen_at` freezes — the timestamp alone already means "not found by a scanner in a while." Deleting the `hosts` row cascades (`ON DELETE CASCADE`) through `host_port_observations`, `screenshots`, `rdp_screenshots`, `tls_certificates`, `ssh_host_keys`, `host_tags`, and `host_comments`; `scan_requests.host_id` is `ON DELETE SET NULL` instead, so queue rows survive with the host reference cleared. Every purge gets both a `logger.info` and a `recordAudit` call (actor `"retention"`), same as any other mutation.

**The retention window moved from a `config.ts` env var into `app_settings.host_retention_days`** (migration `1742600000000_app_settings_host_retention.js`, same singleton-row idiom as `require_admin_totp` right next to it) - editable live from the Settings page instead of needing a redeploy, same reasoning as every other DB-backed `app_settings` field. The migration seeds the column from whatever `HOST_RETENTION_DAYS` was set to at upgrade time (falling back to 180, matching the env var's own old default) so an existing deployment's customized value carries over rather than silently reverting - this is the one and only place the env var is ever read again; `config.ts` no longer has a `hostRetentionDays` field at all, and `retention.ts` reads exclusively from `getAppSettings()` from here on, fetched fresh on every tick so a change takes effect on the very next hourly run without a restart.

**The actual purge logic is `retention.ts`'s exported `runRetentionSweep()`, shared by the hourly ticker and a new manual trigger** (`POST /api/settings/retention/run-now`, admin-only, same access level as every other Settings mutation) - one implementation so an on-demand cleanup from the Settings page's "Clean up now" button can never behave differently from what the scheduled sweep would have done, including the `hostRetentionDays <= 0` short-circuit (a manual run against a disabled sweep is a no-op returning `{purgedHosts: 0, purgedAuditLogEntries: 0}`, not "delete everything," which is what a naive "just use `now()` as the threshold" implementation would have done). The button's confirmation dialog states the current retention window and that the action can't be undone before running.

**The same sweep also purges `audit_log` rows older than the identical `host_retention_days` window** - `audit_log` used to be kept forever with no pruning at all (still true of `webhook_deliveries`'s own separate, fixed-count-per-webhook trim, a diagnostic tail rather than a retained record - see below). Reusing the existing host-retention setting rather than adding a second, independent one keeps "how long do we keep history" a single admin-facing knob instead of two that could silently drift apart. Computed against the same threshold instant the host purge already derived, run right after it in the same function call, and itself gets a `retention.audit_log_purged` `logger.info` + `recordAudit` entry (actor `"retention"`) when it actually deletes something - which, being newly-written, is naturally exempt from being purged by this same run and only becomes eligible on a future one once it's aged out like anything else.

**`DELETE /api/hosts/:id` (`search/routes.ts`, admin-only) is the one-off counterpart to retention's automated, age-based sweep** - a deliberate removal of one specific host regardless of `last_seen_at`, for the "this was a decommissioned/misidentified/one-off test target, I don't want to wait for retention" case. Same `requireAdmin` tier as revoking/deleting a scanner agent (not `requireOperator`, unlike the day-to-day host annotation actions like tags/comments/rescan) since this is a permanent, irreversible action. Uses the identical `deleteFrom("hosts")` shape retention's sweep already uses - same `ON DELETE CASCADE` fan-out (`host_port_observations`, `screenshots`, `rdp_screenshots`, `tls_certificates`, `ssh_host_keys`, `host_tags`, `host_comments`) and the same `scan_requests.host_id` `ON DELETE SET NULL` behavior, so a still-queued rescan for a just-deleted host survives with its host reference cleared rather than vanishing outright. `HostDetail.tsx`'s "Delete Host" button (admin-only, positioned before "Export data" in the header) confirms via `window.confirm` with the host's ip/hostname and a note that ports/screenshots/certs/tags/comments all go with it, then navigates back to the dashboard on success. `Dashboard.tsx`'s bulk selection toolbar has its own admin-only "Delete selected" button, same `Promise.allSettled([...selected].map((id) => api.deleteHost(id)))` frontend-only-reuse pattern the bulk tag/rescan actions already established (no dedicated bulk-delete endpoint) - each selected host's own `DELETE /api/hosts/:id` call either succeeds or fails independently, so one host that somehow 404s doesn't block the rest, and the status line reports how many actually succeeded.

### Database shape (`server/migrations/`)

- **`hosts.ip` (and `scanner_agents.last_seen_ip`/`audit_log.source_ip`) is Postgres `inet`, which is dual-stack** — it natively stores either an IPv4 or IPv6 address, and `<<=`/`::cidr` CIDR-containment matching (`search/routes.ts`'s dashboard search) already works correctly for both without any explicit casting. This meant adding IPv6 scan-target support needed zero migrations anywhere — the only IPv4-only surface was in application-level validation (`lib/net.ts`'s three helpers) and the scanner's masscan-only discovery stage, not the schema. See `scanner/CLAUDE.md`'s "IPv6 targets" section and the frontend note on `Dashboard.tsx`'s `compareIp` below.
- **A host's identity is `(ip, scanner_agent_id)`, not `ip` alone** (`hosts_ip_scanner_agent_id_key`, replacing a plain `UNIQUE(ip)` — migration `1740000000000_host_scanner_scoped_identity.js`). Two different scanners in two different, non-interconnected networks can each have a real device at the same private IP (overlapping RFC1918 ranges across sites are common, not an edge case) - the old global-unique-`ip` upsert (`POST /api/ingest/hosts` in `ingest/routes.ts`) would silently merge them into one `hosts` row, blending ports/screenshots/tags/comments from two unrelated physical devices. `scanner_agent_id` is set from `req.scannerAgentId` at ingest time, so it's never null for a host as of its own submission - it only ever becomes null afterward, if the scanner that reported it is later deleted (`ON DELETE SET NULL`, consistent with `scan_jobs`/`scan_requests`' own agent-delete behavior - preserves the host rather than losing it, but it can no longer collide-detect against a *different* deleted agent's same-ip host either, which is accepted as an edge case not worth chasing). Every ingest lookup that resolves "the host this submission is about" (the upsert itself, and the screenshot/RDP/TLS-certificate handlers that look a host up by ip to attach a capture to it) filters by `scanner_agent_id` in addition to `ip` - a lookup that filtered on `ip` alone would nondeterministically attach a capture to whichever scanner's same-ip host happened to match first. The backfill for pre-existing hosts (at migration time) assigns each host to whichever scanner most recently reported it (via `host_port_observations` → `scan_jobs`) - safe because `ip` was still globally unique at that point, so backfilling a value onto a single existing row can't create a new collision; it does **not** retroactively split any host that was already a merged collision before this migration existed, since there's no reliable way to un-blend already-mixed port/screenshot history after the fact. The dashboard (host list, CSV export, host detail) and the external API (`GET /api/v1/hosts/lookup` and friends) surface the owning scanner's name precisely because two rows can now legitimately share an `ip` and need to be told apart - the external API specifically returns `409` with the candidate list when an `ip`/`hostname` lookup is ambiguous, and accepts an optional `scannerAgent` (name) parameter to disambiguate, rather than silently guessing which of several real devices an external caller meant. The Dashboard's own "Scanner" filter (`search/routes.ts`'s `HostFilterParams.scannerAgentIds`, applied in `applyHostFilters` alongside every other filter) is the same idea from the search side - narrows the host list to one or more scanners' hosts (`.where("hosts.scanner_agent_id", "in", scannerAgentIds)`), defaulting to "All Scanner" (no filter applied, empty array), and combines with the free-text search box and every other facet exactly like the rest of `applyHostFilters`'s filters do (each one is an additional `AND`-ed condition, not a replacement) - options come from the same `GET /api/agents` the Scanner Agents page uses, which is `requireAuth` only, not `requireAdmin`, so every role can populate and use this filter (subject to the per-user scanner-agent restriction above, if any). It's a multi-select presented as a closed-by-default dropdown (`components/ScannerMultiSelect.tsx` - a toggle button + an absolutely-positioned checkbox panel, closing on an outside click) rather than a native `<select multiple>`, which renders as an always-open listbox, not a compact dropdown; the same component is reused on the Users page (per-account scanner access, in place of a permanent row of checkboxes), the Excludes/Schedules pages' own "Scanner" filters, and the Scanner Agents page's Queued-requests filter - anywhere "pick zero or more scanners" is needed, not just this one filter. It takes an `align` prop ("left" default, "right" for a toggle pushed to the end of its row via `.push-right`) so the checkbox panel opens growing away from the nearer viewport edge instead of overflowing it.
- `host_port_observations` is **append-only** — every scan writes new rows rather than updating existing ones, which is what gives the host detail page its history/timeline. `current_host_ports` is a view (`DISTINCT ON`, latest row per host+port+protocol) used for "current state" queries like search and facets. When adding a query that should reflect "what's true right now," use the view; when it should reflect history, query the base table.
- Almost every "current state" query (search filters, facets, the open-port count, the host detail port list) filters `state = 'open'` explicitly against `current_host_ports` — this was a real bug once (closed/filtered ports leaking into "open port" counts and facets), so any new host-listing query needs the same filter.
- `GET /api/hosts/facets`'s Ports list is capped at the top 10 (by how many hosts have each open) to keep the sidebar a manageable size - a port that's only open on a handful of hosts (or just one) is real, correctly-recorded data that simply doesn't make that cutoff, not a bug (confirmed against a real report of a "missing" port that turned out to have a host-count of 1, far below the 10th-place cutoff at the time). `GET /api/hosts/facets/ports` is the same query without the limit - fetched on demand only when "show all ports" is clicked (`Dashboard.tsx`), rather than folded into the main facets response, since it's a strictly bigger payload most sessions never need.
- Both facets routes take the same filter query params as `GET /api/hosts` (`parseHostFilterParams`) and scope every facet's counts down to whatever the *other* active filters currently narrow the host list to - a keyword search live-updates the Ports/Services/Tags/OS/Device sidebar to only matching hosts, not just the host list itself (this was a real, reported bug: the routes ignored their own `req` entirely and always returned fleet-wide counts, so the sidebar looked frozen while searching). Each facet excludes *its own* dimension when computing its own counts (e.g. selecting port 22 doesn't hide every other port from the Ports list) - standard faceted-search semantics, so a facet doesn't hide its own alternatives just because one of its own values is already picked. `current_host_ports`/`host_tags` aren't queried from `hosts` directly, so this goes through an `innerJoin("hosts", ...)` to bring `applyHostFilters`'s `hosts.*` references into scope, rather than a separate host-id lookup. Skipped entirely (no join, no `applyHostFilters` call) when no filter is active at all, so a plain unfiltered page load stays exactly as cheap as before this existed - most dashboard visits never search anything.
- **`current_host_ports` is `SELECT * FROM host_port_observations`, and Postgres freezes a view's `*` into a fixed column list at creation time** — it does not pick up columns added later to the underlying table. This bit us once when adding `extra_info`/`os_type`/`cpes` to `host_port_observations`: the migration has to explicitly `DROP VIEW` + `CREATE VIEW` again (see `1738200000000_host_os_classification.js`) whenever a new column needs to show up through the view.
- **A port that quietly stops responding never gets an explicit `closed` row, and so keeps showing as `open` in `current_host_ports` indefinitely.** `state = 'closed'`/`'filtered'` rows do exist (nmap reports them when it actually re-probes a port masscan found open and gets a different answer this time) — but masscan itself only ever reports ports it currently sees open; if a port simply stops answering masscan's SYN probe, nmap is never even asked about it that run, so *no* observation row (open, closed, or filtered) gets written for it at all, and the `DISTINCT ON`-latest-row-per-port view keeps surfacing its last-known "open" observation as if it were current. This is a real, confirmed limitation (a user noticed a port shown open on the host detail page that had actually stopped responding several scans earlier), not a bug in the view's query — masscan being a stateless SYN scanner (see above) makes it impossible to reliably tell "genuinely closed" apart from "one lost probe" purely from absence, so auto-correcting this to `closed` would risk false positives. The mitigation is a "Last confirmed" column + `stale` badge on the host detail page's Open Ports table (`HostDetail.tsx`) instead: each port's own `observed_at` is compared against the *most recent `observed_at` among this same host's ports* (not `hosts.last_seen_at`, which is set from the webserver's own `Date.now()` rather than Postgres's `now()` and can disagree by a few milliseconds even for ports written in the exact same scan — confirmed the wrong way round via testing before settling on this comparison, which stays within one clock source and produces zero false positives on a fully fresh scan).
- `hosts` carries OS/device classification (`os_name`/`os_family`/`os_vendor`/`device_type`/`os_accuracy`) upserted with `COALESCE(excluded.x, hosts.x)` rather than a plain overwrite — OS detection is root-only (see above) and doesn't run on every scan, so a non-root rescan must not erase a previously-captured classification. `mac_address`/`mac_vendor` (from nmap's `<address addrtype="mac">` XML element — `pipeline/nmap.go`'s `applyMACAddress`) use the same `COALESCE` upsert for the same underlying reason, just a different root cause: nmap only ever resolves a MAC via ARP, which only works when the target is on the scanner's own local L2 segment — confirmed against a real nmap run (`MAC Address: BC:24:11:18:6A:68 (Proxmox Server Solutions GmbH)` scanning a same-subnet gateway; a routed target's `<host>` element has no `mac`-typed `<address>` at all). A rescan from a different vantage point, or of a target that's since become routed instead of local, must not silently erase a MAC captured on an earlier, more favorably-positioned scan.
- `hosts.probe_hostname` (nullable) is the one host field the scan pipeline itself never writes — a manual, operator-set override used instead of the bare IP for TLS SNI and the gowitness screenshot URL, distinct from `hostname` (which nmap's own PTR lookup overwrites every scan). See "Manual probe hostname override" above.
- `screenshots` and `rdp_screenshots` are separate tables (different column sets — only `screenshots` has URL/HTTP status/TLS/tech/headers fields; both have `ocr_text`, nullable — populated by the scanner's Tesseract OCR pass, see `pipeline/ocr.go` above, null when tesseract wasn't installed on the scanner or recognition failed); the dashboard picks whichever is newest per host for the thumbnail (`thumbnail_id`/`thumbnail_kind` in the hosts list query) and serves images through parallel authenticated routes (`/api/screenshots/:id/image`, `/api/rdp-screenshots/:id/image`) that validate the resolved path stays under `config.screenshotDir`.
- `host_comments` is append-only, like `host_port_observations` — analyst comments (owner, ticket references, false-positive confirmations) keep their own `author`/`body`/`created_at` rather than overwriting a single field, so the host detail page can show who said what and when. Replaced an earlier single overwritable `hosts.notes` column (migration `1738500000000_host_comments.js`) precisely because a last-write-wins field lost that history.
- `host_comments`, `webhooks`, and `audit_log` are independent of the scan pipeline entirely — they're dashboard-side bookkeeping (comments annotate a host, webhooks/audit_log record actions taken through the dashboard or ingest API), not something a scan ever produces on its own. `host_tags` used to be purely manual in the same way — it no longer is, see "Auto-tags from detected services" below.

### Auto-tags from detected services

**Every ingest also derives a small set of generic service tags from the host's currently-open ports, in addition to whatever a user tagged manually** — `server/src/lib/serviceTags.ts`'s `deriveServiceTags(ports)` is a plain, unit-tested rule table (service-name substring match, with a well-known port number as fallback for a port nmap only identified generically — the same two-tier shape `pipeline/gowitness.go`'s `isHTTPPort`/`pipeline/nmap.go`'s `isSMBPort`/`pipeline/rdp.go`'s `isRDPPort` already use on the Go side, though this is its own independent TS copy rather than a shared import, same reasoning as `scanProfiles/knownNseScripts.ts` being its own copy of the Go NSE lists) covering `WebServer`, `FTP-Server`, `SSH-Server`, `Telnet`, `DNS-Server`, `RDP`, `SMB`, `Mail-Server`, `LDAP`, `VNC`, `MySQL`, `PostgreSQL`, `MSSQL`, `MongoDB`, `Redis`, `Docker-API`, `SNMP`, and `IPMI`. `ingest/routes.ts`'s host-ingest transaction calls it right after inserting that scan's `host_port_observations` rows and inserts the result into `host_tags` with the same `onConflict(...).doNothing()` idempotency every other insert in that transaction already uses — `host_tags` has no manual/auto distinction column, so this is deliberately just more rows in the same table a user's own tags live in, not a parallel system.

**An auto-tag is never removed automatically, even once the service that produced it stops appearing.** There's no "is this tag still backed by an open port" reconciliation pass — a host that once ran FTP but has since locked it down keeps its `FTP-Server` tag, which is treated as a feature, not a staleness bug: "this host has been observed running this service" is itself a fact worth keeping visible, the same preserve-history-over-hard-delete philosophy `host_port_observations` (append-only) and retention (hard-deletes the whole host, never silently edits one field of it) already follow elsewhere in this file. A user can still delete an auto-tag by hand exactly like a manual one (same `DELETE /api/hosts/:id/tags/:tag`) — but if a later scan still finds that same service open, the tag simply comes back, since derivation re-runs from scratch on every ingest rather than only on a tag's first appearance; confirmed by an integration test (`tests/integration/serviceAutoTags.integration.test.ts`) that deletes an auto-tag and then re-submits the same open port, asserting the tag reappears. Every genuinely new tag insert (an actual row, not a no-op conflict — checked via `.returning()`) gets a `host.tag_added` log line and audit entry with `added_by: "auto-tag"` instead of a username, so the Audit page can tell a system-derived tag apart from one a person actually clicked "Add" on.

**Host Detail's own tag chips visually distinguish an auto-tag from a manual one, so deleting one is an informed choice, not a guess.** `host_tags` itself still has no source/kind column (a name collision between a service-derived tag and a manually-typed one is harmless either way), so this is display-only: `frontend/src/lib/knownServiceTags.ts`'s `AUTO_TAG_NAMES` is a frontend-only copy of `serviceTags.ts`'s tag names (same independent-copy precedent as `scanProfiles/knownNseScripts.ts`, there for validation, here purely for this cue), and `HostDetail.tsx` gives a matching chip a dashed border (`.chip-auto`) plus a `title` tooltip explaining it was added automatically - a border-style change rather than a color change, since color alone wouldn't read consistently across the accent-color/theme picker.

### Roles and permissions

Three dashboard roles, stored in `users.role` and mirrored into the session (`req.session.role`, set at login in `src/auth/routes.ts`): **admin** (everything), **operator** (read-only plus rescan/tags/comments/saved searches — anything an analyst does day-to-day), and **user** (read-only). Enforcement is two middlewares in `src/auth/middleware.ts` — `requireAdmin` and `requireOperator` (admin or operator) — applied per-route on top of the router-level `requireAuth`, not router-wide, since within a single router (e.g. `search/routes.ts`) some routes are operator-level (rescan, tags, comments) and others are admin-only. Scanner agents, schedules, webhooks, scan excludes, and user management are **always** `requireAdmin`, regardless of what operators are allowed to do elsewhere — when adding a new mutating endpoint, default to `requireAdmin` unless it's clearly a day-to-day host action like the existing operator-level ones. The frontend mirrors this by hiding (not just disabling) buttons the current role can't use, keyed off `me.role` passed down from `App.tsx`. Dashboard bulk actions (tag/rescan multiple selected hosts at once) are pure frontend reuse of the existing single-host endpoints (looped with `Promise.allSettled`) — there's no separate bulk API surface, so they inherit the same operator-level permission as the single-host actions automatically.

### Per-user scanner-agent visibility restriction

An admin can restrict an `operator`/`user` account (never `admin` — admins are always unrestricted, since they could otherwise just remove their own restriction) to only see results from specific scanner agents — `user_scanner_agents` (migration `1740500000000_user_scanner_agents.js`, composite PK `(user_id, scanner_agent_id)`, both FKs `ON DELETE CASCADE`). **No assignment rows for a user means unrestricted** — the only way every pre-existing account kept working unchanged after this migration, and the same "absence means default-allow" idiom `scan_excludes.scanner_agent_id IS NULL` already used for "applies to all scanners." Loaded into the session once at login (`req.session.allowedScannerAgentIds`, `src/auth/session-types.d.ts`) — same trust/staleness model as `role` itself, so an admin changing someone's assignments takes effect on that person's *next* login, not live mid-session. `src/auth/scannerScope.ts`'s `getAllowedScannerAgentIds(req)` is the one place that reads it (`null` = unrestricted); every fleet-wide read endpoint applies it as a conditional `.where(col, "in", allowed)` — `applyHostFilters`'s 3rd parameter (`search/routes.ts`), and equivalently in `scanJobs/routes.ts` (active/history/queue), `digest/routes.ts`, `vulnerabilities/routes.ts` (raw SQL, composed as a conditional `sql` fragment), `certificates/routes.ts`, `agents/routes.ts`, and `schedules/routes.ts`'s `GET /`.

The restriction covers the **entire fleet-wide picture**, not just the main host list (confirmed scope, chosen over a smaller "just Host Detail" alternative) — this includes closing an IDOR gap that would otherwise silently defeat the whole feature: a restricted operator could still view or mutate an out-of-scope host directly by id (tags, probe-hostname, rescan, comments) if only the *list* views were filtered. `hostsRouter.param("id", ...)` (`search/routes.ts`) is the single guard covering every host-by-id route on that router at once — validates the uuid, 404s if the host doesn't exist *or* belongs to a scanner outside the session's allowed set (404, not 403, so an out-of-scope host's existence is never confirmed), and stashes the row on `req.hostRecord` so handlers don't need their own redundant existence check. `scanJobs/routes.ts`'s three mutating routes (`:id` means a different table on each of them) get the same ownership check inline per-handler instead, since a single shared `router.param` doesn't fit as cleanly there.

One easy trap: a facet/list endpoint that has a "skip the join/filter entirely when no other filter is active" fast path (e.g. `search/routes.ts`'s `hasActiveHostFilters`) must also treat a non-null restriction as "active" — otherwise a restricted user with no other filter selected skips the join and gets fleet-wide facet counts anyway. Any new fleet-wide read endpoint needs the same restriction applied, following whichever of the patterns above matches its query shape (Kysely builder vs. raw SQL).

### Audit log vs. SIEM logging — two separate concerns

`audit_log` (table, admin-only `/api/audit`) and the pino/slog stdout logging below are deliberately separate. The stdout logs are the SIEM-facing stream (external log shipper, structured for machine parsing); `audit_log` is for the in-app "who did what" view and is written via `recordAudit()` (`server/src/audit/log.ts`) alongside — not instead of — the existing `logger.info()` calls at nearly every mutation site (agents, schedules, tags, comments, rescans, webhooks, users, login/logout/lockout). `recordAudit` never throws — a failed audit write must not break the request that triggered it. When adding a new mutating endpoint, add both: the existing SIEM-style `logger.info()`/`logger.warn()` call, and a `recordAudit()` call.

`/auth/login` also has an in-memory brute-force guard (`src/auth/rateLimiter.ts`, 5 failures / 15 min, keyed by both username and source IP) — deliberately not DB-backed, since the webserver is already a single-instance deployment (same assumption `scheduler.ts` makes); state resets on restart, which is fine for this threat model.

**The Audit Log page is real pagination, not a fixed-size recent-entries list.** `GET /api/audit?page=&pageSize=&q=&from=&until=&events=&actors=` returns `{items, total, page, pageSize}` (same shape as `scan-jobs/history`), `pageSize` capped at 200; `GET /api/audit/export.csv` (same filter params, no pagination) exports every matching row - both routes share one `applyAuditFilters(query, params)` helper so an export always matches exactly what the current filtered view shows, same discipline as the Dashboard's own host export. Event and Actor are each their own multi-select filter (`ScannerMultiSelect`, repurposed as a generic "pick zero or more strings" control rather than only ever picking scanners), backed by `GET /api/audit/events`/`GET /api/audit/actors` - both **`SELECT DISTINCT ... FROM audit_log`** rather than a hardcoded list, since audit events are free-form strings written from roughly twenty different `recordAudit` call sites across the codebase and a hardcoded list would silently drift the moment a new one was added and forgot to also update it here. `actors` excludes `NULL` (system-initiated entries like `retention.host_purged` have no actor to filter by).

**Every id-shaped field inside an audit entry's JSON `details` blob is resolved to a human name at read time**, not just displayed as a bare UUID - `audit/resolveNames.ts`'s `resolveAuditNames(entries)` batches every entry's `scanner_agent_id`/`webhook_id`/`scan_profile_id`/`api_token_id`/`saved_search_id`/`scanner_agent_ids`/`host_id`/`user_id` fields into one `WHERE id IN (...)`-shaped query per table (a handful of queries total per page load, not one per row per id) and attaches a parallel `resolvedNames: Record<string, string>` to each entry, rendered by the frontend as `key: value (resolvedName)`. An id whose row no longer exists resolves to the literal string `"deleted"` rather than being omitted - this is what makes the resolution work retroactively on audit rows written long before this feature existed, and still correctly labels an entity that's since been hard-deleted. Deliberately **not** resolved: `schedule_id`/`scan_job_id`/`scan_request_id`/`comment_id`/`exclude_id` - none of those tables have a "name" column of their own, since a schedule/job/request/comment/exclude *is* its id, not a named thing with a separate identity worth looking up.

### Two-factor authentication (TOTP) is self-service, per-account, and login becomes a two-step flow once enabled

`server/src/auth/totp.ts` implements RFC 6238 TOTP directly against Node's own `crypto` (HMAC-SHA1 + dynamic truncation, base32 encode/decode written by hand) rather than pulling in a TOTP library - the algorithm itself is small, and this keeps the one genuinely security-critical piece of 2FA auditable in our own code, matching the TLS certificate probe's own stdlib-only approach. Cross-checked against `otplib` (a well-known reference implementation) for the same secret at the same timestamp during development, not just reasoned about from the RFC text. The one new dependency is `qrcode` (rendering the setup QR as a data URL) - encoding a scannable QR code well is genuinely nontrivial (Reed-Solomon error correction, matrix placement rules), unlike TOTP itself, so that one was worth taking as a dependency rather than hand-rolling.

2FA setup (`POST /auth/2fa/setup` → `/confirm`) is necessarily self-service and `requireAuth`-gated rather than admin-controlled - it requires scanning a QR with the account owner's own device, so nobody else could complete it on their behalf anyway. `/setup` stores a secret on `users.totp_secret` without yet setting `totp_enabled`; only `/confirm` validating a real code from that secret flips `totp_enabled` to `true` and issues recovery codes - this prevents a user from locking themselves out by saving a secret they never actually got working. Recovery codes are shown exactly once (same one-time-reveal pattern as a new scanner API key or API token) and only their SHA-256 hash is stored (`totp_recovery_codes`, reusing `hashApiKey` from `ingest/apiKeyAuth.ts` - these are high-entropy generated values, not user-chosen passwords, same reasoning as API keys); a used code is removed from the array so it can't be replayed. `/auth/2fa/disable` requires re-entering the current password (not just being logged in) since the session alone isn't proof the person at the keyboard is still the account owner.

Login itself becomes two requests once `totp_enabled` is true: `POST /auth/login` verifies the password as before, but instead of setting `req.session.userId` (what `requireAuth` actually gates on), it sets a separate `req.session.pendingTotpUserId` and responds `{requiresTotp: true}` - `userId` stays unset until `POST /auth/login/verify-totp` accepts a code, so a password-only request can't reach any authenticated route no matter what, without needing a separate "half-authenticated" check duplicated across every route. Both the password-success and totp-success paths funnel through one shared `finishLogin()` helper, which regenerates the session (rotating the session id on this privilege change, incidentally dropping `pendingTotpUserId` since regenerate creates a fresh session). TOTP attempts get their own rate-limit key (`totp:<username>`, same `rateLimiter.ts` mechanism as login) rather than reusing the password one - a correct password should reset the password-guessing counter even if the code that follows is wrong, since those are different attack vectors and conflating them would lock someone out of retrying their code after one password typo elsewhere in the flow.

The three other endpoints that check a caller-supplied secret against the account (`/auth/2fa/confirm` and `/auth/2fa/recovery-codes/regenerate`, both TOTP codes; `/auth/2fa/disable`, a password re-check) get the exact same `isLockedOut`/`recordFailure`/`recordSuccess` treatment, each with their own key prefix (`totpsetup:`/`totpregen:`/`disable2fa:`) - a real gap a CodeQL scan caught: only `/login` and `/login/verify-totp` had this originally, even though these three are just as much a guessable-secret check against an authenticated session (relevant if a session is hijacked or CSRF'd) as the login flow itself is against a fully unauthenticated caller.

An admin can turn a user's 2FA back **off** (`POST /api/users/:id/reset-2fa`) for when a device is lost - but can never turn it **on** for someone else, consistent with setup being inherently self-service. This is the one place `users/routes.ts` (otherwise entirely `requireAdmin`) acts on another user's account security state.

**An admin can also make 2FA mandatory for every admin account, fleet-wide** — a single global toggle (`app_settings.require_admin_totp`, migration `1742200000000_app_settings.js`, the same singleton-row-id-1 idiom as `digest_email_state`/`webserver_tls_alert_state`/`scanner_release_cache`), read/written via `GET`/`PATCH /api/settings/app` (admin-only, Settings page's "Security" section). Deliberately a DB row rather than a `config.ts` env var, since an admin needs to flip this at runtime from the dashboard, not via a redeploy. `computeTotpSetupRequired(role, totpEnabled, requireAdminTotp)` is `true` only for `role === "admin"` — operator/user accounts are never gated by this setting no matter what it's set to. Both `POST /auth/login`/`verify-totp` and `GET /auth/me` compute and return this as `totpSetupRequired`; `App.tsx`'s `routeElement()` helper checks it *before* the role check (safe, since `totpSetupRequired` already implies `role === "admin"`) and redirects to `/account` — the one route deliberately left unguarded as an escape valve so the admin can actually reach the 2FA setup UI, with a banner explaining why they're stuck there until they finish. Completing setup calls a new `onMeRefresh` prop (re-fetches `/auth/me` into `App.tsx`'s state) so the redirect lifts immediately, without forcing a fresh login. There's no separate "super-admin" tier exempt from this - any admin, including one who just set up 2FA purely to satisfy the toggle, can turn `requireAdminTotp` back off again the same way.

### The webserver's own TLS certificate: upload, atomic replacement, and expiry alerting

The self-signed certificate `tls/generateCert.ts` writes to `config.certDir` (`/data/certs` by default) on first boot (see the root `CLAUDE.md`'s "Full stack" section) doesn't have to stay self-signed forever - the admin-only Settings page (`server/src/settings/routes.ts` + `frontend/src/pages/Settings.tsx`) lets an admin upload a real certificate/key pair to replace it, live, with no restart. `POST /api/settings/tls-certificate` accepts a small (256KB-capped) multipart upload (`multer`, in-memory storage) with `certificate`/`privateKey` fields; `certUpload.ts`'s `validateCertKeyPair` rejects anything that isn't a genuinely matching, not-yet-expired pair *before* touching disk - parses the cert (`crypto.X509Certificate`) and key (`crypto.createPrivateKey`) individually, confirms they match (`x509.checkPrivateKey`), and does a "belt-and-suspenders" `tls.createSecureContext({cert, key})` construction check that exercises the exact call the live listener itself uses - each failure mode gets its own plain-English 400, not a generic validation error. Self-signed detection (`x509.checkIssued(x509)`) is a real signature check, not a string comparison of subject vs. issuer text, confirmed against a real openssl-generated self-signed cert during development.

`saveCertKeyPair` writes atomically, mirroring the same discipline the scanner's own self-update binary replacement uses (see below): any existing `cert.pem`/`key.pem` are renamed aside to `cert.pem.bak-<timestamp>`/`key.pem.bak-<timestamp>` (not deleted - recoverable by an admin with filesystem access) before the new files are written to `.tmp` paths and `fs.renameSync`'d into place (`key.pem` at mode `0o600`, owner-only, same as `generateCert.ts` already used). `tls/activeServer.ts` holds a module-level reference to the live `https.Server` (set once in `index.ts` right before `.listen()`) specifically so the settings route doesn't have to import `index.ts` directly - after a successful upload, `server.setSecureContext({cert, key})` applies the new pair to every *new* TLS handshake immediately; already-established connections keep whatever context they negotiated, so there's no mid-request drop. Verified against a real listener (a fresh handshake after upload presents the new certificate) and a real container restart (the uploaded pair survives), not just reasoned about.

**A second, independent hourly check (`settings/certExpiryAlert.ts`) alerts when the webserver's own certificate - self-signed or uploaded - is nearing expiry**, firing a `webserver_certificate.expiring_soon` webhook once it's within 30 days of `validTo` (same window as the sibling `certificate.expiring_soon` check for scanned-host certificates). Deliberately keyed by certificate **fingerprint** rather than a boolean or a fixed timestamp (`webserver_tls_alert_state`, migration `1742000000000_webserver_tls_alert_state.js` - another singleton id-1 row, `fingerprint`/`alert_sent_at`): since this is a single filesystem artifact rather than a table of many rows, uploading a replacement certificate (previous paragraph) is automatically treated as never-yet-alerted the moment its fingerprint no longer matches whatever was last alerted - no separate "reset the alert state on upload" step needed. The Settings page itself shows a live countdown next to "Valid to" (`certExpiryDaysLeft`, reusing the exact same `certExpiryStatus`/`certExpiryLabel` helpers the fleet-wide Certificates page already uses for scanned-host certs, rather than a second copy of the same 30-day-window logic) - `(Nd left)` or `(Nd ago)` once already past.

### Webhooks fire from inside the ingest path, not a poller

`host.new` and `port.opened` (`src/webhooks/dispatch.ts`, called from `src/ingest/routes.ts`'s `/hosts` handler) fire synchronously during scan ingest, not from a periodic scan. `host.new` is detected via the `xmax = 0` Postgres idiom on the upsert's `RETURNING` clause (tells an insert and an ON-CONFLICT-triggered update apart in one statement); `port.opened` is skipped entirely for hosts that are new in the same ingest call, so one newly-discovered host with 10 open ports fires one webhook, not eleven. `certificate.expiring_soon` is the odd one out — a cert doesn't "become" expiring at a specific data-flow moment, so it's a periodic check instead (`src/webhooks/expiryAlerts.ts`, hourly, tracked via `tls_certificates.expiry_alert_sent_at` so it fires once per certificate, not every check). Dispatch itself is fire-and-forget for both channel types below (`dispatchWebhook` doesn't await the delivery call, only logs failures) — a slow or dead target must never slow down scanner ingest.

**A `webhooks` row is one of three channel types**: `channel_type = 'webhook'` (the original Slack/Discord-style JSON POST), `'teams'` (a Microsoft Teams Adaptive Card, see below), or `'email'` (`server/migrations/1741000000000_webhook_email_channel.js` + `1741200000000_webhook_teams_channel.js`, `webhooks_channel_type_fields_check` — the same "exactly one of these fields is set, matching the type" pattern as `scan_schedules`' `interval`/`cron`/`once` types above, here applied to `url`/`email_to`; `'teams'` shares the `url` column with `'webhook'`, since both are just a POST target — only the request body shape differs). All three share everything except the delivery mechanism: the same `events` array, the same `enabled` toggle, the same admin-only CRUD, and the same `/test` button — `dispatchWebhook` looks up all enabled channels in one query regardless of type and branches per-row on `channel_type` rather than running separate dispatch paths per type. `POST /api/webhooks` defaults `channelType` to `"webhook"` when omitted, so the shape the frontend already sent before this feature existed still works unchanged. `email_to` is a comma-joined recipient list, same multi-value convention as everywhere else in this app (`scannerAgentId` filters, `port`/`service`/`tag` search params) — each address individually validated at creation time (`emailListSchema`) rather than only discovered invalid on first delivery failure.

**Microsoft Teams needed its own request body, not just a new URL to POST the existing Slack/Discord-shaped `{text, content, event, data, timestamp}` JSON to** — Teams' classic "Incoming Webhook" connector happened to also render a bare `{text: ...}` payload (a coincidental overlap, not by design), but that connector is being retired across Microsoft 365 in favor of "Workflows" (Power Automate), whose webhook trigger expects a bot-framework `"message"` activity carrying an Adaptive Card attachment — confirmed against Microsoft's own Adaptive Card + Workflows documentation, not guessed. `buildTeamsAdaptiveCardBody(title, message)` (`webhooks/dispatch.ts`, exported so the `/test` endpoint sends the exact same shape a real event would rather than a hand-rolled second test body) builds `{type: "message", attachments: [{contentType: "application/vnd.microsoft.card.adaptive", content: {...AdaptiveCard}}]}` with two `TextBlock`s (a bold title from `EVENT_SUBJECTS`, then the plain message body) — covered by a real unit test (`webhooks/dispatch.test.ts`, pure formatting logic with no DB/network, same category as `lib/cron.test.ts` etc.) that parses the JSON back and asserts the exact envelope shape, plus a round-trip through values needing escaping (quotes, newlines) to catch a malformed-JSON regression before it ever reaches a real Teams endpoint.

Email delivery (`src/webhooks/email.ts`) goes through `nodemailer` against SMTP settings in `config.smtp` (`SMTP_HOST`/`SMTP_PORT`/`SMTP_SECURE`/`SMTP_USER`/`SMTP_PASSWORD`/`SMTP_FROM`) — deliberately **not** `required()` like `databaseUrl`/`sessionSecret`, since a deployment that never creates an email channel (the pre-existing default for every install before this feature) shouldn't be forced to configure SMTP it'll never use. The transporter is built lazily on first use and cached (`getTransporter()` in `email.ts`) rather than at startup, so a webserver with no SMTP configured never even attempts to construct one until an admin actually creates an email channel and something tries to fire it — at which point `sendEmailAlert` throws a clear "SMTP is not configured" error rather than a raw nodemailer connection failure; both `dispatchWebhook` and the `/test` endpoint surface that the same way they already surface a dead webhook URL. `dispatchWebhook` derives a plain-English subject line per event (`EVENT_SUBJECTS`) for the email case — a webhook channel has no equivalent need, since `event`/`data` already ride along in the JSON body itself.

**`vulnerability.high_epss` and `digest.daily` are the two newest events, both periodic checks like `certificate.expiring_soon` rather than ingest-path-triggered like `host.new`/`port.opened`** — neither "a CVE's score crosses a threshold" nor "it's a new day" is a moment that happens during scan ingest. `vulnerability.high_epss` piggybacks on the existing EPSS sync tick (`cve/epssSync.ts`'s `checkHighEpssAlerts`, called unconditionally at the end of every tick, not just when a refresh happened — a lowered `EPSS_ALERT_THRESHOLD` or a previously-failed dispatch should still get picked up on the very next tick) rather than running its own separate ticker: any `epss_cache` row at or above `config.epssAlertThreshold` (default 0.5) with `alert_sent_at IS NULL` fires once, resolving affected hosts/ports via the same `cve_cache`/`current_host_ports` join `vulnerabilities/routes.ts` uses for the fleet view, just filtered to one CVE id. `alert_sent_at` is never re-armed (same "fire once per row" idiom as `tls_certificates.expiry_alert_sent_at`) — a score oscillating around the threshold day to day can't spam repeat alerts for the same CVE. A CVE that clears the threshold but currently matches zero open ports (the port closed, or the CPE stopped appearing) still gets marked alerted with no webhook fired, so it isn't rechecked forever.

`digest.daily` is its own hourly ticker (`digest/emailDigest.ts`, same cadence as `webhooks/expiryAlerts.ts`) that fires once when `now.getUTCHours() === config.digestEmailHourUtc` (default 8 UTC) and a persisted `digest_email_state` singleton row (`id` always `1`) shows it hasn't already sent today — persisted rather than an in-memory flag specifically so a webserver restart landing within the configured hour can't double-send, same reasoning as `expiry_alert_sent_at`/`scan_schedules.last_run_at`. **A real bug caught by this feature's own integration test, not just reasoned about**: node-postgres's default type parser returns a Postgres `date` column as a JS `Date` (midnight UTC), not the plain `"YYYY-MM-DD"` string it was written as — comparing it directly against `todayUtc` via `===` silently never matched, so the "already sent today" guard never actually triggered and the digest would have re-sent on every hourly tick throughout the configured hour. Fixed with a small `toDateOnlyString` normalizer (`Date | string → "YYYY-MM-DD"`) rather than trusting the `ColumnType`'s declared TS type, which had made the same wrong assumption. `dispatchDigestEmail` reuses `digest/routes.ts`'s exported `computeDigest(from, to, allowedScannerAgentIds)` — the exact function backing the interactive Digest page — for the last 24h ending "now", scoped to every scanner (`allowedScannerAgentIds: null`, a background job with no session to restrict by, same as `savedSearches/checker.ts`'s periodic check), so the emailed digest can never drift from what the dashboard's own Digest page would show for the same window. The plain-text formatting (`formatDigestEmail`) serves both channel types unchanged, same as every other event's `message` — a webhook channel renders it as-is in Slack/Discord, an email channel has no separate HTML body option.

**`scan.stale`, `scanner.update_failed`, and `scan_queue.backlog` are three operational-health events, `webhooks/operationalAlerts.ts`'s `startOperationalAlerts()`** - a 5-minute ticker (`CHECK_INTERVAL_MS`), deliberately far more frequent than the hourly certificate-expiry checks: a scan that's died mid-run or a queue that's stopped draining is actionable right away, not just "worth knowing about sometime today." `checkStaleScans()` finds `scan_jobs` rows still `status = 'running'` that `lib/staleness.ts`'s `isStaleScanJob` (the same activity-aware, `app_settings.stale_scan_threshold_minutes`-based check the Dashboard's own `is_stale` badge already uses - see "Active scans and scanner agent versions" above) considers stale and haven't been alerted yet (`scan_jobs.stale_alert_sent_at`, migration `1742100000000_operational_alerts.js`) - fires once per row, forever, same "a scan_jobs row is created fresh per scan and either finishes normally or stays stuck forever" reasoning as `tls_certificates.expiry_alert_sent_at`. `checkQueueBacklog()` groups `scan_requests` still `pending` by scanner agent, and for any group whose oldest row exceeds `config.queueBacklogThresholdMinutes` (default 30, independently configurable from Fleet Health's own client-side 30-minute heuristic below, "since unlike that page's coloring, this one has a real side effect") fires once (`scanner_agents.queue_backlog_alert_sent_at`) - but unlike `stale_alert_sent_at`, this dedup flag is explicitly **cleared** back to null for any agent no longer in backlog after each tick, since a queue backlog is a recurring condition that should be able to alert again, not a one-time event. `scanner.update_failed` fires synchronously from `PATCH /api/ingest/update-outcome` (see the root `CLAUDE.md`'s "Scanner self-update" section) the moment a self-update exhausts its retries - no dedup column needed, since a fresh attempt only ever starts after an admin explicitly re-triggers it.

**Every actual delivery attempt (success or failure) is now recorded, not just logged to stdout** - `webhook_deliveries` (migration `1742300000000_webhook_deliveries.js`: `id bigserial`, `webhook_id` FK `ON DELETE CASCADE`, `event`, `success`, `status_code`, `error`, `created_at`, indexed on `(webhook_id, created_at DESC)`). `recordDelivery()` (`dispatch.ts`, exported so the `/test` endpoint's own attempts get recorded the same way as a real event) is called from every delivery path (email, and the shared webhook/Teams `fetch`) and trims each webhook down to its most recent 50 rows via a `DELETE ... WHERE id NOT IN (SELECT ... ORDER BY created_at DESC LIMIT 50)` subquery - a diagnostic tail trimmed to a fixed count at insert time, not a retained record like `audit_log` (which keeps everything until it ages out of the host-retention window - see "Host retention" above). Best-effort like `recordAudit`: a failed insert is logged and swallowed, never allowed to affect the delivery it's recording. `GET /api/webhooks/:id/deliveries` (session-`requireAuth` only, not admin-gated - "seeing whether a webhook is actually working isn't more sensitive than seeing that it exists") backs a new per-webhook "History" button/modal (`WebhookDeliveriesModal.tsx`) on the Webhooks page, fetched once on open rather than polled, since past deliveries don't change.

### Saved searches alert on new matches, not on every check

A saved search (`saved_searches`, operator-level like tags/comments) stores a dashboard filter set exactly as `URLSearchParams` sends it (same flat, comma-joined-string shape `parseHostFilterParams` already parses from `req.query`) - `server/src/savedSearches/checker.ts` reuses `parseHostFilterParams`/`applyHostFilters` (both exported from `search/routes.ts` for exactly this reason) unchanged, so a saved search can never silently drift from what the dashboard itself would show for the same filters. A 5-minute ticker re-runs each saved search's query and diffs the resulting host-id set against `saved_search_matches` (last known matches) - only genuinely *new* matches fire a `saved_search.match` webhook; hosts that already matched last time stay quiet, and hosts that no longer match are removed from `saved_search_matches` so they'd alert again if they started matching in the future. This event is scoped like `host.new`/`port.opened`: any webhook subscribed to it fires for *every* saved search's matches, not just one - there's no per-search webhook targeting.

### The Digest is a fleet-wide diff over an arbitrary time range, not just "since now"

`GET /api/digest` (`server/src/digest/routes.ts`) takes `from`/`to` (both ISO timestamps, `to` defaults to now, `from` defaults to 24h before `to`, range clamped to 90 days) rather than a fixed set of preset windows - for every host with at least one observation in `[from, to]`, it compares that host's latest scan job *as of `to`* against its immediately preceding one (`host_scan_jobs` is bounded by `observed_at <= to`, deliberately not also bounded below by `from`, so the "previous" scan compared against can be arbitrarily old). This means a past-dated `to` doesn't just filter which recent changes to show - it reconstructs what the digest would have looked like at that point in time, since "latest" is relative to `to`, not to the actual current moment. The frontend (`Digest.tsx`) exposes this as two `datetime-local` inputs (From/To) rather than a duration dropdown, for exactly that reason - a fixed "last N hours" can't express "what changed between last Tuesday and last Thursday," only "what changed up to right now."

Each entry (both `newHosts` and `changedHosts`) also carries `observedAt`/`scannerAgentName` - a real, reported gap (both were simply absent from the response before), since without them a digest entry couldn't answer "when did this happen, and which scanner found it," useful once more than one scanner is in play or the window spans more than a day. Both come from the same `host_scan_jobs`/`ranked` CTE that already resolves each host's latest-as-of-`to` `scan_job_id` - `observed_at` is carried straight through from there, and `scannerAgentName` is resolved via one extra batched query (`scan_jobs` left-joined to `scanner_agents`, keyed by the distinct set of `latest_scan_job_id`s across all candidates) rather than one query per host. `scanner_agent_name` can be `null` if that agent was since deleted (its scan history is preserved rather than cascade-deleted, see "Deleting a scanner agent" above) - rendered as `"?"` in `Digest.tsx`, same convention as other scanner-name displays elsewhere in the dashboard.

The core computation (`computeDigest(from, to, allowedScannerAgentIds)`) is exported from `digest/routes.ts` rather than kept inline in the route handler, specifically so `digest/emailDigest.ts`'s daily email ticker (see "Webhooks fire from inside the ingest path, not a poller" above) computes the exact same thing the interactive Digest page would show for the same `[from, to]` window, rather than a second, potentially-drifting implementation.

### Trends is a fleet-wide time series, built entirely from data already being historized

`GET /api/trends?days=N` (`server/src/trends/routes.ts`, `N` default 90, clamped to 365) needed no new migration or scan-side data collection - it's a different read over columns already written for other reasons: `hosts.first_seen_at` (set once at insert), `scan_jobs.started_at`, `host_port_observations.observed_at`/`cpes` (append-only, see "Database shape" above), and `cve_cache` (see "CVE correlation" below). Five daily series come out of this: new hosts per day (grouped by `first_seen_at`), scans per day (`started_at`), distinct hosts *scanned* per day (distinct `host_id` in `host_port_observations` observed that day, any state - not filtered to `'open'` the way `openPorts`/`cveMatches` below are, since a host that got rescanned and came back all-closed was still scanned that day), open ports *seen* per day (distinct `(host_id, port, protocol)` observed in an `'open'` state that day), and CVE matches *seen* per day (distinct `(host_id, port, cve_id)` from an open port's `cpes` matching a `cve_cache` row that day - same join `vulnerabilities/routes.ts` uses, just grouped by `observed_at` day instead of returned as one fleet-wide list). `totalHosts` is a running cumulative total - a baseline count of hosts first seen *before* the window (so day one of a 7-day window isn't misreported as "7 hosts total" when 500 existed already) plus each day's new-host count added on top. `hostsScanned` carries the same "seen that day" honesty tradeoff one layer further than `openPorts`/`cveMatches` do: a host masscan probed but found zero open ports on gets no `host_port_observations` row at all that run (masscan only ever reports ports it sees open - see `scanner/CLAUDE.md`'s "Scan pipeline" section), so it won't count as "scanned" here either - this is a real, accepted gap, not a bug, consistent with every other "seen" metric on this page.

`openPorts` and `cveMatches` are both deliberately "seen" counts, not a true point-in-time inventory snapshot reconstructed for every past day - that would need the same "latest scan as-of X" logic `digest/routes.ts` uses per host, run once per day in the range, far heavier for a trend graph's marginal benefit. The honest tradeoff: a port (or a CVE match on that port) open for weeks without a rescan doesn't inflate every day's count, only the days it was actually (re)confirmed - consistent with `current_host_ports`' own documented limitation that a port's "current" state is only as fresh as its last actual observation. `cveMatches` carries one further layer of the same honesty tradeoff: `cve_cache` itself is a daily-synced snapshot per CPE (see `cve/sync.ts`), not historized per day, so a CVE newly published for an already-open, unchanged port surfaces on the day the sync noticed it, not the day the port was first seen open.

**A real off-by-one bug, caught by this endpoint's own integration test rather than reasoned about**: the first cut computed `since` as a bare `now - days*ms` and built the series as `days` buckets starting from `since` - which lands one day short of today, so today's own activity never appeared in the series at all. Fixed by anchoring the window to a UTC day boundary (`since` = midnight UTC, `days - 1` days before today) so the last bucket is always today's, inclusive - the test asserts today's bucket exists and reflects freshly-ingested data, which the original off-by-one version failed outright.

Respects the same per-user scanner-agent restriction as every other fleet-wide view (`getAllowedScannerAgentIds`, applied both to the Kysely `hosts` query and as `= ANY(...)` in the raw-SQL date-grouped queries, joining `host_port_observations` to `hosts` for the restriction since observations don't carry `scanner_agent_id` directly). On top of that session-level restriction, `?scannerAgentId=` (comma-joined, same convention as the Dashboard's own filter of the same name) lets a caller narrow further to one or more specific scanners - kept as its own independent `AND`-ed condition rather than merged into the restriction's own id list, so it can only ever narrow an already-restricted session, never widen it past what `getAllowedScannerAgentIds` allows. `Trends.tsx` sources the picker's options from the same `GET /api/agents` every other scanner filter in this app uses, rendered with the same `ScannerMultiSelect` component (see "Database shape" above) rather than a bespoke dropdown.

`Trends.tsx`'s three charts (cumulative "Total hosts (all time)," single-series "Hosts scanned per day," and a 4-series "Daily activity" line chart) are plain inline SVG - no charting library. The "Total hosts" heading is plain text, not paired with an inline number the way it briefly was - removed as inconsistent with every other chart heading on the page, none of which show one, and redundant with the chart itself. The "Total hosts" line deliberately does **not** use `--accent` (the user's personalizable theme color, orange/green/blue - see "Account-level preferences" below): an accent-blue user would otherwise see it render in the exact same hue as "Daily activity"'s "New hosts" series in the chart directly below, coincidental color identity between two unrelated metrics in two different charts. It uses a dedicated `--chart-headline` token (violet) instead, validated distinct from all three accent choices and from the activity-chart palette - confirmed as a real visual collision by actually screenshotting the blue-accent case (headless Chromium against a static preview built from the same color tokens) before fixing it, not just reasoned about. "Hosts scanned per day" sits directly below "Total hosts" and needed the identical treatment for the identical reason - two stacked single-line charts in the exact same violet would read as the same series at a glance - so it gets its own `--chart-scanned` token (green, categorical slot 6), validated standalone against `--chart-headline` (the only color it's ever visually adjacent to, since single-series charts render no legend to pair it against the activity chart's own palette) via `scripts/validate_palette.js` against this app's actual `--panel` chart-surface color, not the skill's own default surface. The activity chart's 4th series ("CVE matches seen", added alongside the `cveMatches` field above) uses `--chart-series-4` (yellow, categorical slot 4 in the dataviz skill's reference palette) - re-validated via `scripts/validate_palette.js` against all four slots together rather than appended on faith, since the reference palette's own docs flag slot 4 as unsafe for *all-pairs* chart forms (scatter/bubble/choropleth); a line chart only needs the *adjacent* pairlist, which this passes in both themes.

The Chart/Table toggle (`showTable`) is styled and positioned identically to the Dashboard's own Grid/Table toggle (`.view-toggle`, two buttons, active state via `.active`) - pushed to the far right of the controls row, with the day-range chips on the left, rather than a `<select>` or a third chip group, for the same "pick one of two views" interaction the Dashboard already establishes elsewhere. The scanner filter sits in its own `.list-controls` row above that one, aligned far left - not squeezed in between the day-range chips and the view toggle, since it filters a different axis (which scanners' data counts) than either of those.

### CVE correlation is synced daily, not looked up live

`server/src/cve/sync.ts` runs once at startup and then every 24h: it collects every distinct CPE currently seen across `current_host_ports` (nmap's own per-port fingerprinting, not a separate probe), skips ones already cached within the last 7 days, and queries the NVD REST API (`cve_cache` table, keyed by CPE string) for the rest — rate-limited (NVD allows 5 req/30s without a key, 50/30s with one; set `NVD_API_KEY` to use the higher limit). The host detail endpoint only ever reads from `cve_cache`, never calls NVD on the request path, so viewing a host stays fast regardless of NVD's own latency or rate limits. nmap emits CPEs in the older 2.2 URI form (`cpe:/a:vendor:product:version`); NVD's `cpeName` param needs the 2.3 formatted string, so `cve/cpe.ts`'s `cpe22to23` does a pragmatic conversion (not a full binding-spec implementation — nmap doesn't produce the packed edition/sw_edition fields the full spec allows for anyway). A 404 from NVD means "no exact CPE dictionary entry", which is the normal outcome for a versionless CPE (e.g. nmap detecting a product but no version) — treated as zero CVEs, not an error. The main dashboard search's free-text `q` also matches against this cache (raw SQL in `applyHostFilters`, joining `current_host_ports.cpes` to `cve_cache` and unnesting its `cves` jsonb array — no Kysely builder helper for jsonb, same reasoning as the CIDR match in the same function) so searching a CVE id works the same as searching a hostname or banner. `server/src/vulnerabilities/routes.ts` is the fleet-wide equivalent of the per-host lookup — same cache, same raw-SQL unnest approach, but `CROSS JOIN LATERAL jsonb_array_elements` instead of a per-port `Map` dedup, since the fleet view intentionally shows one row per host+port+CVE rather than collapsing them.

**EPSS (Exploit Prediction Scoring System) is a second, independent daily sync** (`server/src/cve/epssSync.ts`, `startEpssSync()`, wired into `index.ts` alongside `startCveSync()`) that scores the *likelihood* a CVE is actually exploited, on top of NVD's CVSS *severity* score - two CVEs can share the same CVSS "critical" rating while having wildly different real-world exploitation probability, and EPSS is what lets the Vulnerabilities page and a host's per-port CVE badges distinguish them for prioritization. It's a genuinely separate cache table, `epss_cache`, keyed by **CVE id** rather than CPE (`cve_cache`'s key) - EPSS scores a specific vulnerability, not a product/version. The sync reads its candidate CVE-id set back out of `cve_cache` itself (`SELECT DISTINCT cve_elem->>'id' FROM cve_cache CROSS JOIN LATERAL jsonb_array_elements(cves)`) rather than re-deriving from `current_host_ports`, so EPSS only ever gets synced for CVEs already known relevant to this fleet - it can never score something the CVSS sync hasn't already surfaced. Batched (`BATCH_SIZE` 100 CVE ids per request to `https://api.first.org/data/v1/epss`, comma-joined - the API accepts a batched query, no per-CVE round trip needed) with a small inter-batch delay as a good-citizen courtesy, not a documented rate limit (unlike NVD, FIRST publishes none for this endpoint). **Re-checked every 24h** (`STALE_AFTER_MS`), deliberately shorter than `cve_cache`'s 7-day staleness window - EPSS's underlying model is recomputed daily by FIRST.org, so unlike CVSS/description text (which genuinely doesn't change once published), a week-old EPSS score can already be stale. A CVE with no EPSS entry (reserved/rejected, or the sync hasn't caught up yet) simply isn't upserted, leaving any previously-cached value in place rather than clearing it - same "don't erase a previously-captured value on an inconclusive re-check" reasoning as the OS/MAC-address `COALESCE` upserts on `hosts` (see "Database shape" above).

Both `vulnerabilities/routes.ts` (fleet-wide) and the per-host port list (`search/routes.ts`'s `GET /api/hosts/:id`) `LEFT JOIN`/look up `epss_cache` alongside the existing `cve_cache` join - left, not inner, since a CVE without a cached score yet must still show up (same "absence isn't an error" reasoning as NVD's own 404 case above). The Vulnerabilities page adds a sortable EPSS column (`Vulnerabilities.tsx`, `epss_score`); a host's per-port CVE badges (`HostDetail.tsx`) append the EPSS percentage inline and add it to the badge's tooltip alongside the CVE description, when a score is cached. A high-enough score also fires a `vulnerability.high_epss` webhook - see "Webhooks fire from inside the ingest path, not a poller" above.

**CISA's Known Exploited Vulnerabilities (KEV) catalog is a third, independent sync** (`server/src/cve/kevSync.ts`, `startKevSync()`, wired into `index.ts` alongside `startCveSync()`/`startEpssSync()`) providing a qualitatively different signal from both of the above: CVSS is severity (how bad *if* exploited), EPSS is a predicted probability (how likely to *be* exploited), and KEV is a confirmed fact (CISA has evidence it *is being* exploited right now). Structurally the simplest of the three syncs - CISA publishes the entire catalog as one bulk JSON file (`https://www.cisa.gov/sites/default/files/feeds/known_exploited_vulnerabilities.json`, ~1300+ entries), so there's no per-CVE batching or candidate-set derivation the way EPSS needs; every sync just fetches the whole thing and upserts it. Also keyed by **CVE id** like `epss_cache` (`kev_cache` - `vendor_project`/`product`/`vulnerability_name`/`date_added`/`due_date`/`known_ransomware_campaign_use`, matching CISA's own field names). The upsert deliberately never touches `alert_sent_at` on conflict (same "don't erase a previously-captured value on a routine re-check" reasoning as EPSS's own upsert) - but unlike `cve_cache`/`epss_cache`, which only ever grow or get individually refreshed, `kev_cache` also deletes any row whose `cve_id` no longer appears in the freshly-fetched catalog, since CISA does occasionally delist a CVE and this table is meant to mirror the catalog's *current* complete state, not accumulate history.

`checkKevAlerts` mirrors `checkHighEpssAlerts` almost exactly (same `cve_cache`/`current_host_ports` join to find affected hosts, same "mark alerted even with zero matches so it isn't rechecked forever" handling for a KEV entry that doesn't affect anything currently open) but with a structurally simpler trigger condition - EPSS fires when a *numeric score* crosses a configured threshold, KEV fires for *every* unalerted row unconditionally, since membership itself is binary (a CVE either is or isn't confirmed actively exploited - there's no equivalent of `EPSS_ALERT_THRESHOLD` to configure). Fires `vulnerability.kev`, a new webhook event alongside `vulnerability.high_epss` (`webhooks/dispatch.ts`'s `WebhookEvent`/`EVENT_SUBJECTS`, `webhooks/routes.ts`'s `EVENTS` array and zod enum, `Webhooks.tsx`'s `ALL_EVENTS`).

Both `vulnerabilities/routes.ts` and the per-host port list `LEFT JOIN kev_cache` the same way they already `LEFT JOIN epss_cache` - left, not inner, since most CVEs are never KEV-listed at all, which is the normal case, not an error. **A real, caught-before-shipping bug**: `kev_cache.date_added`/`due_date` are Postgres `date` columns, and node-postgres returns those as JS `Date` objects, not the plain string the column's own name suggests - the exact same class of bug `digest/emailDigest.ts`'s `toDateOnlyString` was originally written to fix for `digest_email_state.last_sent_date` (see `digest.daily` under "Webhooks fire from inside the ingest path, not a poller" above). Since a second, independent call site now needed the identical `Date | string | null -> "YYYY-MM-DD" | null` normalization, `toDateOnlyString` was pulled out of `emailDigest.ts` into `lib/dateOnly.ts` (alongside the existing, opposite-direction `parseDateOnly`) and exported for real, rather than adding a third hand-rolled copy - `emailDigest.ts` and its own integration test now both import the shared one instead of keeping a private copy. `vulnerabilities/routes.ts`'s raw `sql<>`-tagged query has to apply this manually before `res.json()` (Kysely's raw `sql` tag doesn't run column-type transforms the way `db.selectFrom` does), while `search/routes.ts`'s `db.selectFrom("kev_cache")` call gets the `Date | null` typing for free from `KevCacheTable`'s own `ColumnType` declaration in `db/types.ts` and just needs the same `toDateOnlyString` call at the point it's read.

The Vulnerabilities page adds a "Known Exploited (CISA KEV)" filter chip and a sortable KEV column (`Vulnerabilities.tsx`) - a red `.kev-badge` (`styles.css`), visually distinct from `.cve-critical` (also red, but for a different reason - CVSS severity, not confirmed exploitation) since the two are independent signals that can disagree (a KEV-listed CVE isn't always CVSS-critical, and vice versa). **KEV-listed rows sort ahead of CVSS score, not folded into the same sort key** - the fleet-wide list's default sort now checks KEV membership first, CVSS score as the tiebreaker, since a confirmed-exploited "high" is more urgent than an unexploited "critical". A host's per-port CVE badges (`HostDetail.tsx`) get the same badge rendered alongside the existing CVE badge, with a tooltip naming the date added and (when applicable) known ransomware campaign use.

### Frontend

Plain React + Vite, no state management library. `frontend/src/api.ts` is a thin typed fetch wrapper — one function per endpoint, cookies included for session auth. There are three fully separate auth chains, and a route only ever uses one: session auth (dashboard, `auth/middleware.ts`), scanner API keys (ingest, `ingest/apiKeyAuth.ts`, one key per `scanner_agents` row, scoped to that scanner submitting its own scan results), and API tokens (`apiTokens/tokenAuth.ts`, `/api/v1/*`, for external non-interactive callers like SOAR/enrichment tools — read host data and trigger rescans, but never submit scan results or touch anything session/RBAC-shaped). All three hash their secret with SHA-256 for lookup (`hashApiKey`, shared) rather than bcrypt, since these are high-entropy generated tokens, not user passwords.

`styles.css` caps the main dashboard layout at `max-width: 1600px` (bumped up from an earlier, more cramped `1200px`) so wide-screen viewports show more of the hosts table per row without horizontal scrolling; the screenshot lightbox (`97vw`/`97vh`) and the screenshot grid's minimum tile size were bumped in step, for consistency with the higher-resolution captures described above.

`Dashboard.tsx`'s table-view "IP" column sort (`compareIp`) detects address family by checking for `:` and compares IPv4 addresses octet-by-octet (so `10.0.0.2` correctly sorts before `10.0.0.10`, unlike a plain string compare) and IPv6 addresses hextet-by-hextet after expanding `::` shorthand to the full 8 groups (`expandIPv6Groups`) — a mixed list just puts every IPv4 address before every IPv6 one, consistently, since the two families have no natural shared numeric ordering. Confirmed against a live mixed IPv4/IPv6 host list in the table view: sorted ascending by IP, `10.0.0.5` (IPv4) appeared before both `2001:db8:9::1` and `2001:db8:9::42` (IPv6), which themselves sorted correctly relative to each other.

`components/PageHeader.tsx` is the one place that renders the brand/theme-toggle/username-role/Logout header *and* the main nav (`NavLink`s to every top-level section, current page highlighted) — every page component takes `me`/`onLogout` as props (threaded down from `App.tsx`'s single `me` state) and renders `<PageHeader me={me} onLogout={onLogout} />` rather than duplicating that markup. Both pieces used to be Dashboard-only, with every other page rendering just the brand/theme-toggle and a "← back to search" button (`navigate(-1)`) - now that the nav is always visible, that back button was removed from every page reachable via it. `HostDetail` is the one page that keeps its own "← back" button alongside `PageHeader`: it isn't a nav destination (reached by clicking a host row, not a nav link), and `navigate(-1)` preserves the exact search/filter/pagination state you came from, which the nav can't. When adding a new page, use `PageHeader`, not a hand-rolled `<header>`. The username/role text in the header links to `/account` (self-service 2FA setup - see "Two-factor authentication" above) rather than being plain text - deliberately not a `NavLink` in the main nav itself, since it's account-scoped rather than a top-level section every role sees the same way.

**The top nav is grouped into dropdowns, not one long flat row of links.** Left to right: `Scan Results` (flat, the dashboard itself) → a **Scanning** dropdown (Ad-hoc Scans, Schedule Scans, Scanner Agents, Scan History, and, admin-only, Scan Profiles and Excludes) → four flat links (Certificates, Vulnerabilities, Digest, Trends) → `Health` (flat, Fleet Health - see below) → an admin-only **Admin** dropdown (Webhooks, Users, Audit, API Tokens, Settings). `components/NavGroup.tsx` (new component, `{label, items: {to, label}[]}`) is the one dropdown implementation, reusing the toggle-button-plus-outside-click pattern `ScannerMultiSelect` already established rather than inventing a second one. Opens on click *and* on hover (`onMouseEnter`/`onMouseLeave`, closing after a 150ms grace timer rather than instantly - the panel sits below the toggle with a small gap, and a diagonal mouse path briefly exits the group's own bounding box crossing that gap) so a mouse user doesn't have to click to explore, while a touch device still gets a working tap-to-toggle. Closes automatically on route change, since a click on a `NavLink` *inside* the open panel is "inside" the outside-click detector's own ref and wouldn't otherwise be caught by it. The dropdown grouping went through one intermediate shape (a short-lived "Insights" group for Certificates/Vulnerabilities/Digest/Trends) that was dissolved back into flat top-level links the same day - four items didn't reduce enough visual clutter to earn a group of their own, unlike the six-strong Scanning cluster. Grouping Webhooks into the admin dropdown also fixed a real, if low-severity, gap: its nav link was previously shown to every role even though every Webhooks route was already `requireAdmin`-gated server-side - a non-admin who clicked it only ever got a 403 from the API, never anything from the nav itself saying it wasn't for them.

**Never put `display: flex` directly on a `<td>`** (bit us once on the Scanner Agents actions column) - it strips the element's table-cell box behavior (browsers effectively block-ify it), so the cell stops stretching to the row's actual height and its border ends up drawn too high on any row taller than that cell's own content. Put the flex layout on a `<div>` *inside* the `<td>` instead, and leave the `<td>` itself alone.

**`components/icons.tsx` is every icon in this app** - small, hand-drawn inline SVGs (24x24 viewBox, `stroke="currentColor"`, `aria-hidden`), no icon library, matching the same zero-UI-dependency approach as the Trends charts (plain inline SVG there too). Each icon inherits whatever color the surrounding text already has for free - a button's icon and label are always the same color, in both themes, with no separate icon-color CSS anywhere. `IconPlay`/`IconStop` are the two exceptions that override `fill="currentColor" stroke="none"` - play/stop are conventionally solid shapes in every media player, and a stroke-only outline wouldn't read the same way at this small a size. Nearly every `<button>` whose full visible content is a short action-verb label (Create, Save, Delete, Cancel, Revoke, Test, Search, ...) pairs one of these with its text via the shared `.btn-icon-label` class (`display: inline-flex; align-items: center; gap: 0.4rem`) - this applies equally to solid filled buttons and `.link-button`/`.export-link`-styled ones (e.g. Host Detail's "dismiss"/comment "delete", Excludes' inline "remove"), so a text-styled action still gets the same icon its filled sibling would. Three categories deliberately stay icon-free: buttons that already carry their own symbol (chip `×`, pagination `←`/`→`, sort-column `▲`/`▼`), pure state/view toggles (Chart/Table, filter chips, the day-range chips), and click-to-filter data-value buttons where the label *is* a data value, not a verb (a device type, OS family, or scanner name in the host list - prefixing "Windows" or "nginx" with an icon would be meaningless). When adding a new action button, check this list before deciding whether it needs one.

**The three fleet-wide finding pages (Vulnerabilities, Web Findings, Certificates) export via `components/TableExport.tsx`**, a shared CSV/JSON control - they previously had no export at all while Dashboard/Digest/Audit did, which was exactly backwards, since these are the lists handed to an auditor or pasted into a ticket. Two plain buttons rather than the modal Host Detail/Digest use: those offer a scoping choice and a PDF page snapshot, neither of which applies to a flat table, so the scope here is simply "the rows currently on screen" - it exports the already-filtered, already-sorted array the page is rendering, never a re-fetch, so an export can't silently disagree with the table above it. The CVE and nuclei exports include `triage_state`/`triage_note`.

### External API (`server/src/integrations/routes.ts`, `/api/v1/*`)

Deliberately its own router with its own auth (`tokenAuth`) rather than reusing `hostsRouter`'s session-authenticated routes: those assume an interactive session throughout (RBAC role checks, `req.session.username` for audit attribution), and this has a narrower, stable, external-facing surface — look a host up by `ip` or `hostname` (`GET /hosts/lookup`), trigger a rescan of it (`POST /hosts/rescan`), stop whatever scan is currently running against it (`POST /hosts/cancel-scan`), or queue a one-shot scan against a target that isn't a known host yet (`POST /scans/adhoc`). The first two share `server/src/rescan.ts`'s `requestRescan()` with the dashboard's own rescan button (`search/routes.ts`), so "infer port spec from currently known open ports, use whichever scanner last scanned this host" can't drift between the two callers; `cancel-scan` similarly shares `server/src/scanCancel.ts`'s `requestScanCancel()` with the dashboard's per-job "Stop" button (`scanJobs/routes.ts`). Audit entries from token-triggered actions are attributed as `actor = "api-token:<name>"` rather than a username, so they're distinguishable from interactive admin/operator actions in the audit log. There's one token type/scope (read + rescan-trigger + cancel-trigger + adhoc-scan-trigger) — no separate read-only tier, since splitting that wasn't asked for and would mean a second token type to manage for no clear benefit yet.

**`POST /scans/adhoc` is the External API's counterpart to the dashboard's own Ad-hoc Scans page** — the one route in this router that doesn't require an existing host at all, for the case this whole feature exists for: a SOAR/automation tool reacting to something it learned about from outside this app entirely (a firewall alert about a newly-seen IP, say) needs to scan it right now, not wait for it to already be a known host. Body: `scannerAgent` (name, not the dashboard's internal uuid — same convention every other route here already follows), `targetSpec`, `portSpec`, and the same flat-string `profile`/`nucleiProfile` fields `/hosts/rescan` accepts (`resolveNucleiProfileParam` mirrors `resolveProfileParam` for the independent nuclei pick — `"off"`/`"safe"`/an exact Custom nuclei profile name). Inserts into `scan_requests` with the identical shape `adhocScans/routes.ts`'s dashboard-facing `POST /api/adhoc-scans` already uses (`host_id: null`, same NSE/nuclei profile resolution), just triggered by a token instead of a session — same queue, same scanner-side pickup, so a token-triggered ad-hoc scan is indistinguishable from a dashboard-triggered one anywhere downstream except `requested_by`.

**`POST /hosts/rescan` accepts an optional `profile` field, a flat string rather than the dashboard's `{kind, profileId}` shape** — `"default"`/`"all_safe"` (case-insensitive), or the exact name of a Custom profile. `resolveProfileParam` (`integrations/routes.ts`) is what translates that into the `NSEProfileSelection` `requestRescan` actually takes: an external caller has no reason to know a Custom profile's internal uuid, only whatever name an admin gave it on the Scan Profiles page, so this looks the name up (`scan_profiles.name`) rather than exposing ids at all. An unrecognized name gets a `400` naming the valid options, resolved *before* `requestRescan` is even called, rather than surfacing `requestRescan`'s own less specific `ScanProfileNotFoundError` late. Omitting `profile` entirely still means Default, exactly as before this existed - this was a deliberate, initially-scoped-out gap (the doc comment on `requestRescan`'s own `profile` parameter default used to say the External API "never sends one - a scan-profile picker was never asked for there"), closed once Custom profiles became something an external caller might reasonably want to target. `requestRescan`'s `RescanOutcome` now also returns `nse_profile_label`, echoed back as `profile` in the External API's `201` response so a caller can confirm which profile a name actually resolved to.

**`GET /api/v1/openapi.json` + a Swagger UI at `/api/v1/docs`** describe this router - and *only* this router. The dashboard's own `/api/*` routes and the ingest API are deliberately undocumented: both are internal contracts (frontend↔backend, scanner↔webserver) that change alongside their single in-repo consumer, and publishing specs for them would invite external callers to depend on shapes expected to move. `/api/v1` is the one surface with third-party consumers who can't read this repo.

**Request schemas are generated from the same zod objects the routes validate against** (`integrations/openapi.ts`, via zod 4's native `z.toJSONSchema` - no extra dependency needed), so a field can't drift out of the spec without the validation changing too; adding `masscanRate` to `adhocScanSchema`, for instance, made it appear in the spec with its `minimum: 1` constraint automatically. Response bodies are hand-described and *are* therefore driftable - nothing validates them on the way out, so there's nothing to derive them from. `tests/integration/openapi.integration.test.ts` covers the half that can be checked mechanically: the documented path/operation set must match the router exactly.

Both routes are mounted on their own router **before** `integrationsRouter`, so they sit outside its `tokenAuth` chain - a browser loading Swagger UI can't attach a bearer token to its own page load, and codegen tooling expects an uncredentialed spec fetch. What's exposed is the shape of four endpoints and nothing else (no fleet data, no host records); the endpoints themselves stay token-authenticated, which the test suite asserts explicitly. Swagger UI needs inline script/style that the app-wide `helmet()` CSP blocks, so `docsRoutes.ts` re-applies a CSP **scoped to that route only** rather than weakening the global policy - notably with no external origins, since swagger-ui-express serves its assets locally (a CDN-hosted UI would break air-gapped deployments). Its default `validatorUrl` is also disabled: Swagger UI otherwise renders a "valid spec" badge by calling `validator.swagger.io` with this deployment's own spec URL, i.e. announcing to a third party that a PortTorch instance exists at that address - caught during verification by the scoped CSP blocking the request.

All three lookup-based endpoints (`hosts/lookup`, `rescan`, `cancel-scan`) share `lookupHost()` (`integrations/routes.ts`), which now has to account for a host's identity being `(ip, scanner_agent_id)` (see "Database shape" above) rather than `ip` alone - an `ip`/`hostname` match can legitimately return more than one row if two scanners each have a device at that address. Rather than silently picking one, `lookupHost` returns a three-way result (`found` / `not_found` / `ambiguous`); the `ambiguous` case surfaces as `409` with the candidate list (each with its `scannerAgentName`), and all three endpoints accept an optional `scannerAgent` (name) parameter to resolve it. This never breaks an existing caller that doesn't know the concept yet - the common case (one scanner, or an `ip` that only exists on one network) is still unambiguous without it.

`cancel-scan` only ever stops a scan triggered through the `scan_requests` queue (the same mechanism `rescan` uses) — never an arbitrary ad-hoc scan a scanner's own local `serve` REST API happens to be running that includes this host's IP inside a wider target range. That's because a host doesn't have a direct link to the `scan_jobs` row currently scanning it while that scan is still in progress — `scan_requests.scan_job_id` only gets set once the scan *finishes* (`PATCH /api/ingest/scan-requests/:id`). Instead, `cancel-scan` resolves it via the host's currently `claimed` `scan_requests` row: its `scanner_agent_id`/`target_spec`/`port_spec` are the exact values `pollOnce` (`scanner/internal/api/server.go`) used to create the matching `scan_jobs` row, so matching on all three reliably finds it.

**An API token can carry an optional expiry, set once at creation and never editable afterward** (`api_tokens.expires_at`, nullable, migration `1742400000000_api_token_expiry.js`) - `null` means "never expires," the pre-existing behavior for every token created before this column existed, needing no backfill. `POST /api/api-tokens` rejects an expiry date in the past outright (400) rather than silently creating an already-useless token. `tokenAuth.ts`'s lookup query gains `WHERE expires_at IS NULL OR expires_at > now()` alongside the existing `revoked_at IS NULL` check - an expired token fails auth the same generic way a revoked or simply-wrong one does, with no distinguishing detail leaked back to the caller either way. The frontend (`ApiTokens.tsx`) offers fixed presets (never / 30 / 90 / 365 days) that resolve to a concrete ISO timestamp client-side at creation time - the backend only ever stores a plain instant, with no notion of "expires in 30 days" as an ongoing relationship.

Dashboard state is split deliberately between three persistence layers, not just component state:
- **Search filters, sort-by-facet, and pagination** live in the URL (`useSearchParams`), not `useState` — Dashboard fully remounts when you click into a host and back, so anything only in component state resets to defaults on return. `updateFilters` (search/facets) always resets to page 1 by rebuilding a fresh `URLSearchParams`; `goToPage` copies the existing params and only touches `page`, so the two can't accidentally clobber each other.
- **View mode, visible table columns, and sort direction** are pure display preferences with no bearing on what data is fetched, so they live in `localStorage` (`porttorch.dashboard.tablePrefs`) instead — they don't need to survive in a shareable URL, but should survive across sessions.
- **Account-level defaults** (theme, hosts-per-page, default scanner filter, whether to show the Active Scans banner - all set from the Account page's "Preferences" section) live server-side on the `users` row instead, since these are meant to follow the person across browsers/devices, unlike the two purely-local layers above - see the dedicated paragraph below for how they interact with the existing per-browser theme toggle and URL-based filters without fighting either one.

**Account-level preferences** (`pref_theme`/`pref_hosts_page_size`/`pref_show_active_scans_banner`/`pref_default_scanner_agent_id`/`pref_timezone`/`pref_time_format`/`pref_accent_color` on `users`, migrations `1740100000000_user_preferences.js`, `1740300000000_user_timezone_time_format.js`, `1740600000000_user_accent_color.js`, and `1740700000000_user_accent_color_blue.js`) are a deliberately small, explicit set of columns rather than a jsonb blob - matches this codebase's general preference for typed columns over variable-shape storage when the shape is actually known and fixed. `GET /auth/me`, `POST /auth/login`'s `finishLogin`, and `POST /auth/login/verify-totp` all return the same `preferences` shape (via a shared `toPreferences()` helper in `auth/routes.ts`) so the frontend never has to reconcile two representations of the same thing - a fresh login gets preferences immediately, without a second round-trip. `PATCH /auth/preferences` is a genuine partial update: an *omitted* field is left untouched, an *explicit* `null` clears it back to "no override" - distinguishing those two requires checking `"field" in req.body` on the raw body, since zod's parsed output can't tell "the client didn't send this" apart from "this optional field happens to be undefined."

Each preference interacts with an existing, independent mechanism rather than replacing it, and each does so differently:
- **Theme**: the existing quick toggle (`ThemeToggle`, `lib/theme.ts`) is unchanged and still applies synchronously from `localStorage` before first paint (`main.tsx`, to avoid a flash) - the account preference only matters on a browser that's *never* had an explicit choice made on it (`hasStoredTheme()` returns false), applied once `/auth/me` resolves (`App.tsx`'s `handleMe`). It can seed a brand-new browser/device with your preferred theme, but can never silently override a choice already made on one already in use. Saving a theme preference from the Account page itself applies immediately to that browser too (same as clicking the toggle) - but only when a concrete theme was chosen there, not when clearing back to "Browser default," which intentionally leaves whatever's currently active alone.
- **Hosts per page**: `Dashboard.tsx` derives `pageSize` from `me.preferences.hostsPageSize ?? 50` and passes it explicitly on every `GET /api/hosts` call - the backend's own default (still 50, `search/routes.ts`) is unrelated and only kicks in for a caller that never sends `pageSize` at all (e.g. a raw API call).
- **Default scanner filter**: seeded into the URL's `scannerAgentId` param (still the singular query-param name — see `HostFilterParams.scannerAgentIds` below, comma-joined like `port`/`service`/`tag`) as a one-element list on a genuinely fresh tab/session only, guarded by a `sessionStorage` flag (`porttorch.defaultScannerConsidered`) rather than just "the URL doesn't have this param yet" - the latter can't distinguish "never set" from "the user just explicitly cleared it via the filter chip," and would otherwise silently reapply the default every time Dashboard remounts (e.g. navigating back from a host detail page), undoing an explicit "All Scanner" choice made earlier in the same browsing session. A real page reload or new tab resets `sessionStorage` and lets the default apply again, which is the intended "this is my default for opening the dashboard" behavior.
- **Active Scans banner**: a plain `me.preferences.showActiveScansBanner &&` gate ahead of the existing `activeScanJobs.length > 0` check - no interaction with anything else to reconcile.
- **Accent color**: `lib/accent.ts` mirrors `lib/theme.ts` exactly (`data-accent` attribute + `localStorage`, applied before first paint in `main.tsx`) - one CSS custom property (`--accent` in `styles.css`) is the only place any button/link/highlight color in this app comes from. Orange (`#ff6b25`) is the default, baked directly into the base `:root`/`:root[data-theme="light"]` blocks rather than an override, since it's a single flat value identical in both themes; green and blue are the two selectable overrides. `:root[data-accent="blue"]` is a single override block (blue is likewise a flat value in both themes), but green needed two: it keeps the darker/more-saturated shade (`#1f9d5a`) it always had for light backgrounds, so `:root[data-accent="green"]` (dark) is joined by a higher-specificity `:root[data-theme="light"][data-accent="green"]` (two attribute selectors on `:root`, placed after the plain one so it wins in light mode) - the one accent color whose override isn't a single flat value. Unlike theme, there's no "browser default" concept for accent (only three fixed choices, orange being the same as no override) - saving it on the Account page always applies immediately, it's never a no-op sentinel the way clearing theme back to "Browser default" is.
- **Timezone/time format**: unlike the others, these don't gate one specific piece of UI - they're read by `frontend/src/lib/formatDate.ts`'s `formatDateTime`/`formatDateOnly` helpers, which every page that renders a stored timestamp (Dashboard, HostDetail, ScannerAgents, Schedules, ApiTokens, Audit, Users, ScanHistory, Certificates) calls with `me.preferences` instead of a bare `new Date(...).toLocaleString()`. Both fields are `null`-means-no-override same as the rest: `timezone: null` passes `timeZone: undefined` to `Intl.DateTimeFormat`, which resolves to the browser's own local zone; `timeFormat: null` passes `hour12: undefined`, which lets the current locale decide (e.g. en-US defaults to 12h, de-DE to 24h). All timestamps everywhere in this codebase are stored/exchanged as UTC ISO strings (see the root `CLAUDE.md`'s "Logging is SIEM-oriented" section, and the scheduler sections above) - this is purely a display-layer preference, nothing server-side ever needs to know a user's timezone. `Intl.supportedValuesOf("timeZone")` (same engine on both Node and the frontend, so the two can't drift) backs both the Account page's dropdown and `auth/routes.ts`'s server-side `VALID_TIMEZONES` validation - with one explicit addition: "UTC" itself is added to both, since `supportedValuesOf` only enumerates canonical IANA identifiers and doesn't include the bare "UTC" alias at all (confirmed by testing - Node's `Intl.supportedValuesOf("timeZone")` list has no "UTC"/"GMT"/"Etc/*" entries whatsoever), even though `Intl.DateTimeFormat` itself accepts `timeZone: "UTC"` just fine - and UTC is likely the single most-requested option for this kind of tool. Like the other preferences, saving a new timezone/format on the Account page doesn't update the in-memory `me` object held by `App.tsx` (only the theme preference gets that special-cased immediate-apply treatment) - it takes effect on the next full page load/login, not instantly on the same tab, which is an accepted, pre-existing limitation of this preferences system, not something new introduced here. `Schedules.tsx`'s "Run at"/"Time" *input* pickers also read this preference (via `lib/zonedTime.ts`, see the Schedule Scans section above) - reinterpreting a picked wall-clock value as the user's timezone before converting to UTC is a different problem than formatting an already-known instant for display, so it's a separate code path, but the same underlying preference. `Digest.tsx`'s `datetime-local` inputs are the one place deliberately left as plain browser-local time, unconverted - a from/to range query has no stored value to get "wrong" the way a schedule's fire time would, so there's less at stake, and it's already documented separately (see the Digest section above).

The "← back" links/buttons across detail pages use `navigate(-1)` (real browser history), not a hardcoded `<Link to="/">` — the latter drops whatever search state was in the URL you came from.

**`HostDetail.tsx`'s prev/next navigation** steps through whatever (filtered/sorted) list of hosts was on screen when you clicked in, without a fresh query for every click. `Dashboard.tsx` passes `{ hostIds, filters, page, pageSize, total }` via router `state` from both the grid `<Link>` and the table row's `navigate()` - `hostIds` matches whichever order is actually visible (the table view's client-side column sort is independent of the grid's server-provided order, so it's computed per view, not shared). The top-left button relabels itself "← previous" and steps to the prior id in that list whenever one exists, falling back to its original literal `navigate(-1)` only at the start of the list or when there's no router state at all (e.g. the page was opened directly via a bookmark/refresh); "next →" only renders when there's somewhere to go. Running off either end of the current page fetches the adjacent page (`api.hosts`) and jumps to its first (next) or last (previous) host - always in the list's own server order, never the table's client-side sort, since that sort doesn't extend across separately-fetched pages. Each click pushes a new history entry (not `replace`), so plain browser back undoes one host at a time, same as the explicit "previous" button.

**Screenshots/RDP Screenshots and History all use the same "most recent stays visible, older gets grouped and collapsed" pattern** (`HostDetail.tsx`'s `groupByDate` helper + `.date-group` in `styles.css`) - a host scanned regularly for a long time would otherwise grow an unbounded flat list on this page. The two screenshot sections (headed "Screenshot(s)"/"RDP Screenshot(s)" - deliberately not the plain plural, since a host with exactly one capture reads oddly as "Screenshots") group by the *calendar date* of `captured_at`: only the single most recent date's cards render directly, every earlier date becomes its own collapsed `<details className="date-group">` showing that date and its item count in the `<summary>`. History groups differently - by *count*, not date: the most recent 5 scan runs (`historyGroups`, already newest-first) render directly regardless of how many different days they span, and only runs past that render as the same collapsed-by-date `<details>` groups - a host rescanned several times in one day would otherwise never collapse anything under a date-only split, unlike the screenshot sections where that's fine (a burst of same-day screenshots is exactly what should stay together, uncollapsed).

**A port number in the Open Ports table links to its own card in Service Banners & Enumeration further down the page** when one exists (`portsWithDetails`, the exact same has-a-banner-or-ftp-anon-or-smb-shares-or-nse_extra-or-ssh-hostkey condition that section itself filters on) - `styles.css`'s `.port-link` (accent-colored) vs. plain text for a port with nothing to jump to, so it's never a link to a section that doesn't exist. Each `banner-card` gets a matching `id="port-detail-{port}-{protocol}"` anchor and `scroll-margin-top` (so the browser's anchor-jump doesn't land it flush against the viewport edge); `html { scroll-behavior: smooth }` makes the jump itself readable as "the page moved" rather than an instant, disorienting cut. The Open Ports table's Banner column header carries an explanatory `title` tooltip for the same reason part of `scanner/CLAUDE.md`'s "Scan pipeline" section documents about the `banner` NSE script: it only ever populates for a service that greets a client unprompted (SSH, FTP, SMTP, ...) - HTTP(S)/RDP/etc. require the client to speak first, so `banner` genuinely never fires for those regardless of scan success, which the tooltip states directly rather than leaving it looking like a gap in coverage (the same info is available for those ports elsewhere - the HTTP(S) response headers/OCR text under Screenshots, or whatever NSE scripts under Service Banners & Enumeration did apply).

**Export** (`Dashboard.tsx`'s "Export data" link) opens `components/ExportModal.tsx` - the same generic `Modal` shell as the scan progress "Details" popup - offering three downloads rather than a single link + a row-shape `<select>` next to it, since a plain link can't express three destinations. `GET /api/hosts/export.csv?detail=host|port` has two row shapes: `detail=host` (default) is one row per host with `open_port_count` as a number; `detail=port` is one row per host+open-port instead (port/protocol/service columns, host columns repeated per row) for a flat asset-inventory export. `GET /api/hosts/export.json` is the third option - one JSON object per host (same host set/columns as `detail=host`) with a nested `openPorts` array, for a caller that wants the host-level fields and the full port list in one file without CSV's flatten-or-lose-the-nesting tradeoff; ports are fetched in a single second query keyed by the matched hosts' ids and grouped in application code, rather than a per-host round trip. All three go through the same `applyHostFilters`, so an export always matches exactly what the dashboard's current view is scoped to.

**Export can also be scoped to just the bulk-selected hosts, not everything the current filters match** - `HostFilterParams` grew a fourth kind of scoping (`ids: string[]`, alongside `q`/`ports`/`scannerAgentIds`/etc.), parsed the same way as every other comma-joined filter and applied in `applyHostFilters` as one more `AND`-ed `hosts.id IN (...)` condition rather than a separate ids-only code path per export route - all three export handlers (`export.csv`'s two detail levels, `export.json`) call the shared `applyHostFilters` already, so this one addition covers all three for free. Composing it as "yet another filter" rather than "replace the filters" is deliberate: it's still `AND`-ed with `allowedScannerAgentIds`, so a crafted `ids` list can never bypass the per-user scanner-agent restriction, even though in the common case the selected ids are already a subset of what the filters match anyway (selection happens from the already-filtered list). `ExportModal.tsx` shows a checkbox ("Export only the N selected hosts...") only when `selectedIds.length > 0`, pre-checked by default - unchecking it falls back to the original filter-scoped behavior.

**The host list itself grew a compact CVE/KEV risk indicator and click-to-filter badges** - two smaller additions bundled into the same round as the export change above. `search/routes.ts`'s `GET /api/hosts` query gained three more correlated subqueries (`cve_count`, `max_cvss_score`, `has_kev`) alongside the pre-existing `thumbnail_id`/`thumbnail_kind` ones - same pattern, same reasoning: scoped per host via `WHERE chp2.host_id = hosts.id`, not part of the `GROUP BY`, and therefore only ever evaluated for the current page's rows rather than the whole matched set. **A real bug caught by screenshot verification, not just reasoned about**: `cve_count` is `count(distinct ...)`, a Postgres `bigint`, which node-postgres returns as a *string* - the frontend's `RiskBadge` component checked `host.cve_count === 0` to decide whether to render anything at all, and a strict `===` against the string `"0"` silently never matched, so every host with zero CVEs rendered a stray "0 CVEs" badge instead of nothing. Same root cause as the pre-existing `ScanHistory.tsx` screenshot-count bug (see "Scan History is /active's historical counterpart" above) - fixed the same way, an explicit `Number(...)` wrap on `cve_count` before `res.json()`, this time on every row in a list rather than a handful of aggregate fields. `Dashboard.tsx`'s `RiskBadge` (used by both the grid card and a new toggleable "Risk (CVEs)" table column) reuses `cveSeverityClass`/the `.cve-badge`/`.kev-badge` styles the Vulnerabilities page and host detail already established, so the same red "KEV" marker means the same thing everywhere in the app.

Click-to-filter reuses the existing `toggleOsFamilyFacet`/`toggleDeviceTypeFacet` (previously only wired to the sidebar facets) and a new `toggleScannerAgentFilter` (the array-toggle pattern `togglePortFacet`/`toggleServiceFacet` already use, applied to `scannerAgentIds`) - the device type and OS family badges on a card, and the "via `<scanner>`" text on both card and table row, are now buttons that call these directly. This needed `hosts.scanner_agent_id` added to the host list's own `SELECT` (previously only `scanner_agents.name` was exposed, enough to *display* the scanner but not enough to *filter* by it without a separate name-to-id lookup). Every click handler needs `e.preventDefault()` (the grid card is a `<Link>`) and `e.stopPropagation()` (both the card and the table row have their own outer click-to-navigate handler) so clicking a badge filters instead of also opening that host's detail page.

A fourth addition from the same round, a "Copy link" button next to "Export data", was removed shortly after shipping at the user's request - no replacement, the Dashboard's URL-based filter state (see "Dashboard state is split deliberately" below) is still just as shareable by copying the address bar directly.

**Host Detail has the same "Export data" link/modal, but built entirely client-side** (`components/HostExportModal.tsx`) rather than linking to a backend route - the data (this one host's record plus its open ports, already including banner/CPEs/CVE ids/OS fingerprint fields the fleet-wide export doesn't carry at all) is already sitting in the page's own `data` state from the initial `GET /api/hosts/:id` load, so there's nothing a round trip would add. `lib/download.ts`'s `downloadBlob`/`csvEscape` (a `Blob` + object URL + a synthetic `<a download>` click, same `csvEscape` quoting rule as the backend's) are generic enough to reuse for any future client-side-only export, not specific to hosts. Three options instead of the Dashboard's three - no "host summary" shape, since Host Detail is already scoped to one host: CSV (one row per open port), JSON (the full host object plus the ports array, pretty-printed), and PDF.

**The PDF option is `window.print()` against the page's own DOM, not a PDF library** - no server round trip, no re-fetching screenshots, whatever's already rendered (loaded `<img>`s included) is exactly what gets printed/saved-as-PDF, so it can never drift from what the page actually shows. This only works because `styles.css` carries an `@media print` block making that raw print output actually usable, rather than a literal screenshot of the app chrome: it hides `header`/`.main-nav`/`.modal-backdrop` globally (harmless on any page, not just Host Detail) plus, scoped to `.host-detail`, every mutating control (prev/next, Rescan, the Export trigger itself, the probe-hostname/add-tag/add-comment forms, comment delete links) - none of them make sense in a static, already-generated document. It also force-overrides `--bg`/`--panel`/`--border`/`--text`/`--muted` to light-mode-like values regardless of the active theme toggle - browsers don't print CSS `background-color` by default (no ink wasted filling the page), so a dark-theme session's light-on-dark text would otherwise print as near-invisible light text on the default white page background; this was confirmed as a real problem (not just reasoned about) by rendering an actual PDF via a real browser's CDP `Page.printToPDF` against a dark-themed session before adding the override. Verified end-to-end with real ingested data including a real uploaded screenshot: the generated PDF (rendered back to PNG via `pdftoppm` for inspection) shows the host header, open ports table, banners, and the screenshot image itself, paginating correctly across page breaks - not just that `window.print()` was called.
